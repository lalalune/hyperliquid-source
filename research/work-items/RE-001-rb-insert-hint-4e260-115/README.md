## Bounded question

Where does a u8 key belong in a red-black tree: is it already present,
and if not, under which node does it insert? The hinted routine
0x5d4e260 answers that question when a caller already holds a nearby
node (a hint), and falls back to the unhinted routine 0x5d49910 when
the hint does not bracket the key. Together they are one complete
behavior — a hinted search plus its fallback — not a lone-window
fragment: the hinted routine's branches, the fallback's descent, and
the single consumer's use of the result are all pinned.

## Object layout (pinned by the disassembly)

- Tree object: header node at +0x08, so root = tree +0x10 (the
  header's parent slot), leftmost = tree +0x18, rightmost =
  tree +0x20, node count = tree +0x28. The header node itself is
  the end iterator, which is why the hinted routine compares the
  hint against tree +0x08.
- Node: color +0x00, parent +0x08, left +0x10, right +0x18, key
  byte +0x20 (the first payload byte after the 32-byte node base).
  Only the key byte is read by either routine.

## Algorithm (branch table, verified against both excerpts)

Unhinted 0x5d49910 (rdi = tree, esi = key byte): descend from the
root, going left when key < node key, else right, tracking the last
node and the last step's direction; stop at a null child. Empty tree
returns (0, header). If the last step went right, the last node
decides: key >= last key returns (last, 0); the shared tail returns
(0, last) when the last key is above the key. If the last step went
left and the last node is the leftmost, return (0, last); otherwise
take the predecessor: predecessor key >= key returns (predecessor,
0), predecessor key < key returns (0, last).

Hinted 0x5d4e260 (rdi = tree, rsi = hint node or header for end,
edx = key byte), in order:

1. Hint is end: node count nonzero and rightmost key < key returns
   (0, rightmost); otherwise run the unhinted descent (inlined in
   this routine, same branch table as above).
2. Key < hint key: hint == leftmost returns (hint, hint);
   predecessor key >= key falls back to 0x5d49910 (tail jump at
   0x5d4e3b0); predecessor key < key returns (0, predecessor) when
   the predecessor has no right child, else (hint, hint).
3. Hint key < key: hint == rightmost returns (0, rightmost);
   successor key <= key falls back to 0x5d49910; key < successor key
   returns (0, hint) when the hint has no right child, else
   (successor, successor).
4. Key == hint key returns (hint, 0).

Return convention: (existing node, 0) means the key is already
present; (0, parent) means the key is absent and inserts as a child
of parent; (node, node) occurs only on the hinted paths above and is
reproduced exactly. The binary's only observed consumer (the four
call sites in 0x5d85480) moves the first result aside and branches
when the second result is 0, i.e. it treats second == 0 as the
already-present case; that consumer check is pinned, the caller
convention for doubled pairs is not (see Unknowns).

The successor/predecessor steps run through the PLT stubs
`_ZSt18_Rb_tree_incrementPSt18_Rb_tree_node_base` (0x63f0ea0) and
`_ZSt18_Rb_tree_decrementPSt18_Rb_tree_node_base` (0x63f0df0); the
model implements the standard in-order walks. The binary never calls
either stub on the header sentinel on any path that reaches them, and
neither does the model. The hinted routine's end-hint walk block
repeats the unhinted descent's shape; the only actual transfer to
0x5d49910 is the fallback tail jump.

## Model and tests

- `tools/rb_insert_hint_4e260_115.py`: both searches over hand-built
  node/link trees, following the branch table above literally.
- `tests/test_rb_insert_hint_4e260_115.py`: 19 tests — empty tree,
  every existing key as the duplicate marker, below-leftmost,
  between-node child placement, above-rightmost, all hint paths
  (end, equal, leftmost, predecessor/successor brackets with a free
  and an occupied child slot, both fallbacks, rightmost), and the
  successor/predecessor walks. Model development caught and fixed
  four wrong test expectations (insertion parents for keys 12 and 27
  in the test tree), not model errors: the descent runs through
  nodes the first draft of the tests had skipped.

## Unknowns

- How the binary's callers consume a doubled (node, node) pair beyond
  the observed second-slot-null test in 0x5d85480; the model
  reproduces the pairs exactly and does not guess a caller
  convention.
- The payload stored after the key byte at node +0x21 and beyond;
  this packet pins only the key byte the search reads.
- The identity and purpose of the single calling function
  0x5d85480..0x5d878e2 beyond its four call sites and its
  second-slot-null test; its body is not pinned here.
- Whether the tree is a map or a set (key-only node vs
  key-plus-value node); the search reads only the key byte, so the
  packet does not distinguish them.
