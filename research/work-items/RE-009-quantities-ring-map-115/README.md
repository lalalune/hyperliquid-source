# RE-009 hl-quantities ring-or-tree record map, ring and B-tree remove, lookup, range, collect, vector growth (node #115)

Node #115 stores per-asset quantity records in a map that is either a ring buffer (VecDeque) of 24-byte records sorted by a u64 key, or, once the ring would hold 0x40 records, a B-tree; this work-item fixes the ring half, the inline B-tree lookup and the complete B-tree removal path (0x51d8900 with the predecessor swap 0x4d33ab0, the rebalancing leaf removal 0x4d19d30 and its merge / steal helpers 0x4ca1610, 0x4c958a0, 0x4c96370, checked on node shapes of height 0 to 3 and tall chains up to height 17) plus the vector growth rule 0x5963a10 / 0x5963650 for every element-size class, so a reconstruction can implement upsert (0x4dd6150), remove-by-key (0x4ddbf90), the shared binary search (0x57f6910), the triple lookup used by the range builder (0x5362120, 0x5b72670) and the limit collector (0x5b9ebf0) as pure functions; the B-tree repair chain is now checked up to height 3 and every single-byte change of it is either separated by a case or justified from the bytes.

- Component ID: RE-009 (state roots; owners in `l1/books.rs`, `l1/asset/pdi.rs`, `l1/spot_meta.rs`, `base/l1_map/entry.rs`, `l1/dex_registry/perp_dex.rs`)
- Target release: node #115, `artifacts/node/115/hl-node`, SHA-256 a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301
- Source commit: a8616af9432b8d8517b2af677880e117b7c28ef3 (workspace origin/main at the time of the run)
- Claim status: reimplementation checked against the interpreted bytes on 8200 cases; the tree arm of upsert (conversion 0x516b610, tree insert) is unresolved
- Scope: ring representation of 0x4dd6150 and 0x4ddbf90, the whole of 0x57f6910, 0x580dc90, 0x57eee80, 0x5362120 (ring and tree arms), 0x5b72670, 0x5b9ebf0, 0x5963a10 and 0x5963650 (also driven directly), and the tree remove chain 0x51d8900, 0x4d33ab0, 0x4d19d30, 0x4ca1610, 0x4c958a0, 0x4c96370 with the leaf-level and ancestor-level repairs. Not covered: the root 0x55bef10 that calls them, 0x3ce8df0, 0x50f0280, the call from 0x4ddbf90 into the tree remove (the chain is entered here at 0x51d8900 with a handle pointer) and the tree upsert / conversion (0x5b929a0, 0x51da3a0, 0x516b610, 0x51f21d0).

## Reproduce

    python3 tools/hl_quantities_ring_map_115.py --out research/work-items/RE-009-quantities-ring-map-115
    python3 -m unittest tests.test_hl_quantities_ring_map_115

The tool reads only the ELF bytes (fails on a different SHA-256), runs the listed functions in a small x86-64 interpreter and compares a Python model on every case; `measure.json` carries the counts below.

## Evidence

Observations (objdump of the bytes, addresses are virtual addresses of node #115):
- Handle (32 bytes): word 0 is the ring capacity or `0x8000000000000000` for the tree form, word 1 buffer / root pointer, word 2 head (ring) / height (tree), word 3 length. Ring record: key u64, then two value words.
- 0x57f6910 (94 instructions, no calls) takes (handle, &key) and returns rax = 0 present / 1 absent, rdx = logical index or insertion index. It splits the ring into its first slice (capacity - head records) and second slice, compares the first record of the second slice, then runs a branchless halving walk (`seta/sbb` three-way compare, unsigned) on the slice that can hold the key.
- 0x4ddbf90 remove-by-key: capacity `0x8000000000000000` selects the tree arm (not modeled); otherwise search, copy the 24-byte record out, `tail = len - 1 - index`; if `tail < index` it moves the tail down one slot with 0x580dc90, else it advances the head and moves the front up, and decrements the length. The result is `u32 tag` at +0 and the two value words at +4 (unaligned); a miss writes only the tag.
- 0x580dc90 is the ring copy (wrap_copy): copy `count` records from slot src to slot dst with wrap-around, memmove semantics, through slot 0x64df568.
- 0x4dd6150 upsert (key by value, value by address): ring below 0x40 records only; a hit swaps the value words and returns the old pair with tag 1; a miss calls 0x57eee80 (VecDeque insert at index; grows through slot 0x64e5e18 when full, then shifts the shorter side with 0x580dc90) and returns tag 0. A miss at 0x40 records or more converts to the tree through 0x516b610 (not modeled).
- 0x5362120 reads one key from three maps (ring or tree) into three `Option<(u64,u64)>` of 0x14 bytes each at +0, +0x14, +0x28. Its inline B-tree walk uses the node layout: values 16 bytes at +0, parent +0xb0, keys at +0xb8, parent index +0x110, length u16 at +0x112, edges at +0x118.
- 0x5b72670 builds a `Vec` of 0x3c-byte results, one per index of `start..end` with key `start + asset * 10000 + i` (`mul` overflow and `add` wrap each reach a separate panic slot, 0x64df870 / 0x64df520, with the same Location 0x64aa638); the count is `max(end - start, 0)` and counts above 0x222222222222222 reach the capacity error 0x64df498 before allocating.
- 0x5b9ebf0 collects pointers to 0x20-byte records into a `Vec<&Rec>` until the first record whose u64 at +0x18 is 0x2711 or more; that record is stored into an error slot (tag 0x158, pointer at +8) after dropping a previous non-empty value with 0x5630000. The vector starts with capacity 4 (one allocation of 0x20 bytes) and grows through 0x5963a10 (amortized doubling, minimum 4) and 0x5963650.
- 0x51d8900 (tree remove-by-key, rsi = &handle.root): a null root is a miss (tag 0). Otherwise it walks nodes with a linear scan (`seta/sbb` three-way compare per key, unsigned), descending `height` levels; a leaf miss returns tag 0. A hit at a leaf calls 0x4d19d30 directly (through 0x4d33ab0, height 0); a hit at an inner node takes the rightmost entry of the left subtree (0x4d33ab0 descends the last edge `height - 1` times), removes it with 0x4d19d30 and writes it into the inner slot, returning the old inner entry. The map length is decremented; when 0x4d19d30 reports an emptied inner root (flag byte) the root becomes edge 0, its parent link is cleared, the height drops and the old root is released (size 0x178).
- 0x4d19d30 (leaf removal, 0x7d8 bytes): memmove the keys (8 bytes each) and values (16 bytes each) down, length - 1. A leaf with 5 or more entries, or without parent, is done. Otherwise the parent index picks the left sibling (index > 0) or the right sibling (index 0; an empty parent reaches the panic at 0x4d1a4ef): if the two lengths plus the separator fit in 11 entries (`add; cmp 0xc; jae`) the helper 0x4ca1610 merges (right node into left, separator pulled down, parent edges shifted, back links renumbered), otherwise 0x4c958a0 (steal from the left, count 1) or 0x4c96370 (steal from the right) moves entries through the separator. The loop at 0x4d1a000 repeats this for ancestors while the node holds 4 or fewer entries, with count 5 - length for steals, merging inline (children released with size 0x118 for leaves, 0x178 for inner nodes) and renumbering moved edges; a parentless node sets the emptied-root flag when its length is 0.
- 0x5963a10 (grow-amortized, rdi = &{cap, ptr}, rsi = length, rdx = additional, rcx = align, r8 = element size): element size 0 or length + additional overflow is the capacity error (rdi = 0 to slot 0x64df498); new capacity = max(2 * cap, length + additional, floor) with floor 8 for one-byte elements, 4 up to 1024 bytes, 1 above; 0x5963650 rejects a byte size above 2^63 - align (or a multiplication overflow) as a capacity error; a zero old capacity allocates (0x64df480, or 0x64df590 with log2(align) when align is above 16, above the size, or not 1), a nonzero one reallocates (0x64df588 / 0x64df580); a refused allocation reports (align, size) to 0x64df498.

Inferences (not proven): the 10000 factor is the per-asset id stride and 0x2711 the exclusive upper bound of valid ids within one asset; the ring/tree switch thresholds 0x40 (to tree) and 0x20 (back to ring) come from the constants in 0x4dd6150 and 0x4ddbf90; contracts below stand for functions not decoded here.

Contracts (documented, not decoded): allocator slots 0x64df480 / 0x64df588 / 0x64df590 / 0x64df580, memmove slot 0x64df568, growth slot 0x64e5e18 (modeled as capacity max(2 * cap, 4) with the records re-linearized and head 0), panic slots 0x64df520 / 0x64df870, alloc-error slot 0x64df498, error-slot drop 0x5630000 (logged only).

## Implementation and comparison

`tools/hl_quantities_ring_map_115.py` holds the interpreter (copied core, with the LOCK prefix turned into an undefined-opcode halt so a mutant landing on one is detected), the pure models `search_model`, `wrap_copy_model`, `remove_model`, `deque_insert_model`, `upsert_model`, `triple_model`, `range_model`, `collect_model`, `tremove_model` (a node-by-node port of the B-tree removal: node objects with parent links, merge, steal left / right with a count, emptied-root pop, position tracking through rebalancing), `grow_model`, case generators for nine case sets, and the mutation harness. For the tree set the compared state is the whole reachable tree (node addresses, parent address and index, keys, values, children), the handle (root, height, length), the result option and the ordered list of released blocks (address, size); stale bytes past a node's length are ignored. Each case is run on the bytes and on the model; return values, outputs, the call log (for the range and collect sets) and the whole heap image must agree. Misses leave payload bytes unspecified in the bytes, so the compare masks them. Negative controls are single-byte mutations of every condition and of immediates / displacements of the ring-representation instructions in the listed bodies (the tree arms of 0x4dd6150 and 0x4ddbf90 are outside the mutation set); each mutant is run on the detection subset of every case set that executes it, then on up to 80 targeted cases that execute the mutated instruction. A mutant on an instruction no case executes is not replayed (its run cannot change); it is listed as unreached.

## Results and limitations

- cases 8200; negative controls 813; detected 733; equivalent 80 (see `equivalent-mutants.tsv`; every undetected mutant carries a reason, none is left open). Run time of one regeneration is about 2.5 minutes on 4 cores (the mutant stage uses a 4-process fork pool; results are collected in order, so the files do not depend on scheduling).
- Files: `body.tsv` (instruction bytes per function), `coverage.tsv`, `branches.tsv` (taken / fall-through executed), `routes.tsv` (cases per route), `cases-sample.tsv`, `controls.tsv`, `layout.tsv`, `summary.json`.
- Limits: the tree arm of upsert and the ring-to-tree conversion are unresolved (0x5b929a0, 0x51da3a0, 0x516b610, 0x51f21d0); the root 0x55bef10 and members 0x3ce8df0, 0x50f0280 are not covered; contracts replace the allocator, the growth slot and the error drop; the tree lookup is checked on trees of height 0 and 1 only; the tree remove is checked on shapes of height 0 to 3 (nodes of 3 to 11 entries, roots of 0 to 11, plus chains to height 17), not on trees containing duplicate keys or on heights between 4 and 17 other than the chains; the node allocator, the memmove / memcpy slots (0x64df568, 0x64df508), the release slot 0x64df4a0 and the panic slots are contracts; grow is checked with fixed fake block addresses and a 1 MiB allocation refusal limit.
- Equivalent mutants: seven undetected single-byte changes in the tree chain are justified from the bytes, not by cases: 0x4d33c7a (the compare is reached only when height & 7 is not 0, so height 8 never arrives), 0x4d19fee (the shifted spill read only changes r15, whose uses are spill slots and a compare against 2 that cannot fail for either value), 0x4d1a342 (the release size is overwritten before use because the guarding test at 0x4d1a358 is never taken), 0x4d1a47a and 0x4d1a47e (the unroll guard is entered with a positive multiple of 4 remaining edges), 0x4ca165a (the only caller merges only when left + right + 1 is below 12) and 0x4ca1888 (the leaf-level context never carries a height of 2). Each reason is also in `equivalent-mutants.tsv`; they are inferences from the disassembly, not proofs by execution.
- Heap layout: node addresses are spread over low bytes (pre-order slot times 0x300 plus a 0x10-step offset) because with a fixed stride the low byte of a node pointer is only ever 0 or 0x80, which hid a displacement mutant in 0x4c96370.
- Height 3: a new generator climbs two ancestor levels so that parents and grandparents of every length around the minimum fill are repaired; it separates the compare at 0x4d1a013.
- Relation to the assigned bundle (0x4dd6150, 0x55bd810, 0x55bef10): the bundle root 0x55bd810 calls 0x4dd6150 (upsert), which calls the ring and tree helpers fixed here; the roots 0x55bd810 and 0x55bef10 themselves are not reconstructed by this item.
- Next question: model the conversion between ring and tree (0x516b610, 0x5b929a0, 0x51da3a0) so the 0x40 / 0x20 thresholds can be checked, then the root 0x55bef10 that drives these maps.
