## Bounded question

How does node #115 register thread-local destructors: which routine does it,
which dispatch does it use (the libc fast path vs the pthread-key fallback),
what does the fallback registry hold, and how many registration sites exist?

## Answer (pinned)

- The registrar is `register_dtor` at **0x5ca0d20..0x5ca0e1f** (`(t, dtor)` in
  `(rdi, rsi)`). It passes the GOT slot **0x64fe448** as the `dso_handle`
  argument; that slot holds a RELATIVE relocation to **0x64efa20**
  (`__dso_handle` itself).
- **Fast path:** if GOT **0x64ec9b0** (`__cxa_thread_atexit_impl`, GLOB_DAT
  dynsym 198) is non-null, tail-jump to it with `(dtor, t, 0x64fe448)`.
- **Slow path (fallback registry):** a per-thread vector of 16-byte
  `(t, dtor)` entries, held in TLS slots relative to `%fs:0x0`:

  | slot | offset | contents |
  | --- | --- | --- |
  | guard | -0x1150 | 0 = active, -1 = registering, 1 = drained (later registration panics) |
  | capacity | -0x1148 | vector capacity |
  | vec_ptr | -0x1140 | entry array pointer (8 = `Vec::new()` dangling pointer after teardown) |
  | count | -0x1138 | entry count |

  The guard is checked at entry (non-zero jumps to the panic path at
  0x5ca0de6), set to -1, `key::enable` (0x5ca0e20) runs, the pair is appended
  (growing via `grow_one` 0x5c8b620 when count == capacity; new capacity =
  max(4, 2 × old capacity), pinned from the grow helper 0x5c8b980), and the guard
  returns to 0.
- `key::enable` creates the pthread key once: BSS key variable **0x64feda8**
  (initial 0), destructor function pointer from GOT **0x64fedb0**
  (RELATIVE -> the dtor runner 0x5ca53f0), `pthread_key_create` /
  `pthread_key_delete` / `pthread_setspecific` (GLOB_DAT dynsyms 199/200/201).
  The loser of the CAS race deletes its spare key. Three callers:
  register_dtor (0x5ca0d80), guard_alloc (0x5c9d286), guard_use (0x5ca4521).
- The **dtor runner** 0x5ca53f0..0x5ca5510 (the pthread-key destructor
  callback) drains the vector **LIFO** (`count -= 1; call vec[count].dtor(vec[count].t)`),
  frees the array, resets `(capacity, vec_ptr, count)` to `(0, 8, 0)` and
  increments the guard. It panics (via *0x64e12e0 -> 0x1680b70) if the guard
  is non-zero at entry. Its tail handles the guard object at `%fs:-0x428`:
  if the refcount at guard+0x00 hits 0, the guard dtor runs via GOT
  0x64dfe58 -> 0x5c98b40.
- The guard object (0x30 bytes, `malloc`'d in guard_alloc 0x5c9d1f0):
  +0x00 refcount = 1, +0x08 = 1, +0x10 epoch from the global counter at
  0x6500050, +0x18 = 0, +0x28 = 0. guard_use (0x5ca44a0) bumps the refcount
  and re-stores guard+0x10 at `%fs:-0x428`; guard_free (0x5c98b40) clears the
  first byte of the string at guard+0x18, invokes the callback at guard+0x20
  if non-null, then `lock decq guard+0x08`.
- **Census: 1153 registration sites in 604 distinct caller FDEs** (range
  0x14e1ee6..0x5d0050d), calling `*0x64e0510` (GOT slot, RELATIVE ->
  0x5ca0d20). **28 distinct destructors.** Two dominant TLS objects:
  - **-0x1130: 845 sites**, arc-dec destructors only (state byte +0x48;
    dominant 0x5cdf410, 651 sites).
  - **-0x1180: 287 sites**, slice-drop destructors only (state byte +0x20;
    0x26a05d0 173 sites, 0x4e39190 109 sites).
  - -0x10e0: 4 sites (0x5cffca0 / 0x5d00840); -0x470: 2 sites (0x5c7f7f0);
    -0x480: 2 sites (0x5c7f7d0); caller-passed: 13 sites, one per remaining
    destructor. Every destructor marks its state byte = 2, then drops the
    inner object when its refcount hits 0; see `records.json` for the
    per-destructor shape table (10 shapes across the 28).

## Method notes

- Sites were found by byte-scanning for `FF 15 <disp32>` targeting GOT
  0x64e0510, and cross-checked against a full-`.text` objdump grep
  (1153 both ways; `census.py --full-objdump-check` asserts this).
- A naive byte-level disp32 scan **misses** the `cmpq $0, GOT 0x64ec9b0` at
  0x5ca0d35 (its imm8 follows the disp32, shifting the next instruction);
  objdump is authoritative for that site.
- Per-site `(dtor, TLS offset)` resolution walks the caller FDE linearly;
  13 sites needed a guard-check cross-check because the linear walk crossed
  a branch boundary (e.g. site 0x5a60547: walk -0x1131 vs guard -0x1130).
  The guard check that gates a registration reads the object's own state
  byte, so it wins on disagreement; `census.py` counts these as
  `guard_corrected` (13) and `verify.py` re-derives them.
- **Correction found while building this packet:** offsets are canonical
  signed values. The immediate `0xffffffffffffeed0` denotes **-0x1130**
  (not -0x1230 as first read) and `0xffffffffffffee80` denotes **-0x1180**
  (not -0x1280). The two dominant TLS objects are therefore -0x1130 and
  -0x1180; the earlier "−0x1230/−0x1130 pair" reading was a hex-arithmetic
  error, caught when `census.py` was changed to emit canonical signed
  offsets and the distribution was re-checked.

## Observations, inferences, unknowns

- **Observed:** every fact above is read directly from the disassembly,
  relocations, or the census.
- **Inferred:** the TLS slots form a Rust `Vec<(ptr, dtor)>` plus a guard
  (the teardown reset `(cap, ptr, len) = (0, 8, 0)` matches `Vec::new()`
  with an 8-aligned 16-byte entry type, whose dangling pointer is 8); the
  28 destructors are monomorphized copies of a small set of shapes (the
  same body at different addresses, e.g. seven copies of the +0x48 arc-dec
  shape). The guard's 0/-1/1 states are read as a re-entrancy guard plus a
  drained flag; the exact Rust source names are not claimed.
- **Unknown:** the Rust source type of each TLS object and each destructor
  (no symbol names survive); which crate each caller FDE belongs to; the
  exact Rust identity of the two dominant TLS objects (only their offsets,
  state-byte positions and destructor families are pinned).
