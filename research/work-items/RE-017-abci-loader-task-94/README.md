# RE-017: state-loader task construction, polling and result handoff

A node-runtime Location-bearing entry reaches three state-future initializers, and one registration lane connects through matching queue fields to a conditional poll and result handoff, giving a reconstruction concrete ownership and outcome rules.

- Component ID: `abci` / RE-017, with runtime task plumbing as the bounded extension.
- Target release and full SHA-256: node #94, `artifacts/node/94/hl-node`, `3b7179cd967d1b13b683e05debfc685ad4c750e918226402d5d575eff1c0459f`.
- Source commit / reference commit: repository `56c0ec672bd8fdcfaa80f2db700a61e6240b3663`; unlicensed lead `references/can1357-hl` at `999556f6e0a474b8312db96ec3149e1c44e97c23`. The lead supplies no implementation here.
- Claim status: observation for the selected bytes, signed table displacements, relocations and conditional data movements; scheduler identity, runtime reachability and Rust types are inferences or unresolved as stated below.
- Scope included and excluded: 26 new unwind extents and the selected windows, transfers, decision branches, literals and table entries listed in the generated files. The previously studied `0x22ae8a0` state future and previously indexed `0x2046b70` consumer are boundaries, not newly owned functions. The RE-017 loader GOT, its call site, and the earlier materializer chain are not re-owned. Other target releases, begin/action/end-block execution and state-root construction are excluded.

## Evidence

All addresses below are ELF link-time virtual addresses; data and code file offsets are generated separately. Each selected `.eh_frame` record is reconciled with the `.eh_frame_hdr` entry and the complete selected extent is SHA-256 checked. An unwind extent is not, by itself, a complete source function boundary. The 84 fixed windows below bind the discussed observations; they do not claim complete instruction decoding or CFG reachability.

### Entry and task selection

A higher selected extent, `0x2893110`, has three direct paths into the initializer family. It calls `0x247bbf0` at `0x28934a0`, calls `0x247c020` at `0x2893845` (which calls `0x2032480`), and calls `0x2885a80` at `0x28939ee` (which calls `0x22b8920`). These are instruction-site observations; they do not establish that every arm is reachable in a particular deployment.

A runtime-builder result of 2 branches to a length-matched `Failed building the Runtime` diagnostic. The code at that failure passes a Location record at `0x56c6708`; its type-8 relocation points to the 14 bytes `src/hl_node.rs`, with line 5 and column 47. This anchors the selected failure context to a node source path without assigning the whole extent an original function name. A nonzero return after the `0x247bbf0` call reaches `failed to park thread`; return byte 2 after `0x247c020` reaches `Failed to Enter::block_on`. The exact diagnostic bytes and their separate contexts are in `diagnostics.tsv` and `locations.tsv`.

| Caller extent start | Initial zero byte | Input buffer | Call to launcher | Subsequent consumer boundary |
| --- | --- | --- | --- | --- |
| `0x2032480` | `0x2032514` | stack `+0x10` | `0x2032528` | `0x203253b` |
| `0x22b8920` | `0x22b899f` | stack `+0x18` | `0x22b89b3` | `0x22b89c6` |
| `0x247bbf0` | `0x247bd53` | stack `+0x70` | `0x247bd67` | `0x247bd80` |

In all three, the zero byte is at buffer offset `+0x216`. The enclosing jump tables' first four signed entries are in `jump-tables.tsv`; entry zero reaches each initializer and entry three reaches its consumer continuation. There is no claim about indexes outside those four. `0x2032480` additionally has a guard whose zero result bypasses the initializer. A raw `e8`/`e9` scan of the four executable sections finds these three candidate rel32 calls to `0x229ec10`; the fixed windows independently place these three at the selected instruction sites. Such a byte scan may match operands and says nothing about indirect transfers.

The selected outer caller `0x247c020` calls `0x2032480` at `0x247c115`. After a normal return it branches on the returned byte: value 2 reaches the context/wait path and, if that helper returns normally, retries at `0x247c0c0`; a different byte reaches the return path. If its initial fallback context lookup returns zero, it can return 2 without calling the inner function. If a fallback lookup during the wait path returns zero, the selected path supplies a length-matched `Result::unwrap()` error diagnostic. The behavior of those external helpers remains a boundary.

`0x229ec10` copies `0x6368` bytes from its input, obtains an allocation, copies the same length into it, and chooses between two task constructors using a thread-local word. Its ordered, conditional decisions are:

| Checked condition | Observed destination |
| --- | --- |
| Allocation result is zero | `0x229ed4f`, allocation-failure call |
| Thread-local flag is 2 | `0x229ed04`, cleanup and failure call |
| Counter is at least `0x7fffffffffffffff` unsigned | `0x229eddd`, failure call followed by `ud2` |
| Mode word equals 2 | `0x229edec`, cleanup and failure call |
| Otherwise, low mode bit is one | `0x23c3c70`, lane A |
| Otherwise, low mode bit is zero | `0x2888350`, lane B |

The table assumes the preceding helper calls return normally; it is not a claim that every raw word is reachable. In each lane the registration function passes the allocated future pointer into a constructor, which constructs a `0x80`-byte object. The constructor installs the table address at object `+0x10`, initializes the variant at `+0x30` to zero and places the future pointer at `+0x38`:

| Lane | Registration -> constructor | Relocated table word -> thunk -> poll wrapper | Table word at `+0x18` -> thunk -> reader |
| --- | --- | --- | --- |

| B | `0x2888350` -> `0x2003d20` | `0x5693650` -> `0x22a4460` -> `0x1d8e930` | `0x5693668` -> `0x229f710` -> `0x1d589c0` |

The four table words have type-8, symbol-zero relocations and zero captured file words; their addends, the constructor LEA targets and the thunks' signed jump displacements are regenerated. The separate selected generic dispatch window at `0x14c681e` loads a table from object `+0x10` and calls its first word with the object pointer.

### Conditional lane-B queue connection

The normal insertion arm in `0x2888350` passes the same newly allocated task pointer in both `rsi` and `rdx` to `0x27a8a90`. On that selected arm the latter retains the `rdx` value and returns it; the caller tests the result and, if nonzero, passes it to `0x4f6c870`. The thread-local branch leading to `0x4f6c8d8` dereferences the scheduling handle, adds `0xb0` and passes that queue address and the same task pointer to `0x4f72170`.

In the open-queue arm, `0x4f72170` either stores the task into both head and tail of an empty queue, or links it at the prior tail's `+0x08` and updates the tail. It increments the queue count. A closed queue instead takes a reference-release path. An all-ones count reaches the overflow failure path **after** the pointer stores; this packet does not assume rollback. Those observations are conditional on the selected branch and ordinary helper returns.

`0x14c5ad0` can load its dequeue callee from the separately verified relocation at `0x576fe38` -> `0x4f6d080`. In the shared-queue arm, the dequeue checks the count, acquires the lock and conditionally decrements the rechecked count before reading the head. A nonzero head is unlinked; the code clears the tail if the next pointer is zero, clears the removed node's `+0x08`, and returns that node. A zero count or a zero head takes a no-node path. In the inconsistent nonzero-count, zero-head case, the decrement occurs before the no-node path. The local-queue and lock-contention arms remain separate.

The relative address arithmetic on these selected arms is reproduced from instruction bytes:

| Field | Append, relative to queue | Dequeue, relative to its worker base | Effective offset if both shared bases are equal |
| --- | --- | --- | --- |
| Lock | `+0x00` | `+0x10 + 0xa0` | `+0xb0` |
| Head | `+0x08` | `+0x10 + 0xa8` | `+0xb8` |
| Tail | `+0x10` | `+0x10 + 0xb0` | `+0xc0` |
| Count | `+0x20` | `+0x10 + 0xc0` | `+0xd0` |

The producer's queue base is shared base `+0xb0`; `queue-layout.tsv` derives all four equalities and checks the matching node-link offset. A selected worker-context path also narrows the shared-base question: `0x14c60dd` reads a pointer from stack `+0x78`, and `0x14c6121` stores that pointer in its thread-local slot at base `-4392` plus `0x10`. The same stack word is reloaded at `0x14c61b9`, spilled at `+0x98`, and copied within a 16-byte block from stack `+0x90` to `+0x150`, placing it at `+0x158`; the worker later loads that word at `0x14c675d`. The launcher uses the same encoded thread-local base and passes the slot at `+0x10` to lane B, whose registration function dereferences it. `tls-handoff.tsv` binds the instruction operands and copy offsets.

If the launcher executes in that worker's selected thread-local context, the two source loads observe the same stack word, and no intervening code changes the slot or the copied worker pointer, the two shared bases are equal. This is a conditional dataflow relation; the producer's actual invocation in that context and the behavior of intervening helpers are not established. Consequently, **if** the producer and worker use the same shared base, the queue starts empty, the append succeeds, no intervening operation changes that queue, and the worker selects this shared-queue arm, the returned node is the inserted task pointer. On the selected continuation, if the intervening guards and helpers permit it, the worker tests the returned pointer and invokes its table's first word. Whether the required thread context persists, whether the worker selects this arm, and concurrent interleavings are not established by these offsets. The distinct worker relocation is new; neither the earlier loader GOT nor its call site is re-owned.

### Poll and replacement decisions

Both poll wrappers pass object `+0x20` to `0x2013c00`. That bridge requires its input variant at `+0x10` to be zero and passes input `+0x18` to the previously studied state future `0x22ae8a0`. Therefore the constructed object's variant and future pointer correspond to object offsets `+0x30` and `+0x38`. The existing [ABCI state inventory](../abci-state-inventory-94/README.md) binds `0x22ae8a0` to the state-file Location and the earlier [loader packet](../RE-019-rmp-json-loader-94/EVIDENCE.md) identifies its loader call. We add the upstream handoff, not the old loader body or call site.

For a current unsigned 64-bit task word `x`, the following tables describe only a successful compare-exchange attempt. A failed compare-exchange retries with the newly observed word. Bitwise complements are masked to 64 bits.

| Before the callback | Outcome before the first table dispatch |
| --- | --- |
| `x & 4 == 0` | Diagnostic path containing `next.is_notified()` |
| `x & 4 != 0` and `x & 3 == 0` | Store `(x & ~7) + 1`; table index `(x >> 5) & 1` |
| Remaining case with `x <= 63` | Diagnostic path containing `self.ref_count() > 0` |
| Remaining case | Store `x - 64`; index 3 if the new word is below 64, otherwise 2 |

Index 0 reaches the callback; index 1 reaches a replacement path, index 2 returns, and index 3 reaches a lane-specific helper. The exact lane-specific targets are the `poll_a_before` and `poll_b_before` rows in `jump-tables.tsv`.

After a nonzero callback byte, a second dispatch has a different table and these ordered tests:

| After the callback | Outcome before the second table dispatch |
| --- | --- |
| `x & 1 == 0` | Diagnostic path containing `curr.is_running()` |
| `x & 0x20 != 0` | Index 3 without this compare-exchange |
| `x & 4 != 0`, sign bit set | Range diagnostic path |
| `x & 4 != 0`, sign bit clear | Store `(x & ~0x21) + 64`; index 1 |
| Remaining case with `x <= 63` | Reference-count diagnostic path |
| Remaining case | Store `(x & ~0x21) - 64`; index 2 if the new word is below 64, otherwise 0 |

Here indexes 0, 1, 2 and 3 respectively reach return, a lane-specific helper path, a release-helper path and a variant-replacement path. The names are observations about call placement, not recovered scheduler APIs. Five assertion texts are bound separately in each lane; `diagnostics.tsv` includes their exact byte lengths and records the shared wording.

When the bridged future returns AL zero, the bridge invokes `0x1fa3d10` on the variant, then writes variant 2. The variant-zero cleanup calls another helper on the future pointer and passes `0x6368` to the deallocation slot. Each wrapper then prepares a 32-byte variant-1 record whose first two payload words are zero and calls `0x201c250`. That helper first processes the old variant and copies two 16-byte blocks into object `+0x30`. The final payload word comes from a register and is not established as zero. The nonzero callback case does not take this zero-result replacement directly.

### Conditional result delivery and failure

The two table `+0x18` words lead to `0x1d589c0`. If its helper returns AL zero, the reader returns without the selected result copy. If that helper returns nonzero, the reader copies the 32-byte task record, writes task variant 2, and tests the saved variant. Variant 1 leads to a 24-byte payload copy from task `+0x38` into output `+0x08`, with output word zero; another variant reaches a diagnostic prefix `JoinHandle polled after completion`. The reported prefix is a bounded byte witness: the nearby length argument is larger, so it is not reported as the complete diagnostic string. The reader may first dispose of an existing output payload under its own null/variant checks.

Each of the three upstream state machines separately calls the already indexed consumer boundary `0x2046b70` with the handle and checks the resulting buffer. On their selected failure paths, a nonzero first payload word reaches a length-matched diagnostic naming `Result::unwrap()`; the exact text and bytes are retained in `diagnostics.tsv`. The existing consumer's interior and its dynamic table dispatch are deliberately not reclaimed. Thus the table-to-reader relation and the caller-side buffer tests are proven separately, while the particular dynamic connection between them remains conditional.

## Implementation and comparison

Not yet implemented. No independent Rust implementation, build, lockfile, target execution, behavioral differential or binary comparison is claimed. No operands were normalized; `windows.json` contains original bytes. The test model treats the words and payloads as synthetic values and does not execute or emulate the captured node. ## Results and limitations

The generated evidence contains 26 FDE extents, 84 fixed byte windows, 30 selected direct transfers, 87 selected conditional branches, 28 entries from seven relative tables, six relocations, three RIP-reference bindings, four queue-field correspondences, 11 TLS-flow witnesses, one Location, 18 diagnostic witnesses and 14 raw transfer candidates. The 18 focused tests include 174 single-byte branch opcode/displacement corruptions, table and literal corruption, bad digest, invalid FDE/header, SHT_NOBITS and range controls, and independent comparisons for all 256 low-byte inputs to each atomic decision model. There are no skipped tests.

These are scoped observations, not a denominator for all ABCI functions or matched machine code. The runtime's actual queue-to-dispatch dataflow, all behavior of the existing consumer, state-file read outcomes, action/end-block processing, state-root inputs and semantics of nonzero callback results remain unresolved. The generated milestone remains 0/4; no progress gate is requested. Next question: establish that the producer executes in the selected worker context without an intervening slot change. Then close queue synchronization and the result consumer before assigning source-level types or end-to-end runtime reachability.
