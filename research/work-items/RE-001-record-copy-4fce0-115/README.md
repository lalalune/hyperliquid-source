## Bounded question

What does the routine at 0x5d4fce0 do when it copies one small record:
which fields move verbatim, how is the heap string field replaced, and
what happens to a string the destination already held?

## Semantics

Arguments: rdi = destination record pointer, rsi = source record
pointer; returns void. Record layout (offsets from the record pointer):

- +0x00: u32 field, copied verbatim.
- +0x04: u16 field, copied verbatim.
- +0x06..+0x07: two bytes, never read and never written.
- +0x08: heap C-string pointer, replaced as below.

In order:

1. Destination +0x00 = source +0x00 (4 bytes); destination +0x04 =
   source +0x04 (2 bytes).
2. Destination +0x08 = 0. This runs before any clone, so a string the
   destination already held is dropped here with no delete.
3. If source +0x08 is non-null, the clone callee 0x61cf610 runs with
   (out slot = a stack slot, source string): length = strlen(source);
   a fresh buffer of length + 1 bytes is allocated with operator
   new[]; length + 1 bytes are copied with __strncpy_chk; the new
   pointer is stored to the out slot and the out-slot pointer is
   returned. The returned pointer is stored to destination +0x08.
   If source +0x08 is null, the clone does not run, no allocation
   happens, and destination +0x08 stays zero.
4. The post-clone delete[] check reads the stack slot after it was
   zeroed (the code zeroes the slot before storing the clone into
   the destination), so it is dead on the normal path: it never
   frees anything.
5. Stack-canary check, then return.

Landing pad: entry at 0x5d4fd86 (endbr64, exception object saved),
cleanup at 0x5d4fd63..0x5d4fd71 deletes destination +0x08 when
non-null, then _Unwind_Resume. This cleanup is vacuous on every
reachable path: destination +0x08 is zeroed before the only throwing
call (the clone) and is only assigned after that call returns
normally, so the delete never fires. Recorded as observed vacuity,
not as a second behavior.

## Model and tests

`tools/record_copy_4fce0_115.py` models the copy over fake records
with an allocation tracker; `tests/test_record_copy_4fce0_115.py`
covers the full copy, the null-string path, the empty-string clone,
the dropped-not-freed old string (both with a new source string and
with a null source string), the clone helper directly, and null
guards. Null destination/source raise in the model only as a stated
model guard: the binary dereferences both pointers with no check.

## Unknowns

- What the record denotes and what the u32/u16 fields mean; only
  their widths and copy order are pinned.
- Whether callers always pass a fresh destination; the routine as
  written drops a prior destination string without freeing it, so a
  live destination would leak that string.
- The clone callee's other callers (it is a shared string-clone
  helper with many call sites); only its behavior as used here is
  pinned.
