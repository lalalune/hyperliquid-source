# RE-001: map node #115 0x58-byte tree teardown 0x5d4d250

## Bounded question

Open PR #2453 mapped the assign for the 0x48-byte single-string
tree nodes (assign 0x5d4e140, rebuilder 0x5d4de20, leftover
teardown 0x5d4cba0). That teardown has 25 direct call sites, and
9 of them sit inside one unmapped routine. What does the routine
at `0x5d4d250` (FDE `0x5d4d250..0x5d4d48c`, 572 bytes) do end to
end? It is the teardown of a second, larger tree node type whose
nodes each carry a nested 0x48-byte tree.

## Answer, stated literally

The routine takes a node pointer in `rdi` and returns void. A
null head returns immediately and deletes nothing. Otherwise it
destroys the whole sibling chain starting at that node, in chain
order, and deletes every node it reaches.

### Node fields

Node (0x58 bytes, delete size 0x58): the next sibling is the
qword at `+0x10`, the first child is the qword at `+0x18`, and
the nested-tree root pointer is the qword at `+0x38`. The bytes
at `+0x00`, `+0x08` and `+0x40`..`+0x57` are never read or
written by this routine. The nested-tree root is a 0x48-byte
tree node pointer (or null); it is handed whole to the
0x5d4cba0 teardown, whose semantics are referenced from open
PR #2453 and not re-claimed here.

### Per-node order

For each node, in `+0x10` chain order:

1. Destroy the node's whole `+0x18` child chain (same routine,
   see below).
2. Tear down the node's `+0x38` nested tree via the 0x5d4cba0
   teardown (null nested root tears down nothing).
3. Delete the node itself with size 0x58 (delete PLT).

Then advance to the node's `+0x10` successor and repeat. The
net observable order is post-order: children before their
parent, siblings in chain order, each node deleted exactly
once on a well-formed tree.

### How the child chain is destroyed

The binary unrolls the first six child-chain levels inline and
recurses for deeper levels; the observable order is identical
either way. Reading the descent from the entry: the head node
is held in a stack slot; its `+0x18` child is loaded, then
that child's `+0x18`, and so on through six registers (the
second through sixth levels). When a level's `+0x18` is null,
that level's node is processed at once (nested teardown, then
delete 0x58); when a seventh level exists, the routine calls
itself (site `0x5d4d2e8`) on that seventh level's `+0x18`
child chain, then processes the seventh-level node, then
unwinds level by level: each level's node is processed, and
if it has a `+0x10` successor, the descent restarts at that
successor's child chain before the parent level is processed.
The nine nested-teardown call sites inside this routine are
`0x5d4d2fd`, `0x5d4d31e`, `0x5d4d346`, `0x5d4d372`,
`0x5d4d399`, `0x5d4d3cd`, `0x5d4d402`, `0x5d4d42f` and
`0x5d4d45c` — one per unrolled level plus the recursion
unwind path. The only other calls in the routine are the
self-recursion and the delete PLT.

### Census

Whole-file scan, reproduced by the packet's `census.py` and
re-run inside `verify.py`: the routine has exactly 4 direct
calls — its own self-recursion at `0x5d4d2e8` and three
external sites (`0x5d84b37` in `0x5d8479c..0x5d85475`,
`0x5d87e97` and `0x5d885df` in `0x5d878f0..0x5d887b0`,
recorded site-only in `callers.tsv`) — 0 tail jumps, 0 stored
qwords, 0 RELATIVE addends.

### NOT claimed

What the trees, nodes or nested trees denote; the semantics of
the three external caller functions beyond their site
addresses and FDE ranges; the meaning of the never-read node
fields; behavior on cyclic or dangling structures (the binary
shows no cycle guard; the model raises instead of looping,
and cyclic behavior is not claimed). The 0x5d4cba0 teardown
semantics are referenced from open PR #2453, not re-claimed.
