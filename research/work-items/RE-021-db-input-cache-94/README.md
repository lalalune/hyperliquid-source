# RE-021: private EVM database inputs for the precompile path

The private EVM database distinguishes cached account absence, missing code and missing storage with three different cache transitions: a returned account tag zero can create a negative account entry, a returned code tag four creates an empty-code value, and a slot miss may either cache zero or return zero without inserting the slot, allowing an independent reconstruction to preserve these distinctions at the input boundary of the previously mapped address-09 precompile route.

- Component ID: `evm`, RE-021 continuation; RE-021 is not a new row in the official task table.
- Target release and full SHA-256: Linux x86-64 node #94, `3b7179cd967d1b13b683e05debfc685ad4c750e918226402d5d575eff1c0459f`.
- Source commit / reference commit: repository `56c0ec672bd8fdcfaa80f2db700a61e6240b3663`; inferred reference tree `999556f6e0a474b8312db96ec3149e1c44e97c23`. The unlicensed reference is a lead, not implementation source.
- Claim status: **observations** are the selected FDE records, raw bytes, displacement-derived branches and calls, RELA records and field operations. Names for database, account, storage, cache and enum variants, plus compositions across other packets, are **inferences**. Runtime seeds, backing-store effects, dynamic callbacks and behavioral equivalence are **unresolved**.
- Scope included and excluded: three database adapter FDEs and their selected cache, construction, reserve and cleanup helpers. PR #1413 records calls from the private execution path to the account and code adapters as external boundaries; PR #1563 records the access-list call to the slot adapter. Their callers, the registry/lookup/dispatch and the BLAKE2b wrapper/compression bodies are dependencies, not selected again. The pre-existing `RE-009-evm-kv-schema-94` packet owns the three backing getters and their key schemas. #115, visor, captured execution, networking and chain actions are excluded.

## Evidence

All addresses are linked ELF virtual addresses before load bias. `functions.tsv` also records file offsets, exclusive FDE ends, CIE/FDE/LSDA coordinates and whole-extent hashes. The selected corpus comprises **24 FDE intervals, 14,637 bytes, 3,447 linear byte shapes, 454 control records, 20 reviewed call edges, 39 selected predicate branches, nine compared hash paths, 60 semantic windows, 20 table entries, 36 relocations and 45 exception call-site intervals**. These are selected-corpus counts, not node coverage. An FDE is an unwind range and a linear walk does not establish reachability or prove every instruction's semantics. Four very short selected helpers are retained to bind method-table entries; they are not counted as independent recovered features.

`call-edges.tsv` resolves selected direct calls and RELATIVE-indirect calls from bytes. `predicate-branches.tsv` retains each selected compare/test, conditional encoding, taken destination and fallthrough. `instructions.json`, `control-flow.tsv`, `rip-references.tsv`, `unwind-records.json`, `exception-call-sites.tsv` and `lsda-records.json` retain the wider raw ledger. `branch-tables.tsv` records bounded four-entry table windows; it does not prove that arbitrary input tags are valid. `dynamic-symbols.tsv` resolves three symbol-bearing relocations to `memcpy`, `memmove` and `memset`; their symbol records are undefined in this ELF, so they do not determine the runtime implementation or address.

The first vacant-account route can call the account getter twice (`0x1e6b366`, then `0x1e6b45d`) before a slot read. This is observed call order, not a claim that two real backing reads can return different results. The account result converter tests **zero versus nonzero**, whereas the slot-miss path tests **bit zero**. Thus a hypothetical state byte two would be treated as nonzero by the converter but would take the no-backing-read slot branch; the packet does not establish that byte two occurs in a valid live state.

### Keys, entry publication and code variants

The three entry helpers read their process words through a relocated pointer and use a table seed. For the 20-byte account key the four little-endian 64-bit loads start at offsets 0, 4, 8 and 12; the code and slot keys use offsets 0, 8, 16 and 24. The inlined final XOR immediates are respectively 20, 32 and 4. The slot immediate is an observed hash-domain constant, not a claim that the slot key is four bytes. The selected byte windows pin the full multiply-high/XOR sequences. `hash-paths.tsv` additionally derives the key-load displacements and XOR immediate for lookup, in-place rehash and growth rehash: after accounting for bucket stride, all three paths for each key family read the same key offsets and domain immediate. Synthetic tests use supplied seeds; the actual process words are mutable and are not recovered from file bytes.

For all three helpers, a seven-bit fingerprint filters a group of 16 control bytes, followed by comparison of the complete key. An `0xff` control ends a failed probe; further groups advance by 16, 32, 48 and so on with the bucket mask. Matching control bytes alone do not establish key equality. `0x27c9ad0` additionally distinguishes replacing an existing 32-byte slot value from inserting a new key/value pair. Its replacement arm returns raw tag one and the old value; its insertion arm returns tag zero, writes the fingerprint to both control positions, decrements the growth word by the old control's low bit, and increments the occupied count. This is cache state, not a durable database write.

The raw file bytes of the empty-map header at `0x574ce10` are zero, but its first word has an `R_X86_64_RELATIVE` relocation to `0x202e90`, whose 16 file-backed bytes are all `ff`. `constants.json` and `relocations.tsv` retain both layers; interpreting the unrelocated zero word as the runtime control pointer would be incorrect. The default account and code builders initialize separate method-table pointers and a logical code length of zero. The fixed hash bytes used by the account default match the conventional empty-code hash, but that algorithm name and the source-level object types are inferred.

Both code hit and post-insertion paths dispatch raw tags zero through three to the same four clone arms. Tags zero, one and three call an indirect clone method; tag one additionally increments a shared word, and tag two increments a shared word without that clone call. Tags one and two take `ud2` if the signed post-increment result is nonpositive. Tag four is checked by the account conversion path as a separate no-code form. These bounded windows do not establish behavior for out-of-range tags or the complete trait ABI.

### Reserve, allocation and exceptional exits

The three entry helpers pass one as both the additional request and the reserve failure-mode argument. Each reserve body checks carry in occupied count plus requested count, compares the requested total with half the current maximum load to choose an in-place or growth branch, and checks allocation arithmetic. On the growth arm let `request` be the greater of the old maximum load plus one and the occupied-plus-additional total. The selected small cases yield bucket counts 4, 8 or 16; for the larger inspected domain the multiply-high sequence corresponds to `next_power_of_two(floor(8 * request / 7))`. `reserve-invariants.json` derives the operands, reciprocal constant, checked maximum request and layout bound directly from selected instructions. The layout is `bucket_count * stride + bucket_count + 16`, with strides 208, 96 and 64 for account, code and slot respectively. The arithmetic and smallest-capacity interpretation assume valid table invariants; the synthetic oracle does not run target instructions.

On the in-place rehash arm, each helper applies the same signed-byte comparison and `0x80` mask from `0x207980`: any control byte below `0x80` becomes `0x80`, while any byte with its high bit set becomes `0xff`, before the subsequent rehash loop. On the new-allocation arm, the selected windows store the new control pointer, bucket mask and growth word before calling the old-storage release boundary. That ordering is conditional on reaching those instructions and does not establish successful completion or whole-operation atomicity.

The selected reserve branches expose separate count-overflow, size-overflow and null-allocation destinations. Their failure-mode tests lead to distinct out-of-line diagnostic/allocation helpers; their full side effects and unwinding semantics remain external. The code and account default constructors have separate null checks for their one-byte and shared-object allocations. The account and slot paths also retain exception intervals and landing pads: for example the slot adapter's backing-read interval has a landing that calls the optional-code cleanup before the unwind-resume boundary, while the slot-insertion interval has a different cached-account cleanup. Action chains and catch types are not decoded. No whole-operation atomicity is claimed; an entry probe can resize a cache before a later backend or allocation boundary fails.
