- Component ID: RE-001 (node #115 function map)
- Target release and full SHA-256: node #115,
  `a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`

- Source commit / reference commit: upstream main `05bc2de3`
- Claim status: observation for everything below except the items listed

## Bounded question

When a 32-byte tagged value — the value the sibling packet at
0x57ae540 widens narrower values into — is destroyed, exactly what
does its destructor release, in what order, through which callee,
for each tag? The routine answers it in 445 bytes with a 21-entry
jump table: 16 tags own nothing at all, two tags own a byte buffer,
two tags own a boxed child destroyed by recursion, one tag owns a
vector of 32-byte elements, and every remaining tag owns a vector
of 64-byte pairs. The subtle part is the asymmetry the table hides:
elements and pair halves are dropped by a *different* instantiation
of the same decision table (0x5b20680) than the one that drops box
children (this routine itself). A reconstruction that guesses the
wrong element destructor, the wrong element size (1/32/64), or the
wrong capacity multiplier leaks or double-frees; this packet pins
the whole ownership table from the bytes.

## Object layout (pinned by the disassembly)

The value is 32 bytes; the routine reads only what each arm needs.

- +0x00: tag byte. Compared against 0x14: tags 0..0x14 dispatch
  through the table at 0x9317a4; any larger byte takes the default
  arm. The no-payload arms read nothing else.
- +0x08: word A — the capacity (in elements) of a buffer triple, or
  the child pointer of the box arms.
- +0x10: word B — the buffer pointer of a buffer triple.
- +0x18: word C — the length (in elements) of a buffer triple: byte
  count base for tag 20's elements, pair count for the default arm.
  Unread by the no-payload, byte-buffer and box arms.

## Behaviour by tag

- No payload (tags 0..11, 13, 15, 16, 18): the arm at 0x57aa837
  returns immediately. No field beyond the tag is read, nothing is
  called, nothing is freed.
- Byte buffer (tags 12, 14): if A == 0, nothing happens; otherwise
  one sized deallocation dealloc(B, A) — the size is A unshifted, so
  A counts 1-byte elements and C is never read.
- Box (tags 17, 19): drop the child at A with this same routine,
  then dealloc(A, 0x20) unconditionally. Tag 17's body (0x57aa8c5)
  and tag 19's body (0x57aa8d3) are the same three instructions;
  tag 17 joins tag 19's tail.
- Value vector (tag 20): twin-drop each of the C elements at
  B + 0x20*i in increasing address order, then if A != 0,
  dealloc(B, A << 5).
- Pair vector (default arm, any tag byte >= 0x15): for each of the
  C pairs at B + 0x40*i in increasing address order, twin-drop the
  first half (B + 0x40*i) then the second half (B + 0x40*i + 0x20);
  then if A != 0, dealloc(B, A << 6).

Every deallocation goes through GOT slot 0x64df4a0 to the
sized-deallocation entry 0x635de30 with the third argument always 0;
on the non-throwing paths these are tail jumps through the shared
epilogue at 0x57aa90d. The routine stores nothing anywhere.

## The twin, and the recursion asymmetry

The elements and pair halves are *not* dropped by this routine: all
five element-drop call sites (0x57aa87d, 0x57aa8af, 0x57aa8be in the
main arms, 0x57aa940 and 0x57aa99d in the landing pads) call
0x5b20680, a second instantiation of the same 21-tag decision
function. The twin has the same FDE size (445 bytes), a jump table
(at 0x93d9ac) whose case grouping is tag-for-tag identical, and an
LSDA whose call-site ranges and landing-pad offsets match this
routine's offset-for-offset. It differs where it must: it is fully
self-recursive (7 self-calls — its elements drop with itself), while
this routine's elements drop with the twin and only its box children
recurse into itself. Two further instantiations of the same shape
exist at 0x21d8eb0 and 0x3b62630 (445-byte FDEs); verify.py checks
that their jump tables carry the same case grouping. Which of the
four a given value meets is decided by its producer, not by the
value; this packet pins this instantiation, the one 2,555 call
sites name, and does not claim the twin's own element semantics —
its body is a separate bounded question.

## Unwind behaviour (pinned by the LSDA)

- A raise out of the tag-20 element call lands at pad 0x57aa98c:
  it drops the elements *after* the interrupted one with the twin
  (the pad's first decrement consumes the interrupted element),
  deallocates the buffer (A << 5) as a call, and resumes with
  _Unwind_Resume.
- A raise out of the pair loop's first-half call lands at pad
  0x57aa938: it twin-drops the interrupted pair's second half,
  continues over the later pairs with the pair glue 0x5b0ad70
  (FDE 0x5b0ad70..0x5b0adac: twin-drop both halves of one pair),
  deallocates the buffer (A << 6) as a call, and resumes. A raise
  out of the second-half call lands at pad 0x57aa94d — the same
  continuation entered after the current pair.
- A raise out of either box self-call lands at pad 0x57aa928
  (tag 19 reaches it through the 0x57aa926 alias): it deallocates
  the 32-byte box as a call and resumes.
- A raise inside any cleanup call in the pads themselves routes
  (pads 0x57aa947, 0x57aa986, 0x57aa9c7, action 1) to the
  panic-in-a-destructor shim at 0x1680cab through slot 0x64df4c0.
- The finish/resume region (0x57aa9a2..0x57aa9cd) has no landing
  pad; the deallocation calls and _Unwind_Resume there run
  unguarded.

## Consumers

The widen caller FDE 0x57ae710..0x57ae7aa calls the widening
conversion 0x57ae540 and then drops the widened value with this
routine on both the normal and the unwind path — construction is
pinned by the widen packet, destruction only here. Three of the
four tail-jump callers (0x57a716a, 0x57ad427, 0x57aec4a) sit in the
same function neighbourhood as that caller; the full site list is
in callers.tsv.

## Relations

- `RE-001-tagged-value-widen-ae540-115` (PR #3328) pins the widening
  conversion that *builds* this value (its argument tags 0..21) and
  names the input variants. It does not pin destruction; this packet
  is the drop counterpart and states the tag arms independently —
  read from the drop's own table, not inferred from the widen's.
- The msgpack string-writer packet (writer body 0x57cf5d0, prepared
  against this same base) drops this value as its failure cleanup
  and cites this routine as the value destructor; the layouts the
  two packets pin agree (tag at +0x00, words at +0x08/+0x10/+0x18,
  size 0x20).
- Open-PR and merged-work sweep at this base found no packet or
  owners.json pin naming 0x57aa810, 0x5b20680 or 0x5b0ad70; the
  RE-001 destructor packets by other authors cover bodies in the
  0x5d5xxxx range, different routines entirely.

## Unknowns

- The semantic (source-level) identity of the tagged value, and of
  the type the twin destructs, is not pinned. Only bytes, layout,
  sizes, ownership and call structure are claimed.
- Tag bytes above 0x15 cannot arise from the sibling widening
  conversion (its table ends at tag 21); whether any other producer
  forms them is not investigated. The default arm's behaviour for
  them is pinned mechanically regardless.
- The twin destructor 0x5b20680's full semantics are checked only
  for table grouping and LSDA geometry, not modelled or
  differentially tested here.
- The sized-deallocation entry 0x635de30's internal behaviour is
  cited from the relocation addend only — the same boundary sibling
  packets use for that entry.
- The landing pads are pinned structurally (LSDA rows plus the pad
  code); they are not executed by the differential, which covers
  the non-throwing paths.
