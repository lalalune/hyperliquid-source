# RE-001: create a Statistics object by name (node #115)

## Bounded question

How does node #115 build a `Statistics` object when a caller asks
for one by name, and what does the registered `BasicStatistics`
factory pin down about that object?

## Answer in one paragraph

The host routine at `0x6077820` runs a `std::call_once` once-init
(`0x6075bc0`, the `rocksdb::RegisterBuiltinStatistics` lambda) on
first use, then dispatches on the name: an empty name or
`"BasicStatistics"` is constructed directly through the
`StatisticsImpl` ctor `0x6071a00` with a fresh `shared_ptr`
control block (use 1 / weak 1); any other name goes through the
registry lookup `0x609e510`. The once-init locks the default
`ObjectLibrary` (singleton accessor `0x61f8b60`), builds a
`PatternEntry` named `"BasicStatistics"` and a `FactoryEntry`
holding the creator `0x6071ba0` and the `std::function` manager
`0x606fa50`, and appends it to the `"Statistics"` vector in the
registry map. The ctor builds the 0x70-byte `StatisticsImpl`
(vptr `0x64d2d88`, byte 3 at +0x20, options-record vector at +0x8,
`std::string` at +0x28, mutex at +0x38, ticker shard store at
+0x60), appends the `"StatisticsOptions"` record, and the creator
installs a fresh object into the caller's `Statistics*` slot,
deleting any old occupant. The registered `PatternEntry` matches
exactly `"BasicStatistics"` — both of its pattern vectors are
empty, its flag at +0x48 is 1 and its offset at +0x50 is 0.

## Key facts pinned

- Host `0x6077820` (FDE `0x6077820..0x60780a0`): once-flag
  `0x6506238`; TLS slots `__once_callable` `0x64ed818` /
  `__once_call` `0x64ed820`; `__once_proxy` GOT `0x64ed828`;
  the register routine is `lea`'d at `0x607788d`.
- Register `0x6075bc0`: mutex at registry offset 0; the
  `PatternEntry` is 0x70 bytes with the name in SSO and the
  second length copy 15 at +0x28; the `FactoryEntry` is 0x30
  bytes with the manager at +0x20 and the creator at +0x28.
- Ctor `0x6071a00`: shard bits are 3 when
  `hardware_concurrency <= 8` (the `0x607187c` default), else the
  smallest bits >= 4 with `2**bits >= hw`; shard block size is
  `count * 0xce40 + 0x40`; the `"StatisticsOptions"` record is
  `{name, obj+0x28, 0x6506200}`.
- Matcher: helper `0x61f8430` + sub-matcher `0x61f8280` (modes 2
  literal, 3 integer, 4 float, other = find). With empty
  sub-pattern vectors the entry matches its name exactly.
- Typeinfo chain: `StatisticsImpl` (`0x64d2cf8`) ->
  `Statistics` (`0x64d2ce0`) -> `Customizable` (`0x64d34a0`) ->
  `Configurable` (`0x64d3410`); `FactoryEntry` and
  `PatternEntry` derive from `ObjectLibrary::Entry`
  (`0x64cd990`). The registration lambda's typeinfo name
  (at `0x975560`) is stored with a leading `*`; that character
  is part of the stored name, verbatim.

## Open unknowns

- The host's exact C++ name (described by behaviour).
- The registry lookup `0x609e510` / `0x609a410` and the
  translator `0x6076b20` bodies.
- The identity of BSS address `0x6506200`, the options
  record's third field (stored opaquely in the model).
- The creator's exact C++ parameter mapping (observable:
  `rdx` = address of a `Statistics*` slot).
- The `ObjectLibrary` base-subobject interpretation of the
  singleton holder's `obj+0x10` pointer (observed fact;
  inference flagged).
- The 28 unpinned `StatisticsImpl` vtable slots
  (`0x10..0xe0`, `0xf8`) — #3362/#3378 ground, not re-derived
  here.
