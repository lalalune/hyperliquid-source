# RE-001: node #115 hash merge-accumulators body

## Status

Bounded question: pinned. Semantic identity: the RE-002 vendor
census registers these 152 bytes as librocksdb-sys 0.11.0+8.1.1
`XXPH3_mergeAccs` (start 102508528, end 102508680); that identity
is cited, not re-asserted -- this packet pins what the
instructions at the address compute, nothing more.

## Bounded question

The hash-long packets leave one body by contract. The with-seed
packet (RE-001-hash-long-seed-61c2cb0-115, PR #3510) pins that
the body 0x61c2cb0 finishes by calling a merge callee at
0x61c31fc with the accumulator array, the custom secret + 11
bytes and length * PRIME64_1, and returning its rax -- without
pinning what the callee computes. The family parent packet
(RE-001-hash-callee-61c3530-115, PR #3486) reaches the same
callee only through that contract. What does the merge body at
0x61c27f0 itself compute from its three arguments, over what
read extents, with what side effects, and who else calls it?

## Answer pinned

Routine 0x61c27f0 (FDE 0x61c27f0..0x61c2888, 152 bytes) is the
merge body. Signature: merge(acc=rdi, secret=rsi, start=rdx)
-> rax. The whole body is straight-line: no branches, no calls
of any kind, and one balanced push %r12 / pop %r12 pair (r12 is
never written; the pair has no observable effect beyond a
transient 8-byte stack slot). It reads exactly the 64 bytes at
rdi (eight accumulator qwords) and exactly the 64 bytes at rsi
(the secret window at the handed pointer), writes neither
window and no other memory, and computes, with all arithmetic
mod 2^64:

1. Four lane-pair folds. For pair i = 0..3, with
   a = acc[2i] XOR secret64[16i] and b = acc[2i+1] XOR
   secret64[16i + 8], the pair contributes
   fold(a, b) = lo64(a * b) XOR hi64(a * b), from one 128-bit
   mul per pair.
2. The sum start + fold0 + fold1 + fold2 + fold3. (In
   instruction order the start value is added third -- at
   0x61c2843, after the second fold term and before the third
   -- but addition mod 2^64 commutes, so the total is as
   stated.)
3. The closing avalanche of the sum: x ^= x >> 37;
   x *= 0x165667b19e3779f9 (movabs at 0x61c286f);
   x ^= x >> 32. The avalanche product is the return value.

Caller census (whole executable segment, candidates confirmed
by decoding): exactly two direct calls, no tail jumps, no
stored qword and no RELATIVE relocation addend naming this
body:

| caller body (FDE) | site | arguments at the site |
| --- | --- | --- |
| seedless hash-long body 0x61c2890..0x61c2cad | call 0x61c2c8e | rdi = accumulator array (frame base); rsi = 0x97df0b (default secret + 11); rdx = length * PRIME64_1 |
| with-seed hash-long body 0x61c2cb0..0x61c3221 | call 0x61c31fc | rdi = accumulator array (frame +0x00); rsi = custom secret + 11 (frame +0x4b); rdx = length * PRIME64_1 |

Both callers return this body's rax as their own result, and
both are themselves reached only from the parent hash dispatch
0x61c3530 (108 direct call sites, pinned by
RE-001-hash-callee-61c3530-115, PR #3486), so the runtime
reachability of this body runs through them. The +11 secret
offset is the callers' choice; this body simply reads the 64
bytes at the pointer it is handed.

NOT claimed here:

- the seedless hash-long body 0x61c2890's own instructions
  (its default-secret accumulation loops and lane schedule);
  this packet pins only its merge call site and the argument
  setup at that site
- the exact source spelling beyond the RE-002 vendor census
  identity cited above; the body itself carries no symbol
- the callers' length/seed semantics beyond the argument
  setups recorded at the two call sites
- behaviour on invalid pointers: the body dereferences both
  windows unconditionally, and no caller hands it anything
  but full windows

## Verification scope and next step

`verify.py` (worktree and cleanroom-verifier runs) checks the
digest, the verbatim excerpt, key-instruction spot bytes, the
FDE ranges, the relocation facts, the pinned census and
callers, the machine-readable record, the model tests and the
manifest.

`differential.py` maps the binary page containing the body
(no stubbing is needed: the body calls nothing) and runs it
against the Python model over the golden vectors, both
callers' exact +11 secret-pointer geometry, a structured grid
over accumulator / secret / start patterns, a seeded random
sweep, and read-extent guard cases that end each window
exactly at the end of the mapped data region. Return values
match the model exactly in every case, and every case also
confirms that neither window (nor any other data byte) is
written, that the stack is untouched apart from the push %r12
slot holding the preserved r12 fill, that rsp is restored and
that all callee-saved registers survive. Emulation is
observational; the disassembly in `main.txt` is the normative
evidence.

What remains open in this family: the seedless hash-long body
0x61c2890, the last contract-only body of the dispatch family
-- its dispatch from the parent and its merge call are pinned,
its own instructions are not. That is the natural next bounded
question; it does not hold this answer open.
