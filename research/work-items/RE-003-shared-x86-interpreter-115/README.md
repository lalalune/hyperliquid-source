# RE-003: shared offline x86-64 interpreter for node #115 evidence tools, proven equal to five merged tools

This packet lets every later #115 evidence packet write `from x86_115 import Image, load_image, decode, Machine` instead of carrying its own copy of the same ~1,150 line decoder and interpreter: `tools/x86_115.py` is that one module, and it decodes 2,151,565 instructions of 15,508 sampled FDE functions exactly to their FDE ends, gives the same decoded fields as the decoders of five merged tools on all 2,534 instructions those tools execute (0 differences), runs 11,642 cases of those tools with identical return values, registers, instruction counts and memory-write digests (0 differences), passes 141 hand-derived semantic probes, and is attacked by 59 deliberately broken copies of which 58 are caught and the 59th is shown to be behaviourally equal.

- Component ID: RE-003 (test harness design: isolated offline differential protocol with positive and negative controls)
- Target release and full SHA-256: node #115, `a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`
- Source commit / reference commit: repository base `0781ce04826eeefd89fe336cb8ea073be0c1de30`; the code moved into the shared module comes from the merged tools `tools/staking_admission_gate115.py` (lines 1-1103), `tools/funding_rate115.py` and `tools/funding_premium115.py` (their extra instructions and floating point rules), `tools/twap_slice_115.py` (`andnpd`, `cmpeqsd`). No code from `references/can1357-hl`.
- Claim status: observation (equality of the shared interpreter with five merged interpreters on the stated inputs, decode coverage counts, control results). Instruction semantics beyond those inputs are inference and are not claimed.
- Scope included: `tools/x86_115.py` (ELF image view through `elf_index` and `fde_extents`, instruction decoder, memory model, interpreter with a stub hook table), the comparison tool `tools/re003_x86_115_check.py`, its tests (53). Compared tools for decode and execution: `staking_admission_gate115`, `staking_listed_set115`, `staking_validator_snapshot115`, `funding_rate115`, `funding_premium115`; decoder-only comparison: 11 tools of `tools/` that carry a `decode(read, va)` and a Machine copy. Excluded: every packet-specific fixture, hook and rule list of those tools (they stay in the tools), vector instructions beyond the ones the compared tools use, segment-prefixed (fs) accesses, x87, the tools whose interpreter has another shape (not rebound), and any execution of the node binary.
- Substitution: the assignment named a `vault_base_conversion115` tool; no such file exists in the repository base, so `funding_premium115` (also a floating point body with its own interpreter copy) is the fifth compared tool.

## Reproduce

From the repository root (the binary is the linked read-only `artifacts/node/115/hl-node`; nothing is executed, there is no network access):

```sh
python3 tools/re003_x86_115_check.py --out research/work-items/RE-003-shared-x86-interpreter-115
python3 -m unittest tests.test_re003_x86_115_check
```

The tool checks the SHA-256 first. One run takes about 150 s and 470 MB resident memory; the tests take about 6 s. Two runs with different hash seeds and time zones into different folders compared equal with `diff -r`. The tool imports the compared tools from `tools/` (they must exist at run time) and calls no external program. `MANIFEST.sha256` lists every file of this folder except itself; `measure.json` carries the counts used below.

## Evidence

All addresses are virtual addresses of the #115 image; code bytes are read through the section table (NOBITS sections refused). Function extents are the FDE ranges of `.eh_frame`.

1. **Decode survey** (`decode-survey-summary.tsv`, `decode-survey-ops.tsv`, `decode-survey-stops.tsv`, `decode-survey-functions.tsv`). Every 8th FDE function of the image (16,915 of 135,313) is decoded linearly with the shared decoder: 2,151,565 instructions, 15,508 functions decoded exactly to their FDE end, 0 overran an FDE end, 1,407 stop at an instruction form the decoder does not model. The stop table names the forms: segment-prefixed forms (`64 48 8b`, `64 48 2b`, ... thread-local accesses) are the largest group, then `0f 5a` (float conversions) and `0f c1` (xadd). `decode-survey-ops.tsv` lists the operations the decoder produced with their counts, next to the number of distinct instructions the compared tools reach. `decode-survey-functions.tsv` keeps 303 sampled rows (start, size, instructions, decoded bytes, stop bytes).
2. **Decode equivalence** (`tool-equivalence.tsv` columns `executed_instructions`, `decode_different`, `swept_*`, `tool_raises_shared_decodes`, `sweep_different`; `decode-equivalence-instructions.tsv`). After each compared tool ran its cases, every instruction in its interpreter's decode cache (522 + 961 + 431 + 350 + 270 = 2,534 rows, listed one per line with a digest of all fields) was decoded again by the shared decoder and compared field by field (address, size, operation, both operands, width, condition, target, next address, immediate position and size, RIP displacement position). Then every FDE function holding such an instruction (18 functions, 3,096 addresses) was swept linearly with both decoders. Differences: 0. The old `shrdi` name of two tools is compared as `shrd`.
3. **Decoders of 11 tools on one sample** (`all-tools-decode.tsv`). Each `tools/*.py` with a `decode(read, va)` and a Machine copy (11 files) decodes the same 38,679 addresses (every 500th FDE function) next to the shared decoder. The three staking tools differ in 0 instructions and refuse 26 instructions the shared decoder accepts (all 26 are `endbr64`). The other eight differ in 3 instructions each, all three at `f3 0f 10/11` (`movss`, for example `f3 0f 10 44 24 44` at 0x3ada48f), which those eight decode as a 16-byte `movx`; the shared decoder keeps the 4-byte meaning. They also refuse between 140 and 424 instructions the shared decoder accepts (rol, bt, movsx, dec, xchg, cmpxchg, endbr64 ...), counted in `tool_narrower`. These instructions were not executed by the compared tools (decode equivalence above has 0 differences), so no merged result changes, but a packet that rebinds one of the eight to the shared module would change that decode.
4. **Execution equivalence** (`tool-equivalence.tsv` columns `cases_run` ... `identical_cases`; `execution-equivalence-cases.tsv`). Each tool's own case generator runs once with its own Machine and once with the module globals `Machine`, `Memory`, `decode`, `decode_range` and the exception classes rebound to the shared ones (`bound()` in the tool; a subclass of the tool's `Memory` is rebased too). For every case the digest of (rule-list match, result, per `run()` call: entry, outcome, all 16 registers, all 16 vector registers, instruction count, SHA-256 of every memory write) must match, and the shared run must still agree with the tool's written rule list. Cases: gate 4,000 of 15,928, listed set 1,200 of 11,365, validator snapshot 400 of 19,259 (980 machine runs), funding rate 3,023 of 3,023, funding premium 3,019 of 3,019: 11,642 cases, 12,222 machine runs, 1,672,720 instructions executed on each side, identical in 11,642 of 11,642; rule-list agreement 11,642 of 11,642 on both sides. The cases file lists every 40th case with both digests.
5. **Semantic probes** (`probes.tsv`). 77 hand assembled routines in 141 cases (flag conditions after cmp/add/sub/test/or, conditional jumps, 8/16/32/64 bit widths, sign extension, adc/sbb chains, mul/imul/div, shifts and rotates by `cl`, bt, bsr/tzcnt, cmpxchg, xchg, lea, cmov, push/pop, ucomisd, cvttsd2si/cvtsi2sd, scalar float NaN and zero-division rules, pshufd, pcmpeqb/pmovmskb, and/or/andn on doubles). Their expected values were written from the x86-64 instruction definitions, not taken from any tool, because the compared tools never reach several of these instructions (`decode-survey-ops.tsv`, column `reached_by_tools` is 0 for bsr, bswap, cmpxchg, div, movsx, rol, sar, tzcnt, xchg ...). All 141 pass on the shared interpreter.
6. **Controls** (`controls.tsv`, `equivalent-mutants.tsv`, `positive-controls.tsv`). 59 textual mutations of the shared module (flag conditions, carries, widths, sign extension, address arithmetic, call/stack handling, vector lanes, decode fields) are rebuilt as modules and run against the probes, then the decode references, then the reference digests of the five tools (160 cases each). 58 are detected (49 by a probe, 7 by a decode difference, 2 by a tool execution difference); 1 is listed as equivalent with its reason (`carry-cvttsd2si-edge`: the edited bound only matters for the input -2^63, where the exact result and the integer indefinite value are both 0x8000000000000000; the test file runs three boundary inputs through both). Positive controls: the unmodified shared module and an unmodified rebuilt copy agree with every reference. Detected + equivalent = 59 = all mutations made.

## Implementation and comparison

The shared module is the gate tool's lines 1-1103 moved unchanged, plus the differences found by diffing the five interpreters (these are findings about the tools, not about the binary):

- Added so that no compared tool needs a private decoder: `mulpd`, `maxpd`, `andnpd`, `cmpeqsd`, `punpcklqdq` through `66 0f 14`, `cmppd` predicate 2, immediate-count `shrd` (the old `shrdi`) and `endbr64` (decoded as a four byte `nop`).
- Changed behaviour, all outside what the compared tools execute: rotate and rotate-through-`cl` take the count from the operand (the gate copy used the register number); `shld`/`shrd` honour the operand width; scalar and packed `add/sub/mul/div` follow the x86 NaN rules and a zero divisor gives a signed infinity or the indefinite NaN instead of a Python exception (this is the rule the two funding tools already carried).
- Out of the compared range and therefore not claimed: `movzx`/`movsx` from a byte register 4..7 without a REX prefix decode as `spl..dil`, not `ah..bh`.

The tests (53) check the shared module against independent definitions: all 32 flag combinations against all 16 condition codes, byte add/sub flags against integer arithmetic over 256 x 52 operand pairs, memory regions, stub register poisoning, stack argument placement, step limit and callee-saved refusals, division refusals, a table of instruction forms with their lengths, data movement through the heap, plus the check tool's mutation targets, survey invariants, binding and probe runner. Rust path: not yet implemented (this packet is Python evidence tooling only, no Cargo graph).

## Results and limitations

Metrics (from `measure.json`): cases 11,642; negative controls 59 (detected 58, equivalent 1, undetected 0); probes 141 cases / 77 routines; decoded functions 16,915; decoded instructions 2,151,565; decode differences 0; execution differences 0.

Limits: equality is shown on the inputs the five tools generate (4,000 / 1,200 / 400 of their larger gate, set and snapshot streams) and 160 cases each for the mutation battery; it is not a proof for other programs. About 8 percent of sampled functions (1,407 of 16,915) stop at unmodelled forms, mostly thread-local accesses. The tools whose interpreter has another shape are not rebound; the eight tools that decode `movss` as `movx` would change on rebinding. The interpreter is a model checked against tool rule lists and hand-derived definitions, not against hardware. No progress gate is requested.

Next question: add the segment-prefix accesses that stop 782 of the sampled functions, then rebind one further family (the twap or bole tools) to `x86_115` and re-run this comparison with the larger set.
