# RE-002 · Node #115 RocksDB RegisterBuiltinComparators

Component: storage / comparators. Target: Linux x86-64 node #115, SHA-256
`a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`.

## Bounded question

How does node #115 register the three builtin comparators — which
function does the registration, what names / factory entry points /
manager functions does each block use, and who invokes the
registration? The 2058-byte body matches the vendor census exactly;
its source hash is reproduced by zeroing the 79 census relocation
fields (the twelve kind-42 sites already carry opcode 0x8B in the
target, so no opcode restoration applies). This is the continuation
of the comparator family: #5844 (the Bytewise/Reverse ordering and
separator functions), #5847 (the U64Ts wrapper layer), #5852 (the
U64Ts factory + Name), #5950 (the Bytewise/Reverse factories). It
closes the last open structural gap between them: how the three
factories get registered, and why the stubs — not the bodies — are
the registered entry points.

## Answer (pinned)

**Call shape.** The function at 0x61c1210..0x61c1a1a (2058 B) is the
`std::call_once` lambda `Comparator::CreateFromString` passes to
`std::call_once` (upstream util/comparator.cc:645-649), with
`RegisterBuiltinComparators` inlined into it — the census symbol
names it as that lambda. It takes no arguments and returns void:
the upstream `return 3` is discarded by the inlining (no
`mov $0x3,%eax` anywhere in the body; eax is 0 on the normal path).

**Prologue.** Fetch the default ObjectLibrary (call 0x61f8b60,
`ObjectLibrary::Default()`; the returned pointer is dereferenced
into r14) and prepare an empty SSO string at rsp+0x60 (the
factory-lambda's unused errmsg slot). Then three blocks, in this
fixed order.

**1. Bytewise (0x61c1238..0x61c1357).** Build the name
"leveldb.BytewiseComparator" (26 chars) by `_M_create` + two movdqa
copies from .rodata — 0x455300 ("leveldb.Bytewise", 16 B, stored at
+0) then 0x453a20 ("tewiseComparator", 16 B, stored at +10,
overlapping the first fragment's trailing "tewise" with identical
bytes) — NUL-terminate it. Form the 32-byte `std::function` object
at rsp+0x80 (16 zeroed functor bytes, manager 0x61bd810 at +0x10,
factory stub 0x61be8d0 at +0x18). Call
`ObjectLibrary::AddFactory<const Comparator>` 0x61c0d50 (library,
name, function) at 0x61c131a. Free the name heap (26 > 15, so heap).
Destroy the local function object by invoking its manager with op 3
at 0x61c1355.

**2. Reverse (0x61c1357..0x61c1435).** The same shape for
"rocksdb.ReverseBytewiseComparator" (33 chars): movdqa 0x452fb0
("rocksdb.ReverseB", 16 B, at +0) + 0x454210 ("ytewiseComparato",
16 B, at +16) + a single `movb $0x72` ('r') at +32. Manager
0x61bd840, stub 0x61be9b0. AddFactory at 0x61c13f8; manager op 3 at
0x61c1433.

**3. U64Ts (0x61c1435..0x61c1510, cold path 0x61c1578..).** The name
is NOT a literal: it comes from
`ComparatorWithU64TsImpl<BytewiseComparatorImpl>::kClassName()`, the
cached static std::string (guard 0x6508898, string 0x65088a0, from
#5852). Guard set: `strlen` the cached c_str and copy it (SSO if
<= 15, heap via `_M_create` + memcpy if longer; the 32-char name
takes the heap path; len 1 and len 0 have their own stores). Guard
clear: `__cxa_guard_acquire`; on 0 another thread built it meanwhile
(re-read the string); otherwise build it with an ostringstream
(insert the 26-char literal at 0x44e0fe, then ".u64ts" at 0x43c8ab),
assign into the cached string, register `__cxa_atexit` for the
string, `__cxa_guard_release`. Then manager 0x61bd870, stub
0x61beac0; AddFactory at 0x61c14d3; manager op 3 at 0x61c150e.

**4. The managers.** 0x61bd810 / 0x61bd840 / 0x61bd870 are 45-byte
functions with identical shape (own FDEs, no census records): a
three-way dispatch on the op word in edx — op 0 stores the address
of a .data.rel.ro slot into *rdi (bytewise 0x64d6ff8, reverse
0x64d7008, u64ts 0x64d7018); op 1 stores rsi into *rdi (copy the
functor value); any other op returns 0 without touching memory. The
two call sites that invoke a manager pass op 2 (inside AddFactory,
before the pair is copied out by movdqu) and op 3 (the local destroy
after each AddFactory); both are no-ops in the dispatch, and the
pair itself is transferred by the movdqu copy.

**5. Who calls what.** The caller census (`census.py`, whole-`.text`
E8/E9/LEA scan, Capstone-validated from enclosing FDE starts) finds
exactly one reference: a LEA at 0x61c01fa inside
`Comparator::CreateFromString` 0x61c0180..0x61c0cb4, taking the
lambda's address for `std::call_once`. No direct calls, no tail
jumps. The lambda is only ever invoked through `call_once`.

## Upstream confirmation (RocksDB v8.1.1)

`util/comparator.cc`: `RegisterBuiltinComparators` (lines 598–634)
is `static int RegisterBuiltinComparators(ObjectLibrary& library,
const std::string& /*arg*/)` — three `library.AddFactory<const
Comparator>` calls with `BytewiseComparatorImpl::kClassName()`
("leveldb.BytewiseComparator"),
`ReverseBytewiseComparatorImpl::kClassName()`
("rocksdb.ReverseBytewiseComparator") and
`ComparatorWithU64TsImpl<BytewiseComparatorImpl>::kClassName()`,
each with a lambda of the form `[](const std::string&,
std::unique_ptr<const Comparator>*, std::string*) { return
BytewiseComparator(); }`, then `return 3`. The lambdas ignore all
three arguments and return the factory directly — which is why the
binary stores the factory stub as the `std::function` functor.
`kClassNameInternal()` (lines 550–558) builds the U64Ts name with
`std::stringstream ss; ss << TComparator::kClassName() << ".u64ts";`
— the ostringstream cold path in block 3 — and `kClassName()`
(lines 461–467) caches it in a function-local static std::string
(the guard 0x6508898 / string 0x65088a0 pair from #5852).
`Comparator::CreateFromString` (lines 637–649) runs
`std::call_once(once, [&]() { RegisterBuiltinComparators(
*(ObjectLibrary::Default().get()), ""); });` — the census symbol
of 0x61c1210 is exactly that lambda, and the binary's single LEA
reference (0x61c01fa) is the lambda address being taken for
`call_once`.

## Open unknowns
- The runtime values of the three manager op-0 slots (0x64d6ff8 /
  0x64d7008 / 0x64d7018): each carries an R_X86_64_64 relocation to
  `_ZTVN10__cxxabiv117__class_type_infoE + 0x10`, so the value
  materializes only at load; which libstdc++ functor-type record
  each slot points to is not pinned here.
- The libstdc++ `_Manager_operation` enum naming for the op values
  observed here: AddFactory invokes the manager with op 2 and the
  local destroy with op 3, while the manager's dispatch only
  distinguishes op 0 (slot address) and op 1 (copy) from everything
  else (no-op returning 0). Whether op 2 is a move and op 3 the
  destroy in this libstdc++ version is not established from the
  binary alone.
- `ObjectLibrary::AddFactory` 0x61c0d50 (792 B, census-bound) is an
  engine callee: its 0x70-byte registry entry and 0x30-byte node
  layouts are described at contract level only (name copy,
  (manager, stub) pair copy, "Comparator" map insert under the
  mutex, duplicate-name find branch at 0x61c0fa0). Its full internal
  layout is not modeled in this packet.
- `Comparator::CreateFromString` 0x61c0180..0x61c0cb4 (3244 B) has no
  vendor census record, so its body/source hashes cannot be bound the
  census way; its reconstruction is the follow-up, not this packet.
