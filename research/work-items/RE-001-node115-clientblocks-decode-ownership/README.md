# Node 115 ClientBlocks decode ownership

Target: Linux x86-64 node #115, SHA-256 `a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`.

The earlier ClientBlocks grammar packet identifies `0x5ab7f10 -> 0x4fbad90`, the decoded block, attachment vector, and Arc wrappers, while explicitly excluding allocation and destruction. On the selected non-signed-minimum block-result arm, `0x4fbad90` receives the block from `0x4fb7760`, builds a `0x368`-byte allocation with two initial count words of one, and then calls `0x5824840` for the attachment vector. A signed-minimum result with tag `0x12` instead reaches the attachment decoder with the returned owner pointer and bypasses that allocation; the later release applies to that returned owner as well. If that vector returns tag `0x12`, it builds a separate `0x28`-byte allocation with two count words of one and writes the two allocation pointers to output +8 and +0x10, with tag `0x12`. Adapter `0x5ab7f10` forwards that selected pair.

If the attachment vector instead returns an error, the decoder copies the error to its result and atomically decrements the first count of the already allocated block. On a zero result it passes that same allocation's pointer slot to the relocated `0x5a8d7c0` cleanup. This binds the failure cleanup to the allocation made before the vector call, rather than supplying an unrelated pointer. Under normal cleanup returns, `0x5a8d7c0` releases its +0x10-counted backing region at 32 bytes per item, calls inline cleanup at +0x28 and +0x188, and decrements the second count at +8 before a conditional `0x368`-byte release. The previously studied `0x5a8b3e0` callback handles the corresponding 0x28-sized owner: it walks its +0x20 count through 40-byte items, conditionally releases each nested reference, releases the +0x10-capacity backing storage, and decrements its second count before conditional owner release. The element decoder itself does not invoke this latter callback; the enclosing vector error path below can do so for an earlier successful pair.

On the selected outer success arm, `0x5aac96c` supplies `0x5ab7f10` as callback to `0x5824f20`. A successful callback returns the two pointers at +8/+0x10; the vector helper appends them as one 16-byte row. If a later callback fails, the helper preserves that error, calls `0x5b4c550` on the accumulated rows, and then releases the vector backing allocation. Under normal cleanup returns, `0x5b4c550` walks each pair in order, decrements each first count, invokes `0x5a8d7c0` for a zero transition, then decrements the second and invokes `0x5a8b3e0` for a zero transition. This binds both actual decoder-produced owners to partial-prefix cleanup; it does not assert cleanup completed if a destructor unwinds.

This is a selected decode/ownership boundary, not an end-to-end cache or RPC-store trace. Matching sizes and callbacks alone do not prove the decoded pair enters the NV-stream collection or a particular store. Valid input memory, allocator behavior, helper returns and refcount invariants are premises; allocator failure, general unwind, concurrent lifetime and complete destruction of helper-owned subobjects remain open. The separate NV-stream consumer is prior evidence; its input identity is not newly established here.
