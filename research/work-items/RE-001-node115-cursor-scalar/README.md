# RE-001: bind node #115 byte-cursor scalar assembly

- Component: foundation, function map; exact source ownership unresolved.
- Target: Linux x86-64 node #115, SHA-256 `a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`, 105,896,032 bytes.
- Base revision: `8fd8db680ec4bfef40996e5616bce3d5156d0b86`. No source or reference implementation is used.
- Question: given a cursor/end pair and accessible bytes, what does the leaf at `0x1621dc0` return and how far does it advance?

On entry, RDI points to two qwords, cursor then end. If they are equal, the function returns EAX=0 without advancing; EDX is unspecified. Otherwise it reads the first byte, returns EAX=1 and advances by one through four bytes according to that byte: `00..7f` consumes one, `80..df` two, `e0..ef` three, and `f0..ff` four. For one byte EDX is that byte; for longer forms it shifts and combines the first byte masked to 5 bits (2/3 bytes) or 3 bits (4 bytes), and each subsequent byte masked to 6 bits. The first byte is compared unsigned. The function checks equality with end only before the first read; it does not check remaining length, continuation prefixes, overlong encodings, Unicode scalar validity or upper bounds. Thus it resembles UTF-8 assembly on valid inputs but is **not a validating UTF-8 decoder**. The rule assumes all bytes it reads are accessible, pointer arithmetic is valid, and the cursor/end descriptor does not overlap those bytes; it says nothing about invalid memory or concurrent mutation.
