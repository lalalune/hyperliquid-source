# RE-001: node #115's cached ZSTD decompress context

## Bounded question

How does node #115 hand a calling thread its cached ZSTD decompress
context, and what owns the context's lifetime? The answer is one
complete behaviour: a function-local-static shard table, a per-thread
claim that lazily creates the context, and an at-exit teardown.

## Answer (pinned)

- **Table** (`0x61c1f30`, built once by the getter `0x61c2120` via the
  static init `0x61c20d0`): 16-byte struct T — `+0x0` entries pointer,
  `+0x8` shift. `hardware_concurrency` picks the size: `ncpu <= 8`
  gives shift 3, count 8, alloc `0x208`; otherwise the smallest
  `e >= 4` with `(1 << e) >= ncpu`, alloc `count * 64 + 8`. The array
  is `[count:8][entries: count * 64]`; each 64-byte entry starts as
  `{obj: null, marker: -1, claim: self}` — the claim word holds the
  entry's own address while unclaimed.
- **Claim** (`0x61c1e10`, catalogue:
  `rocksdb::CompressionContextCache::GetCachedZSTDUncompressData`):
  pick the shard by the CPUID picker `0x60d5cd0` (leaf 0 → `-1`, else
  leaf-1 EBX >> 24), or by advancing the per-thread LCG seed
  `0x61c4080` once (`*0x41a7 mod 0x7fffffff`) when the picker returns
  `-1`; `entry = base + index * 64`; `lock cmpxchg(entry+0x10,
  expect=entry, new=0)`. The first claimer wins the shared slot and
  lazily creates the context there when empty; every later claimer of
  the same slot gets a fresh private context with index `-1`, which
  never enters the slot. The out pair starts as `(null, -1)`.
- **Create** (`0x628c0b0`, catalogue: zstd `ZSTD_createDCtx`, one of 2
  identical bodies): `malloc(0x176f8)` plus the pinned field init,
  including the CPU feature probe at `+0x75e4` (1 iff cpuid max leaf
  > 6 and leaf-7 EBX has both bits 3 and 8 set, i.e. BMI1 + BMI2) and
  `0x8000001` at `+0x7638`.
- **Free** (`0x628c1e0`, `ZSTD_freeDCtx`) is by contract; 23 direct
  call sites, including the teardown, the table-ctor old-release path
  and the claim landing pad.
- **Teardown** (`0x61c1d60`, registered via `__cxa_atexit` in the
  getter): free each owned slot object (marker `-1`) last-to-first,
  `delete[]` the array, `delete` the 16-byte table.
- **Kind-7 holder factory** (`0x61c1ce0`): kind `7` (ZSTD) builds the
  `0x38`-byte holder with vtable `0x64d7438+0x10` and a fresh DCtx at
  `+0x18`; any other kind returns null. Its one caller (`0x5f01e9d`)
  installs the product at holder `+0x78` beside a `0x8000`-byte array.
- **Consumers**: five claim call sites, all reached through the getter
  `0x61c2120`; the `(object, index)` pair is stored into holder
  structs. The holder ctor `0x60fe740` claims only for kind 7 or
  `0x40`. The teardown has no direct callers — it runs only via
  `__cxa_atexit`.

## Evidence

- `records.json`: semantic records only (no per-instruction mnemonic
  list). Instruction-level detail lives in the raw disassembly
  excerpts below, kept verbatim and whole-function. Mnemonics such as
  `endbr64` are genuine instructions present in the target binary,
  not placeholders.
- Whole-function verbatim excerpts (`*.objdump.txt`, regenerated by
  `export_excerpts.py`): claim, claim landing pad, create, table
  ctor, static init, getter, teardown, factory, picker, seed.
- `frames.txt`: the 10 FDE blocks from `objdump --dwarf=frames`.
- `callers.tsv`: every census site with its containing FDE and role.
- `relocations.txt`: no `R_X86_64_RELATIVE` entry points at a packet
  window; the factory vtable is a RIP-relative `lea`, the static
  slot/guard live in `.bss`.
- `verify.py`: the packet checker — run it from the repo root. It
  re-derives the excerpts, byte-checks fixed samples plus 3 seeded
  random gate spots against a fresh objdump run and the raw binary,
  re-runs the census, and runs the model tests.
- `census.py` / `gen_records.py`: regenerate the census and
  `records.json` from the binary.

## Environment limits (honest)

This VM has no cargo/rustc, no git-lfs, no Ghidra/Java, so `make
verify` / `make test` / `make catalogue-check` could not be run here;
the packet's own `verify.py` and the model tests are the checks that
were run. The vendor attributions are the catalogue's
relocation-qualified matches (235/235 and 290/290 non-relocation
bytes), not this packet's own rebuilds.

16-byte shared_ptr-slot table in `0x5f0a9c0`; LSDA call-site tables.
