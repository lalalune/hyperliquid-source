# RE-002 · Node #115 RocksDB WritableFileWriter::UpdateFileChecksum

Component: storage / file writer / checksum. Target: Linux x86-64 node #115, SHA-256

## Bounded question

How does a `WritableFileWriter` feed appended data to its file checksum generator -- what does
`rocksdb::WritableFileWriter::UpdateFileChecksum(const Slice&)` do with the writer's generator
and the data, and who calls it? The single FDE is census-bound (body hash matches the vendor
census `target_body_sha256` exactly; raw_equal, zero relocations):

| function | FDE | size | body SHA-256 |
|---|---|---|---|
| `rocksdb::WritableFileWriter::UpdateFileChecksum` | 0x604c7b0..0x604c7d1 | 33 | `1f2a30cf85914602784dea75923fb645ef27bc3bfc508a05a57872ab6d25dd63` |

The full hashes are in `functions.tsv` and `records.json`.

## Answer (pinned)

**Signature.** `void UpdateFileChecksum(const Slice& data)`; `this` in `rdi`, the `Slice*` in `rsi`
(`data.data()` at `(%rsi)`, `data.size()` at `0x8(%rsi)`). No stack frame, no canary, no calls,
no LSDA, no `.cold` FDE. The `.eh_frame` record at section offset `0x367168` has length `0x10`,
range `0x21`, `aug_len` 0: no LSDA pointer, no landing pad. The function cannot throw.

**Dispatch.** Load `this+0xc8` (`checksum_generator_`, a `std::unique_ptr<FileChecksumGenerator>`
per `file/writable_file_writer.h:163`); if null, return; else tail-jump to vtable slot 2 of the
generator with (`data.data()`, `data.size()`). Slot 2 is `Update`: `FileChecksumGenerator`'s
virtuals occupy six vtable entries in declaration order -- the two Itanium ABI destructor slots
(complete-object dtor, deleting dtor), then `Update`, `Finalize`, `GetChecksum`, `Name`
(`include/rocksdb/file_checksum.h:52-67`) -- so the third entry (`0x10` past the vptr) is
`Update(const char*, size_t)`. The 10 instructions (verified verbatim by `--live`):

```
endbr64
mov    rdi, [rdi+0xc8]       # checksum_generator_
test   rdi, rdi
je     0x604c7d0             # null: return
mov    rax, [rdi]            # vptr
mov    rdx, [rsi+8]          # data.size()
mov    rsi, [rsi]            # data.data()
jmp    [rax+0x10]            # tail-jump to Update (vtable slot 2)
nop                          # 3-byte alignment padding inside the FDE
ret
```

The binary tail-jumps to `Update` instead of calling it, so this FDE has no return path after the
dispatch -- the tail jump transfers control with Append's return address still on the stack, so
`Update` returns to `Append`, at the instruction after the call site (not to `Append`'s caller).
The concrete checksum algorithm is the generator's own behavior (already reconstructed for the
CRC32C/XXH generators in earlier RE-002 packets), not this function's; this model pins the dispatch
and the forwarded arguments only.

**Callers.** Exactly 1 direct call, 0 tail jumps, 0 LEA refs (whole-`.text` E8/E9/LEA scan,
Capstone-validated) -- `WritableFileWriter::Append` (site 0x6054764), once per `Append` before
`PrepareWrite`.

**Upstream cross-check.** RocksDB v8.1.1 (`meta/rocksdb`, read live this cycle) defines this helper
exactly as the binary behaves -- `file/writable_file_writer.cc:731-735` (`if (checksum_generator_
!= nullptr) checksum_generator_->Update(data.data(), data.size())`) -- and calls it once, in
`Append` (`:59`): the same single call site the census finds in the binary.

## Cases

and the model end-to-end legs (null/present x empty/huge/64-bit lens).

## Environment limits

No cargo/rustc/git-lfs/Ghidra on this VM. The target binary is never executed. The tool models
the helper in Python from its whole-FDE disassembly; data pointers are deterministic ids, not
real addresses, and the generator is modelled as an abstract `FileChecksumGenerator` (null or
named). `make verify/test/catalogue-check` in a tooled environment is still owed upstream.
