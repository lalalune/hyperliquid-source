# foundation: chrono RFC 2822 date parser 0x161fa20 and its seven scanners, run from node #115 bytes against written rules

- Component ID: foundation (chrono `format::parse` / `format::scan` third-party code inside the node; consumer components: l1-shared, action-wire)
- Target release and full SHA-256: Linux x86-64 node #115, `a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`
- Source commit / reference commit: repository base `0781ce04826eeefd89fe336cb8ea073be0c1de30`; no reference source is copied (chrono names appear only as hypotheses to check, taken from the merged RE-002 reference packets)
- Claim status: observation for every table of bytes and every comparison count; inference for the chrono names and for the rule list being "the documented behaviour"
- Scope included and excluded: included - the whole RFC 2822 date flow as one closed call graph run from file bytes: `parse_rfc2822` 0x161fa20 (1,425 bytes, 348 instructions, 55 conditionals) and every body it reaches, the digit scanner 0x161f900, `set_hour` 0x1621cc0, the one-byte scanner 0x1625ce0, the parenthesised-comment scanner 0x1624e80, the weekday scanner 0x1625100 and month scanner 0x1624fb0 (both reached through GOT slots), the zone scanner 0x1625790 and `trim_start` 0x16288c0. Nothing is stubbed except the panic slots. Excluded - the two callers 0x161ffc0 and 0x1620be0, the bytes behind the non-panic error slots, and every gate in docs/PROGRESS.md (no gate is requested). The zone scanner 0x1625790 and trim_start are exercised as callees only; their own edits are not repeated here.

With this packet a Rust reconstruction can write the RFC 2822 date parser as one checked rule list instead of guesses: the order in which fields are scanned (optional weekday and comma, one or two day digits, month name, year of two or more digits with the 50-year window, hour, colon, minute, optional colon and second, numeric or named zone, then any number of comments), which gap after each field is mandatory, which error tag every failure returns (0 out of range, 1 impossible, 3 invalid, 4 too short), the set-once rule of the parsed-fields record (a present field must hold the same value or the result is tag 1) and that fields written before a failure stay written, the exact ranges (day 1-31, year below 2^31, hour below 24, minute below 60, second up to 60), the digit scanner's `min`/`max` contract, and every place a char-boundary panic is raised. 43,552 generated and named inputs were run through the real bytes and agreed with the rule list on the 32 result bytes, the 0xA8-byte parsed record, the `set_hour` return value or the panic arguments every time; 433 negative controls were all detected.

## Reproduce

Working directory: the repository root, platform Linux x86-64, Python 3 standard library only. The tool reads the connected node #115 binary and refuses any other SHA-256 first. It does not run the binary, call objdump or readelf, or use the network.

```
python3 tools/chrono_rfc2822_parse_115.py --out research/work-items/foundation-chrono-rfc2822-parse-115
python3 -m unittest tests.test_chrono_rfc2822_parse_115
sha256sum -c research/work-items/foundation-chrono-rfc2822-parse-115/MANIFEST.sha256
```

The generation is deterministic (no clock, no random source, no absolute path in any output); two runs into different folders are byte-identical. The full run takes about 85 seconds and peaks at about 380 MB: cases are made, run and compared one at a time and only counts are kept. It reuses the evaluator in `tools/bole_rate115.py` (with one added rule: the overflow flag after `imul`, which the digit scanner branches on) and the FDE parser behind it.

## Evidence

All coordinates are virtual addresses of the node #115 ELF. Every number below is produced by the tool from file bytes (section headers, `.eh_frame` FDE extents through the shared parsers, `.rela.dyn` RELATIVE addends, fixed byte patterns for direct calls, slot calls and the `[r14+disp]` operands).

- `functions.tsv` - exact FDE extents, instruction and conditional counts of the nine bodies that run: parse_rfc2822 0x161fa20..0x161ffb1, scan_number 0x161f900..0x161fa20 (288 bytes), set_hour 0x1621cc0..0x1621d20 (96), scan_char 0x1625ce0..0x1625d40 (96), scan_comment_2822 0x1624e80..0x1624fa2 (290), scan_weekday 0x1625100..0x162520b (267), scan_month 0x1624fb0..0x16250f3 (323), timezone_offset_2822 (1,358), trim_start (382).
- `slots.tsv` - the three RELATIVE-relocated GOT slots whose addends are bodies of this packet: 0x64e1b00 -> parse_rfc2822, 0x64e1b08 -> scan_weekday, 0x64e1b10 -> scan_month. This is why the parser is not found by direct `call` scans: its two callers use `call [rip+disp]` on 0x64e1b00.
- `callers.tsv` - 45 call sites (direct E8 calls and `ff 15` slot calls) of the nine bodies, each with its owner FDE. parse_rfc2822 is called from 0x161ffc0 (site 0x16204a5) and 0x1620be0 (site 0x1620ff0). The weekday scanner has five callers (0x161fa20, two sites in 0x161ffc0, two in 0x1620be0), the month scanner four (0x161fa20, 0x161ffc0, 0x1620be0, 0x1625680), the digit scanner four sites, all inside the parser (0x161fc58 year, 0x161fd1c hour, 0x161fd91 minute, 0x161fe33 second).
- `record-layout.tsv` - the offsets of the parsed-fields record that the parser itself touches through `r14`: year 0x10/0x14, month 0x40/0x44, day 0x68/0x6c, minute 0x80/0x84, second 0x88/0x8c, offset 0x98/0x9c (a present-flag word equal to 1, then the value word) and the weekday byte at 0xa0 (7 means none). The hour pair 0x70/0x74 (half day) and 0x78/0x7c (hour of half day) is written only inside `set_hour`.
- `reach.tsv` - how many instructions of each body the cases reached. parse_rfc2822 342/348: the six unreached instructions are the signed overflow of `year + 1900` (cannot happen for a three-digit number), the null-pointer returns of trim_start, and the `sub` overflow panic. scan_number 80/81, scan_comment_2822 74/79 (an alignment nop and the depth-zero and depth-overflow panics), set_hour, scan_char, scan_weekday and scan_month 100%.
- `outcomes.tsv` - cases per function and outcome class; `sample-cases.tsv` - every 800th case with its outcome class and a result digest; `rule-mutants.tsv`, `byte-mutants.tsv`, `structural.tsv` - the negative controls; `measure.json` - the counts the checker reads.

Observed rules (each is a row of the written rule list in `Spec.parse` and its helpers and is checked against every case):

- Entry: `parse_rfc2822(out, parsed, s, len)`; the result is a rest pointer and length at +0 and +8, or a null pointer and one tag byte at +8.
- `trim_start`, then the weekday scanner. A weekday word (Mon..Sun in any case, numbered 0..6 from Monday) must be followed by `,` (otherwise tag 3, even at end of input) and the weekday byte at parsed+0xa0 is set when it is 7 or must equal the word's number (tag 1). No weekday word means the scanner returned 7 and the parser goes on without it.
- Day: one digit, optional second digit (never a third), value 1..31 (tag 0 otherwise), set-once at 0x68; the gap after the day is mandatory: tag 4 when nothing follows, tag 3 otherwise.
- Month: three letters from the table, set-once at 0x40 with value 1..12; a gap is mandatory (tag 4 on empty, 3 otherwise).
- Year: `scan_number(min 2, max unbounded)`; two digits map below 50 to +2000 and the rest to +1900, three digits add 1900, four or more are taken as written; the result must be below 2^31 (tag 0), set-once at 0x10; the digit scanner reports tag 0 once the value reaches 2^63.
- Hour: exactly two digits (`scan_number(2, 2)`), `set_hour` (below 12: half day 0, above: half day 1 and hour minus 12; 24 or more returns 0; a mismatch of the half day returns 1 before the hour is written; success returns 8), then trim, a `:`, trim, minute (two digits, at most 59, set-once at 0x80), trim, an optional `:` followed immediately (no trim) by two second digits (at most 60, set-once at 0x88), a mandatory gap, then the zone scanner (offset set-once at 0x98), then comments `( ... )` with nesting and backslash escape are consumed one after another until the comment scanner fails; the rest is what remains.
- The digit scanner is `scan_number(out, s, len, min, max)`: `min > max` is the assert panic (the 28-byte message), a string shorter than `min` is tag 4, a non-digit before `min` digits is tag 3; digits are read until the first other byte or until `max` digits; `max == 0` never stops on the count, reads every digit and then returns the start pointer with the whole length (a quirk of the compiled body, observed in the `(0, 0)` rows of the shape grid).
- A char-boundary panic is raised at every place the bytes slice the string after a scanned token: the panic arguments (start, length) are compared too. The inputs are well-formed text, plus single stray continuation bytes placed only on the byte the body checks (a `&str` cannot carry them; they probe the byte-level check).

## Implementation and comparison

There is no Rust implementation in this packet ("not yet implemented"): the deliverable is a checked rule list, `Spec` in `tools/chrono_rfc2822_parse_115.py`, that a Rust port can be tested against. The comparison is: for each case, `Harness.run` executes the real bytes of the target body in the evaluator and `Spec.run` computes the expected output from the written rules; the two outcomes (result bytes, 0xA8-byte parsed record after the call, `set_hour` return value, or panic name and arguments) must be equal, and any write outside the result and record is a failure.

- Cases (43,552): 54 named edge inputs; 14,000 composed dates (60% well-formed parts with gaps, 40% free parts), a quarter of them with some parsed fields pre-set to the value the same input would produce, a different value, or a non-1 flag; every byte value 0-127 plus 0x80, 0xBF, 0xC0, 0xC3, 0xFF at every position of four well-formed dates (116 positions x 133 byte values, filtered to the admissible inputs); every truncation of those dates with and without trailing bytes; the digit-scanner shape grid (13 `(min, max)` pairs x 20 digit strings x 5 tails) and 2,200 random strings; `set_hour` for 38 values against 73 pre-set record states each (2,774 cases); characters, comments and names (all three-letter sweeps of every name).
- Outcome classes (`outcomes.tsv`): parse_rfc2822 ok 8,016, tag 0 1,092, tag 1 1,893, tag 3 16,696, tag 4 102, slice panic 564; scan_number ok 1,950 with assert panic 458; set_hour returns 0, 1 and 8 in 1,022, 846 and 906 cases.
- Negative controls (433, all detected): 398 byte edits (every conditional, immediate and displacement of the seven main bodies edited; each is killed by a class-picked subset of the cases; 30 further edits survive and are reported as equivalent, not counted), 24 wrong rule lists (17 single-rule mistakes inside the rule list, such as a wrapping digit scanner, no escape in comments, Sunday-first weekdays, one-based months, EST/EDT swapped, set-once ignored, no 50-year window, seconds capped at 59, comments ignored; and 7 shape-level mistakes, such as tag 3 reported as tag 4, `set_hour` returning 0 on success, state not kept on error, weekday not stored) and 11 structural controls (a flipped file byte changes the SHA-256, four non-start addresses refused, slot contents, call-site lookups, an oversized string refused, scanner result against the wrong rule).
- Reproducibility: the checker regenerates all files in `--out` twice and the bytes agree; the 31 unit tests in `tests/test_chrono_rfc2822_parse_115.py` run in about 30 seconds.

## Results and limitations

Metrics are in `measure.json`: cases 43,552, negative controls 433, detected 433, byte edits 428 (398 killed, 30 equivalent). All counts have explicit denominators in `outcomes.tsv`, `reach.tsv` and the mutant tables.

- The evaluator is a small x86-64 subset interpreter that I wrote and cross-checked only through these cases; an instruction it mis-evaluates would be caught only if the rule list disagreed. The rule list was written from the documented chrono behaviour and from reading the disassembly, so it is not independent of the reader's understanding of the bytes; the equal results show the two agree, not that chrono's source says so.
- The cases are generated, not exhaustive; unreached instructions are listed in `reach.tsv` with the reason, and the equivalent byte edits are not proved equivalent, only not noticed by the subset.
- The zone scanner and trim_start run as real callees, but their own branches are only partly exercised here (366/376 and 87/106); the zone scanner's own rules are in the separate timezone packet (a rule-list copy lives in `Spec.zone`).
- The names (parse_rfc2822, scan_*) are inferences from the shape and from the RE-002 reference packets; the two callers 0x161ffc0 and 0x1620be0 and the stored result of the parsed record (who reads weekday, day, month, year, hour pair, minute, second, offset) are not reconstructed.
- No progress gate is requested; this covers one third-party parser, not a component.

Next question: the two callers of the parser through slot 0x64e1b00 - 0x1620be0 (`parse_internal`, 2,888 bytes, an item-list interpreter that also calls the weekday and month scanners) and 0x161ffc0 (3,098 bytes) - and how the parsed record is turned into a timestamp.
