- Question: which #94 bodies carry the `build_mode.rs` panic anchors, what
  paths and strings do they produce, and does the reference lead match them?

Two bodies carry the three `build_mode.rs` Location records. The build-dir
body prefixes every non-local path with a `static_config.rs` lazy value (the
path its initializer names `cham_dir`). It tests `"run-client"` before
dispatching on the mode byte. The second body is the initializer of a lazy
`String`, built from process arguments, trimmed and space-joined. The reference
lead differs from the binary in five independently checkable ways (listed
below). None of this establishes a Rust signature, the meaning of the second
mode byte, runtime argv or `cham_dir` values, or a gate.

## Build-dir body `0x13cd410`

Arguments: `rdi` result, `rsi`/`rdx` name pointer/length, `cl` mode byte 0,
`r8b` mode byte 1. The result is a 24-byte owned string (`cap, ptr, len`) plus
a tag byte at `+0x18`. Observed routes:

1. `0x13cd428`: if `byte0 | byte1 == 0`, return an owned copy of the name; tag 0.
2. `0x13cd42f`: otherwise, if the name is exactly the 10 bytes `run-client`,
   format `{}/code/run-client` with the lazy `static_config` value's field
   `+0x18` (`0x13cd596`); tag 0 (`0x13cd5f2`). **This test precedes any
   mode-byte dispatch**, so it applies to every non-`(0,0)` mode, including
   ones that would otherwise panic.
3. `0x13cd45f`: byte 0 equal to 1 selects `debug` (5 bytes), equal to 2 selects
   `release` (7 bytes). The body formats `{}/{}` (profile, name), then
   `{}/aws_build/{}` with the same `+0x18` field and that intermediate string;
   tag 1 (`0x13cd54d`). The intermediate string is freed.
4. Anything else panics with `tried to get build_dir of {}, a bug?` at
   `build_mode.rs:199:30`. The argument is the two mode bytes, formatted by
   `0x14444d0` (not closed here).

So the observed non-local paths are `<field>/aws_build/<debug|release>/<name>`
and `<field>/code/run-client`. The meaning of mode byte 1 beyond the `(0,0)`
test and the panic argument is unresolved.

The only decoded call site is `0x13cd7ad` through GOT slot `0x576ea20` (RELA
addend `0x13cd410`), inside caller FDE `0x13cd6d0..0x13cdeed`. It passes the
name pair and two zero-extended mode bytes. The complete `.text` census finds
no direct call or RIP-relative reference to `0x13cd410` itself. The caller's
command object is retained as context only.

### The `+0x18` field is the `cham_dir` path (static_config)

GOT slot `0x576e928` holds the lazy value address `0x577b288`. That slot's
stored initializer (RELA addend) is `0x164ff00`; the build-dir body reads Once
state at value `+0x50` and passes `+0x18` to a string displayer (`0x14566b0`,
`ptr`/`len` at `+8`/`+0x10`). The initializer stores the path it checked at
`+0x18` (`0x164ffa3`). When the predicate at slot `0x5770b38` returns false,
it panics with `cham_dir does not exist: {}` (`static_config.rs:24:9`) and
formats that same path. It also stores `format!("{}/code", …)` at `+0x30`,
which the build-dir body does not use. The helpers that obtain the path, and
the predicate itself, are not closed; the name `cham_dir` comes from the
panic text.

## Invocation-name lazy initializer `0x143ef30`

Slot `0x577ab80` holds RELA addend `0x143ef30`, and its Once state is
`0x577ab98`. Example use `0x13cbae6` passes state `0x577ab98` and a closure
referencing the slot to the Once routine (GOT `0x576e8b8`). The census records 613 RIP-relative
references to `0x577ab80` and 1,236 to `0x577ab98` in `references.tsv`. Their
consumers are not classified here.

Observed body (labels in parentheses are inferences from callee evidence):

1. Initialize an empty accumulator. Call slot `0x576f540` (consistent with
   `std::env::args`), then repeatedly call slot `0x576f548`, whose body
   references `std/src/env.rs:871:51` (consistent with `Args::next`). The niche
   value `i64::MIN` in the capacity word ends the loop. There is no pre-loop
   `next()`, so the first yielded element participates.
2. Skip an argument when its length is at least 2 and it starts with `--`.
3. When `0x1440df0` reports that `/cham/` occurs in the argument:
   - assert that it does not end with `/` (`build_mode.rs:29:17`);
   - find the **last** `/` with an inline backward scan and keep the suffix
     after it. A suffix start at a UTF-8 continuation byte panics
     (`build_mode.rs:32:26`);
   - search that suffix for the **last** `-` with slot `0x576f550`. The helper
     `0x157a8a0` compares `byte[bound-1]` downward. The loop keeps a fixed start
     and shrinks the bound to each hit. If found, keep the prefix before it.
   Otherwise keep the whole argument.
4. Pass the piece through `0x1407ac0`. That helper compares decoded code
   points with Unicode White_Space values such as U+1680 and U+3000 in both a
   forward and a backward pass (consistent with `str::trim`). Then set
   `acc = format!("{} {}", acc, piece)`. A separator is inserted even when the
   accumulator is empty.
5. After the last argument, pass the accumulator through `0x1407ac0` and
   return an owned copy.

Derived from these rules, not executed: an argument `…/cham/hl-node-x-1`
yields `hl-node-x`, and arguments `["a", ""]` yield `a` (the trailing
separator is trimmed).

## Comparison with the reference lead

| Item | `base/build_mode.rs` lead | #94 bytes |
| --- | --- | --- |
| Panic anchors | `30:199`, `17:29`, `26:32` | `199:30`, `29:17`, `32:26` (line and column swapped in the lead) |
| Non-local paths | `/aws_build/{profile}/{program}`, `/code/run-client` | prefixed by the `static_config` `+0x18` path |

| `-` truncation | first `-` (`find`) | last `-` (reverse search) |
| Join | no separator before first name; no trimming | `"{} {}"` every time, each piece and the result trimmed |

These are differences between the lead and observed instructions only. The
lead's attribution of both bodies to `build_mode.rs`, its `debug`/`release`
byte values, the `--` skip, `/cham/` selection, final-segment selection and
tag byte agree with the bytes. A test rewrites each `build_mode.rs` record to
the lead's swapped values and requires rejection.
