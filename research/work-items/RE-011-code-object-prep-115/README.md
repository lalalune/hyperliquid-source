# RE-011: lazy account code-object preparation 0x54793e0 and 0x433c700 with the code-map entry function 0x4ef7e50 reconstructed and checked against the node #115 machine code

- Component ID: evm (RE-011 EVM fork and RPC adapter), CALL-family host path
- Target release and full SHA-256: node #115, `artifacts/node/115/hl-node`, `a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`
- Source commit / reference commit: tool authored against the repository main checkout; no reference source was copied (the labels in references/can1357-hl were not used)
- Claim status: observation (byte-grounded machine-code equivalence under the stated callee contracts) with explicitly marked inferences
- Scope included and excluded: the two bodies in full plus the code-map entry function 0x4ef7e50 (349 bytes, evaluated as real machine code, not stubbed), including the empty-code-hash shortcut, the shared default code object, both map-lookup protocols, the hashbrown insert into the code map, the Arc reference-count rules (including the `lock inc`/`jle` overflow trap) and the release of a previously stored slot value. Excluded: the remaining callees (stubbed with a recorded contract, see below), the unwind landing pads and no gate is requested.

With this packet the code-object cache step that the CALL-family hosts (0x546c330 and 0x4335cf0) run before reading an account's code can be reconstructed as two pure functions: one for the hot-path body 0x54793e0, which finds or inserts the Arc of the code object in a hashbrown map keyed by the 32-byte code hash (lookup through the entry function 0x4ef7e50 with its folded two-multiply hash), and one for its ordinary twin 0x433c700, which asks a tagged lookup and consumes its result by tag; both share the Keccak-256(empty) shortcut, the shared default Arc and the slot-release rule. All 11,820 comparison cases agree with the evaluated machine code, and all 46 negative controls are detected.

## Reproduce

Run from the repository root with the connected binary in place (no external programs are used, the binary is never executed):

```
python3 tools/artifacts.py verify
python3 -m unittest tests.test_re11_code_object_prep115
python3 tools/re11_code_object_prep115.py --out research/work-items/RE-011-code-object-prep-115
sha256sum -c research/work-items/RE-011-code-object-prep-115/MANIFEST.sha256
```

The tool checks the SHA-256 of the input binary first and fails on a mismatch. Every number and list in the evidence files comes from reading the ELF bytes with `tools/elf_index.py` and `tools/fde_extents.py` (section table, `.eh_frame` FDE extents, RELATIVE relocations of the GOT slots, code and constant bytes). Regeneration is deterministic (checked twice, different output folders, `diff -r` empty) and takes about 25 s, at most a few hundred MB.

## Evidence

Coordinates are virtual addresses of node #115. Both bodies are full FDEs: 0x54793e0 is 596 bytes (142 instructions, linear decode is exact), 0x433c700 is 291 bytes (82 instructions), 0x4ef7e50 is 349 bytes (96 instructions); see `constants.json` (`functions`, SHA-256 of the body bytes) and `decoded-instructions.tsv` (every instruction with bytes and whether a case executed it).

Observations (machine code):

- Both start with `cmp qword [rdi+0x70],0` and return when the account code slot is already set. The 32-byte code hash is at account +0x48.
- The hash is compared with two 16-byte constants, `0x4537f0` (first half) and `0x452020` (second half) through `pcmpeqb`/`pand`/`pmovmskb`; together they are c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470, the Keccak-256 of empty input. Both halves must match (mask 0xffff) for the shortcut.
- The shortcut and every miss fall back to the same default: GOT slot `0x64e6c78` (RELATIVE, addend 0x64fdfc0) is a lazy static whose dword at +8 is a state (non-zero: call the init function, 0x5b084ff in the hot body, 0x435059c in the twin), then its word at +0 is the shared default Arc, incremented with `lock inc qword [arc]`. `jle` after the increment goes to `ud2`; since `inc` sets OF, the old value 0x7fffffffffffffff is the only negative-looking result that does not trap.
- 0x4ef7e50 (map entry function; rdi = result, rsi = map header at host +0x40, rdx = 32-byte key) hashes the key as four limbs k0..k3 with the header secret (+0x20) and the process seed (GOT slot 0x64dfa78, RELATIVE, target 0x64ffe90): m = (k1 ^ seed) * (k0 ^ secret) (128-bit), x = lo(m) ^ hi(m) ^ k2, r = x * (seed ^ k3), hash = lo(r) ^ hi(r). It probes 16-byte control groups from `hash & mask` (triangular stride), compares each control byte with `hash >> 57` (pcmpeqb), confirms a match by comparing the full 32-byte key stored in the 40-byte bucket, and stops at the first group that contains an EMPTY (0xff) byte (DELETED does not stop it). A hit returns 0 / bucket end (ctrl - 40*idx) / map; a miss with growth_left == 0 first calls the reserve function behind GOT slot 0x64e6c98 (target 0x5be4680, args map, 1, header+0x20, 1), then returns map / hash / the key copy.
- 0x54793e0 calls that entry function with the map at host +0x40 (host = `[rsi]`) and the hash. A zero first word of the 0x20-byte result is the occupied case: result word +8 points past a bucket whose last word is the Arc (`[ptr-8]`), which is cloned with `lock inc`. Otherwise the result is the vacant case: table pointer, hash, 32-byte key at +0x10. The loader behind GOT slot `0x64e6458` (target 0x43c8ec0) is called with (host +0x90, hash) and returns the new Arc in rax.
- The vacant insert is the hashbrown find-insert-slot over 16-byte control groups: start at `hash & mask`, `movdqu` + `pmovmskb` of the high bits, `tzcnt`, then triangular probing (+16, +32, ... via the `r8` stride loop at 0x54795d6); if the found control byte has its high bit clear (small tables, mirror bytes) the first special slot of the group at control +0 is used (0x54795f9). The control byte and its mirror at `((idx-16)&mask)+16` get `hash >> 57`, the bucket is 40 bytes below the control array (`ctrl - 40*(idx+1)`: 32-byte key, then the Arc), growth_left (+0x10) is decreased by the old control byte's bit 0 and items (+0x18) is increased by one (`psubq` with the constant at 0x450790, which is {0, -1}). The new Arc is then incremented once more (map owns one, the slot owns one).
- 0x433c700 calls the tagged lookup 0x3d48830 on host +0x928 with the hash. Tag 5 (64-bit compare) with a non-zero pointer in result word +8 publishes that Arc without any count change; tag 5 with zero, and every other tag whose low 32 bits are below 2, take the default path. Low 32 bits equal to 2 call the drop slot of a boxed error object (`call [[p1]]`, rdi = p1). Larger tags call the deallocator behind GOT slot `0x64df4a0` (target 0x635de30) with (rdi = result +0x10, rsi = result +8, edx = 0) when result +8 is non-zero. The tag 0x1_0000_0005 style values prove the compare order: the first test is 64-bit, the later ones 32-bit.
- Both end by releasing a previous slot value (it can only be non-zero if a callee stored one): `lock dec`, and at zero the drop-slow function behind GOT slot `0x64e4fa8` (target 0x5bde820) with rdi = account +0x70; then the Arc is stored at +0x70.

Inferences (not proven by bytes alone): the code map is keyed by code hash and the map value is an Arc of the decoded code object; the default Arc is the shared empty-code object; the two bodies are the hot-path and ordinary-path variants of one source function. Names are descriptive only.

## Implementation and comparison

`tools/re11_code_object_prep115.py` contains (a) one independent pure-Python reconstruction `model()` of both bodies, including the exact trap rule (`inc_traps`), the hashbrown probe (`probe`) and the insert bookkeeping, and (b) the evaluation of the real machine code with the concrete x86-64 evaluator of `tools/re11_transient_storage115.py`, extended in this tool by the LOCK prefix and the signed jcc conditions (`jl/jge/jle/jg`). The entry function 0x4ef7e50 is evaluated as real machine code (hash, probe, key compare, reserve call) against its own model. Other callees are stubbed with a recorded contract and compared through a call log: reserve 0x5be4680, loader 0x43c8ec0, lookup 0x3d48830, deallocator 0x635de30, vtable drop, drop-slow 0x5bde820 and the two lazy-init functions. Stubs can store a previous slot value (re-entrancy) so the `lock dec` release path runs.

Comparison per case: outcome (`ok`, `ud2`), account +0x70, the eight Arc counters, the lazy-static state, the whole code-map state (control bytes with mirror, 40-byte buckets, growth_left, items), the ordered call log with arguments, and (for `ok`) that rbx, rbp, r12-r15 and rsp are restored. The 11,820 cases are generated deterministically from a SHA-512 stream: preset slot, empty hash, half-matching hashes (one bit flipped in either half), occupied entries, tables of 4 to 64 slots whose resident keys are placed by the model itself (per-case secret and seed, random residents, decoys that share the key's h2 and probe path, erased entries, a fully occupied first probe group, growth_left exact, 0 or 1), all lazy states, counter edge values (0, 1, 0x7ffffffffffffffe, 0x7fffffffffffffff, 0x8000000000000000, -2, -1), re-entrancy before/after each callee, and 16 tag values (low-32 aliases included) for the twin.

Negative controls (`negative-controls.tsv`): 13 wrong models (key compare skipped in the entry function, DELETED treated as a stop, empty hash compared on one half only, missing default increment, overflow treated as trap, missing drop call, wrong h2 shift, growth always decreased, 32-byte buckets, linear probe, missing small-table fallback, 64-bit tag compare, extra increment on the moved Arc), 31 inverted conditional jumps in the machine code (every jcc of the three bodies), one flipped `.text` byte (digest refusal) and one out-of-range code address. `undetected-code-mutants.tsv` lists code mutants no case distinguishes; it is empty.

## Results and limitations

- `measure.json`: 11,820 cases, 46 negative controls, 46 detected; 0 mismatches. Instruction coverage: 139/142, 79/82 and 96/96 (0x4ef7e50); the unexecuted ones are the unwind landing pads at 0x5479629 and 0x433c818 (store, move, `_Unwind_Resume` call).
- Class counts per body, kind and outcome are in `outcome-classes.tsv`; ud2 outcomes are counted and reproduced (the count stays incremented when the trap is taken).
- Limits: the other callees are not reconstructed here (the tagged lookup 0x3d48830, the loader 0x43c8ec0, the reserve function 0x5be4680, the lazy initialisers); only their register-level contracts are fixed. Memory is a synthetic region layout, not a real host. The evaluator subset is the one used by the sibling packets plus LOCK and signed jcc. This is not a Rust implementation and no progress gate is requested; the evm component gate stays at its current value.
- Next question: the sibling loaders 0x5463980 and 0x4323870 (account load behind the CALL hosts; their callees 0x4ef78b0, 0x54419e0, 0x3ed7040, 0x3d48970 are different from the ones here) and the tagged lookup 0x3d48830 and loader 0x43c8ec0 behind the twin and the hot path.
