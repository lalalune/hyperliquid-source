# RE-001: map node #115 small getter run 0x5eeb150..0x5eeb213: entry-range count and plain field projections

Bounded question: what do the five small getters in the contiguous
0x5eeb150..0x5eeb213 run project into `*out`, and what does the count
getter compute over the entry range of `[outer + 0x788] + 0x30`?

Target: node #115 work binary `work/hl-node-115.bin`,
SHA-256 `a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`
(bound to provenance/artifacts.json for node #115).

## What is pinned

Five whole getters, not lone-window fragments, all returning 1
unconditionally with no null check anywhere:

- Count 0x5eeb150 (outer in rdi, out in rsi): member `[outer + 0x788]`,
  sub-object `[member + 0x30]`, `*out = ([sub + 0xb20] - [sub + 0xb18]) >> 4`
  with an arithmetic shift on the wrapped 64-bit difference. This is the
  entry count of the same 16-byte entry range whose sums the twin
  entry-sum getters of #2307 walk and whose report the blob-file report
  getter of #2313 formats — the count arm of that family, pinned here
  rather than re-derived there.
- Signed field 0x5eeb180 (obj in rdx, out in rsi, rdi ignored):
  `*out = sign_extend32([obj + 0x1438])` via `movslq`, so a stored
  0xFFFFFFFF reads back as -1, not 4294967295.
- Field 0x5eeb1a0 (obj in rdi, out in rsi): `*out = [obj + 0x770]`
  (64-bit, untouched).
- Field 0x5eeb1c0 (obj in rdx, out in rsi, rdi ignored):
  `*out = [obj + 0x1228]` (64-bit, untouched).
- Guarded field 0x5eeb1e0 (obj in rdx, out in rsi, rdi ignored):
  `ptr = [obj + 0x1200]`; `*out = 0` when `ptr == obj + 0x11e0` (the
  empty sentinel arm, which never dereferences ptr), otherwise
  `*out = [ptr + 0x30]`.

The two argument shapes are stated literally rather than normalized:
the count and 0x770 getters take their object in rdi, while the signed,
0x1228, and guarded getters take theirs in rdx and ignore rdi — the
rdx-arg shape already seen in #2263. Instruction-level detail lives
only in the verbatim excerpts; mnemonics such as `endbr64` there are
genuine instructions present in the target binary, not placeholders.

Left by contract, stated openly: the adjacent static initializer at
0x5eeb110 (not a getter — it zeroes the global at 0x65029a0 and
registers its destructor via `__cxa_atexit`); the dispatch mechanism
reaching these getters (no direct callers exist in this binary); and
the record type behind the guarded getter's `ptr + 0x30` field.

## Census (whole-file scan, reproduced by census.py)

All five getters: 0 direct calls, 0 tail jumps, 0 qword hits,
0 RELATIVE addends — the virtual-getter shape seen across the
0x5eebxxx getter run.

## Evidence format

- `records.json`: semantic records only — windows, argument shapes,
  the count range, each getter's projection, and the census. No
  per-instruction mnemonic list: instruction-level detail lives only in
  the verbatim excerpts.
- `count_0x5eeb150.objdump`, `signed_0x5eeb180.objdump`,
  `field_0x5eeb1a0.objdump`, `field_0x5eeb1c0.objdump`,
  `guarded_0x5eeb1e0.objdump`: whole-function excerpts exactly as
  objdump emitted them, regenerated by `export_excerpts.py` with e.g.:
  `objdump -d --start-address=0x5eeb150 --stop-address=0x5eeb17a work/hl-node-115.bin`
  and the same pattern for the other four windows.
- `frames.txt`, `relocations.txt`: FDE extents and relocation findings.
- `verify.py` + `export_excerpts.py` + `census.py`: the checking code is
  committed in the packet, not only claimed here.

## Model and tests

`tools/entry_count_field_getters_115.py` models all five getters end to
end (inputs through the model to the observable `*out` value);
`tests/test_entry_count_field_getters_115.py` covers the empty range,
single and multiple entries, the odd-span arithmetic shift, the
negative-span arm, signed 32-bit boundaries, plain 64-bit fields, both
guarded arms (including the sentinel arm needing no field30), the
missing-field guard, and packet checks.
pytest is not installed on this VM, so the test file runs under plain
python3 via its `__main__` runner.
