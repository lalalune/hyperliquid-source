# RE-001: create-by-name from a registered factory (node #115)

## Bounded question

How does node #115 build a `Statistics` object when a caller asks for
one by name through a registered factory, and what do the registry find
(`0x6076620`), the translator (`0x6076b20`) and the `Status` builder
(`0x61cf670`) pin down about that path?

## Answer in one paragraph

The host (`0x6077820`, see #3386) dispatches on the name: an empty name
or `"BasicStatistics"` is constructed directly, while any other name
goes through the registry lookup `0x609e510` and then the translator
`0x6076b20`, which is the item pinned here. The translator calls the
registry find wrapper `0x6076620`, which walks the registry's entry
vector last-to-first, locks each entry's mutex, and searches that
entry's unordered_map for the type key `"Statistics"` (linear walk
while the element count is at most 20, hash-bucket walk otherwise,
`_Hash_bytes(key, 10, 0xc70f6907)`); the first `FactoryEntry` whose
pattern matches the name wins, recursing into the parent registry at
+0x60 when nothing matches. The translator then invokes the entry's
creator (`0x6071ba0` for `BasicStatistics`) with the name and a
`Statistics*` slot: a missing factory yields `Status` code 3
(`NotSupported`, "Could not load to Statistics"), a creator failure
yields code 4 (`InvalidArgument`) with the creator's error string or
the generic text, a creator that returns an object without installing
it yields code 4 "Cannot make a shared Statistics from unguarded
one" (and the returned object is *not* deleted on that path), and on
success a fresh 0x18-byte control block (`_Sp_counted_ptr<Statistics>`,
counts 0x100000001) is installed into the caller's `shared_ptr` slot
first, then the caller's old control is released. The `Status` builder
`0x61cf670` is the shared constructor behind all of this: a 16-byte
out struct `{code, subcode, severity, msg*}`, with the message being
`msg1` or `msg1 + ": " + msg2`, freeing any old message with
`delete[]`. It has 847 direct call sites across the node.

## Evidence

- `excerpts/` — 15 whole-function objdump excerpts, verbatim as
  objdump emitted them. Generated by `export_excerpts.py` with:
  `objdump -d --start-address=<start> --stop-address=<stop> work/hl-node-115.bin`
  (run from the repository root). The mnemonics in the excerpts —
  `endbr64` included — are genuine instructions present in the
  target binary, not placeholders. Three of the excerpts
  (`translator.txt`, `find_wrapper.txt`, `status_builder.txt`) are
  new in this packet; the other twelve are byte-identical re-ships
  from RE-001-basic-stats-factory-115 (#3386), verified with `cmp`.
- `records.json` — semantic records only: the translator/find/
  status-builder contracts, the hash vectors, the message strings
  with their `.rodata` addresses, the census counts and the open
  unknowns. No per-instruction mnemonic list.
- `vtables.tsv` — 31 rows: the `StatisticsImpl` slots pinned here
  (0x0 dtor, 0x8 deleting dtor, 0x98/0xa0/0xa8 locked read accessors,
  0xb0/0xb8/0xc0/0xd0/0xd8/0xe0 write side, 0xe8 `ToString`, 0xf0
  slot-0xf0) plus the four full small tables
  (`FactoryEntry<Statistics>`, `_Sp_counted_ptr<StatisticsImpl>`,
  `_Sp_counted_ptr<Statistics>`, `PatternEntry`). Every target is a
  `R_X86_64_RELATIVE` addend in `relocations.txt`: the
  `.data.rel.ro` bytes at these addresses are zero in the file,
  and the real pointer values are the relocation addends.
- `frames.txt` — the 15 FDE header lines from
  `readelf --debug-dump=frames-interp`.
- `relocations.txt` — the 55 relocation records for the packet's
  vtable slots (50) and typeinfo headers (5).
- `callers.tsv` — every direct call/jump/lea site for the packet's
  routines, with the enclosing FDE per site; generated by
  `census.py` from one objdump pass over the binary.
- `census.py` — the generator behind `callers.tsv`.
- `verify.py` — the packet checker (see below).

## Model and tests

`tools/registry_create_115.py` models the whole behaviour end to
end: `_Hash_bytes` (verified against the system libstdc++ on 21
vectors), the `Status` builder, pattern matching (`PatternEntry`,
`submatch`), the registry map (linear walk at most 20 elements,
hash-bucket walk above, prime-list rehash at load factor 1.0),
the registry find with parent recursion and last-to-first shadowing,
the `FactoryEntry` creator and the `std::function` manager, and
`create_by_name` — the translator — including the old-control
release on success, the slot-object disposal on the creator-failure
path, and the returned object *not* being deleted on the unguarded
path. `tests/test_registry_create_115.py` exercises all of it
(157 checks, run directly with `python3`).

## Checks

`verify.py` runs 11 checks: the artifact digest, MANIFEST coverage,
excerpt regeneration byte-for-byte, a raw-byte instruction check at
fixed and seeded-random spots (`random.seed(20261106)`), FDE
presence, relocation presence, literal read-back from `.rodata`,
census reproduction (re-runs `census.py` and requires
`callers.tsv` byte-identical), vtable re-derivation from
`relocations.txt` plus model constants, and the model tests.
Run it from the repository root:

    python3 research/work-items/RE-001-registry-create-115/verify.py

It prints `ALL CHECKS PASSED` on success.

## Environment limits

This packet was built on a VM with no cargo/rustc, no git-lfs and no
Ghidra/Java, so `make verify`, `make test` and `make catalogue-check`
cannot run here. The claims above are grounded in the materialized
node #115 binary (`work/hl-node-115.bin`, hash verified against
`provenance/artifacts.json`) and the system libstdc++ for the hash
ground truth; the binary checks that need a tooled environment are
left for maintainers.

## Open unknowns

- The Find pair `0x609e510` / `0x609a410` and the `=` parser
  `0x60c1190` (with sub-helpers `0x61d11f0` / `0x60b97f0` /
  `0x60c0e90`) — the host's first step for non-default names; a
  separate, larger item (transitive closure ~2000+ instructions).
- The fallback Find variant `0x609e2d0`, reached from the host when
  the translator returns code 0.
- The second word of registry vector entries (not read by the find
  wrapper).
- The runtime contents of the global string at `0x6508980`
  (`.bss`; initial bytes zero), set by static init.
- Creator-failure paths that never trigger for the
  `BasicStatistics` creator (it never returns null and never writes
  `err_string`).
- The host's caller at `0x60780d1` (FDE `0x60780a0..0x60781ab`) —
  which public entry calls the host.
- `find_norm` `0x609a410` callers: `0x609b190` (in FDE
  `0x609a740..0x609b6f3`), `0x609e5bf` and `0x609ea72` (both inside
  `find_entry` `0x609e510`).
