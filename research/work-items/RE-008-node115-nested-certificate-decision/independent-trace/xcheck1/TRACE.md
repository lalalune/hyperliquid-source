# 독립 정적 추적: 0x595fd20

## 대상 및 입력 해석

- 지정된 `hl-node`의 SHA-256은 `a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`로 일치한다. `readelf -wf`는 FDE 범위를 `0x595fd20..0x596000d`로 확인한다. 파일을 실행하거나 에뮬레이션하지 않고 `objdump -d -M intel`과 `readelf`로 분석했다.
- `SPEC.md`는 `a`~`e`를 10진수라고 설명하지만, 실제 입력에는 `ffffffffffffffff`, `7fffffffffffffff`, `8000000000000000`, `8000000000000001` 등이 들어 있다. 따라서 실제 파일의 `a`~`e`, `ctx_c`, `ctx_d`를 모두 **16진 u64**로 해석했다. 특히 `77`은 16진 `0x77`, 즉 10진 119로 처리했다. 이 진법 해석은 명세와 파일 간의 불일치를 해결하기 위한 가정이다. 출력 및 참조 레코드의 qword는 10진수이다.
- 모든 대소 비교는 부호 없는 64비트 비교이다. 검증기와 helper의 반환은 주어진 입력값을 사용한다. 반환 레코드 해제에 관해서는 아래의 한계를 적용했다.

## 분기 표

`P`는 `(a, b) == (ctx_c, ctx_d)`를 뜻한다. 표의 호출 횟수는 `(helper, validator)` 순서이다. `00`의 네 값은 판별자에 속한 확정된 필드이며, 나머지 물리적 복사 바이트의 한계는 아래에 따로 적었다.

| 조건 | 결과 및 호출 횟수 | 근거 명령 주소 |
|---|---|---|
| `!P`이고 `a <= ctx_c` | `00`, `a:b:ctx_c:ctx_d`, `(0, 0)` | `0x595fd34..0x595fd53`, `0x595fd6a..0x595fd92`, `0x595fef2..0x595ff64` |
| `!P`, `a > ctx_c`, validator가 `A` | `noreturn`, `(0, 1)` | `0x595fd8f..0x595fdb0`, `0x595ff78..0x595ffdb` |
| `!P`, `a > ctx_c`, validator가 `R` | 검증기 결과 정리가 정상 완료되면 `00`, `a:b:ctx_c:ctx_d`, `(0, 1)` | `0x595fd98..0x595fddf`, `0x595fec1..0x595fef2`, `0x595ff57..0x595ff64` |
| `P`, `c < b` | `05`, `-`, `(0, 0)` | `0x595fd55..0x595fd65` |
| `P`, `c == b`, `d != b` 또는 `e != b` 또는 `tail`에 0이 아닌 바이트가 있음 | `06`, `-`, `(0, 0)` | `0x595fde5..0x595fe63`, `0x595fea5` |
| `P`, `c == b`, `d == e == b`, `tail` 전부 0, helper `F` | `06`, `-`, `(1, 0)` | `0x595fe2c..0x595fe77`, `0x595fea5` |
| `P`, `c == b`, `d == e == b`, `tail` 전부 0, helper `T` | `2e`, `-`, `(1, 0)` | `0x595fe2c..0x595fe79` |
| `P`, `c > b`, `d < c`이고 `b <= e <= d` | 검증기 레코드의 태그, `fwd`, `(0, 1)` | `0x595fde5`, `0x595fe81..0x595fea0` |
| `P`, `c > b`, 위 전달 조건이 거짓 | `2d`, `c:d:e`, `(0, 0)` | `0x595fe81..0x595fe96`, `0x595fead..0x595febc` |

검증기 직접 전달은 검증기가 출력 포인터 `rbx`에 직접 쓰는 호출이다. 따라서 검증기의 결과가 `A`이면 태그는 `2e`이지만 `out_words`는 `fwd`다. 첫 번째 불일치 경로에서는 반대로 검증기의 거절 레코드를 정리하고 직접 만든 `00`을 반환한다. 검증기 수락 경로는 진단 호출 뒤 `ud2`가 있으므로 정상 복귀가 없다.

## helper 두 번째 인자

`0x595fdeb..0x595fe26`에서 104바이트 레코드를 구성하고 `0x595fe65..0x595fe70`에서 두 번째 인자로 전달한다. 오프셋 순서의 13개 qword는 다음과 같다.

```text
0:8:0:0:a:b:b:b:b:0:0:0:0
```

마지막 네 qword는 32바이트 0인 꼬리다. 원래 입력의 네 `head` qword를 이 참조 레코드에 복사하지 않는다. helper의 반환은 명세대로 제공된 `T`/`F`를 사용한다.

## 확신이 낮거나 입력만으로 결정되지 않는 부분

1. **`00` 레코드의 미초기화 복사 영역.** `0x595fd6a..0x595fd8e`는 임시 레코드의 태그와 `a`, `b`, `ctx_c`, `ctx_d`만 초기화한다. 이후 `0x595fef2..0x595ff64`는 이 네 qword 외에 초기화하지 않은 스택 `[rsp+0xa0]`, `[rsp+0xa8]`, `[rsp+0xb0]`, `[rsp+0xb8]`도 각각 출력 `+0x28`, `+0x30`, `+0x38`, `+0x40`에 복사한다. 태그 뒤 패딩 7바이트도 초기화하지 않는다. 입력만으로 이 물리적 바이트의 값을 계산할 수 없으므로, `outputs.tsv`의 직접 생성된 `00` 레코드 224건에는 확정된 네 qword만 기록했다. 따라서 이 열은 해당 경우 함수가 실제로 쓴 **모든** qword를 재현하지 못하며, 나머지 네 값은 0이라고 가정하지 않았다. 검증기 전달을 뜻하는 `fwd`는 이 224건에 포함되지 않는다.
2. **검증기 거절 레코드의 정리.** 불일치 후 검증기를 호출하는 경우, `0x10`, `0x13`, `0x20` 태그는 `0x595fec1..0x595feec`에서 페이로드 qword가 0이 아니면 추가 포인터를 읽어 해제한다. `0x10`은 추가 필드에 따라 두 번째 해제도 할 수 있다. `readelf -Wr`에서 해당 간접 호출 슬롯 `0x64df4a0`은 `0x635de30`을 가리키며, 그 코드는 할당자 정리 경로다. `R:태그:페이로드`에는 필요한 포인터나 할당 상태가 주어지지 않아 해제가 안전하게 완료되는지 결정할 수 없다. `outputs.tsv`는 유효한 레코드의 해제가 정상 완료된다고 가정한다. 입력 40건이 이 정리 경로에 걸린다. 잘못된 포인터 또는 할당 상태라면 그 행의 정상 복귀 여부는 보장되지 않는다.
3. **진법 불일치.** 위에서 설명한 16진 해석은 경계값 표기와 일관되지만, SPEC의 10진 설명과 충돌한다. 특히 `77` 같은 숫자만 있는 표기의 의도는 파일만으로 엄밀히 증명할 수 없다.

## 산출 및 확인

`python3 calculate_outputs.py`로 `inputs.tsv`의 순서에 맞춰 `outputs.tsv`를 생성했다. 입력 621건과 출력 621건의 ID 순서가 일치하며, 출력은 헤더 포함 622행이다. 호출 횟수는 helper 호출 31건, validator 호출 141건이며, 이 중 검증기 수락에 따른 비정상 복귀는 16건이다.
