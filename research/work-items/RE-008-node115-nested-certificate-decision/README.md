### The flow, in the order the native code runs it

`0x595fd20(out, cert, ctx)` first decides from words alone (A=cert+0x20, B=+0x28, C=ctx+0x50, D=ctx+0x58, f30/f38/f40=cert+0x30/+0x38/+0x40, unsigned): D1..D10 in `relations.tsv`. Only three arms reach deeper code:

| Decision arm | Calls | Result |
| --- | --- | --- |
| (A,B)=(C,D), f30 = B, f38 = f40 = B, 32 bytes at +0x48 zero | equality helper `0x4e08870(cert, reference)`, reference = empty signature collection (words `0, 8, 0, 0`) with the same pair and B,B,B | true: tag `0x2e`; false: tag `0x06` |
| (A,B)=(C,D), f30 > B and B ≤ f40 ≤ f38 < f30 | verifier `0x595f880(out, cert, ctx)` | its record is the output |
| (A,B)≠(C,D), A > C | verifier, result dropped unless tag `0x2e` | `0x2e`: no-return diagnostic ("observed qc for newer hardfork, crashing"); else tag `0x00` with A,B,C,D |

**Verifier `0x595f880`** (rows V1..V8), in this order, stopping at the first non-continue result; the native record is 0x48 bytes, the tag is byte 0:

1. Stake-set provider (slot `0x64e64b0` = RELATIVE `0x595e5c0`) with `(ctx, round = cert+0x40)`. Its tag writes are exactly two (`0x595e7e5`: `0x2e` with the set pointer; `0x595e7f5`: `0x28` with the round at +8), so the verifier sees only those. Tag `0x28`: record copied, stop. Inside the provider (rows PR3..PR6, `relations-provider.tsv`), with base = `state+0x20`, execution = `state+0x60`, counter = `state+0x68`: `limit = max(min(base+2000, MAX), min(execution+201, MAX))`; a round at or past the limit increments the counter (atomic, wrapping) and calls a log slot, and the query goes on (a warning is never a rejection); the lookup round is `q = base` while `r < min(base+2000, MAX)`, else `max(base, r-200)` (mod 2^64); the stake set is the stored one with the greatest round `<= q` (history tree or ring of 0x40-byte records, set at record `+8`), none gives `0x28`. Note that `q` is the base, not the round, in the usual case.
2. Signer collector `0x4e00160(set, cert)`: visits the certificate's signature collection (tree: key order; ring: from the head). Each 20-byte key must be in the stake map at `set+0` (tree when the first word is `0x8000000000000000`; else a ring of 32-byte rows searched by `0x57f54e0`). The first absent key gives tag `0x2c` with the key at +1; otherwise the key set is collected (sorted, a repeated key once, built by `0x53492e0`). A tree stake map with a null root fails at the first key.
3. Quorum (slot `0x64e8780` = RELATIVE `0x595bc40`) with `(ctx, set, key set)`: false gives tag `0x07`. `0x595bc40` calls the stake test (slot `0x64e6a98` = RELATIVE `0x4d3e1a0`: saturating stake sum of the signers found versus saturating total, `3 * signed > 2 * total` on 128 bits, equal fails); then reads the double at `ctx+0x88`: infinities and NaNs (either sign) give 1.0, otherwise `min(0.7, max(0.0, x))` with SSE operand order; a zero fraction (also `-0.0`) returns true without the count walk below (the stake test, which ran first, has already walked the signer set: Z2, F1); else it counts the signers found in the validator tree at `set+0x20` and returns `float(count) > fraction * float(set+0x30)` (u64 to f64 with one rounding, strict, an unordered compare is false).
4. For each signature entry in visiting order: a 0x5c-byte frame on the stack (the 32 bytes at `cert+0x48`, the words `cert+0x20/+0x28/+0x30/+0x38/+0x40`, then the signer address) and the message `{1, frame}`; signature check `0x57e8bd0(message, address, signature, set)` through slot `0x64e64b8`. The signature pointer is row `+0x18` for a ring row (V5r), but for a tree entry it is the value slot `leaf+8+72*i` that `0x513b200` returns in rdx next to the key address `leaf+0x320+20*i` (V5t, T1); an earlier text of this packet said `+0x18` for both. False gives tag `0x02` and stops (later entries are not checked).
5. All entries passed: tag `0x2e`. A certificate with no signatures never gets here: the collector succeeds with an empty set, the stake test fails (V9), tag `0x07`.

**Signature check `0x57e8bd0`**: the address must be in the stake map (tree walk or `0x57f54e0`), else false with no digest computed; then digest `0x57e8d40(message)` and recovery (slot `0x64e0ad8`) over (signature, digest); a recovery error result (its boxed error dropped through its vtable) is false; true iff the 20 recovered bytes equal the address.

**Equality helper `0x4e08870` and `0x4e550e0`**: unequal length words (`+0x18`) give false at once; otherwise a 9-word iterator state is built for each collection and `0x4e550e0` walks both in step: each pair must agree on the 20 key bytes and the 65 signature bytes (byte `0x40`, then bytes `0x00..0x3f` of the value), and both must end together.

### The digest side, round 4 (`relations-digest.tsv`, every row pinned like the others)

**The frame** (FB1). The verifier builds, per signature, 0x5c bytes at its stack pointer: the 32 bytes of `cert+0x48` at `+0x00`, the pair `cert+0x20/+0x28` at `+0x20`, `f30` at `+0x30`, `f38` at `+0x38`, `f40` at `+0x40` and the key address at `+0x48` (`0x595faeb: lea 0x48(%rsp),%r13`, the store at `0x595fba1`); the message is the two words `{1, pointer to the frame}` at `0xd0(%rsp)`. The signature check hands that message and a 32 byte output to `0x57e8d40` (S1).

**The digest `0x57e8d40(out, msg)`** (DB1..DB6): it copies the 29 bytes `Hyperliquid Consensus Payload` from rodata into a fresh buffer, serializes the message with `0x5823db0` (no size limit), joins the two with `0x5b3df10` (prefix first), runs the hasher over the joined bytes and returns its 32 bytes. The two timing calls at its start (`0x5c842e0`, `0x5c84210`) write into stack space that is zeroed before anything reads it, so elapsed time does not reach the hash. If the serializer reported an error the bytes to hash would be empty (DB4); with no limit it cannot, so this arm is not reached for this message.

**The serialization** (MS1, MS2, VS1, PV1..PV4, PA1, PA2). `0x5823db0` selects an arm by the message's first word through two jump tables (size pass `0x935c44`, write pass `0x935c58`); the size pass only sets the buffer's capacity. Arm 1 writes the byte `0x01` and calls `0x5966b90`, which writes, in this order: the 20 signer bytes (raw, no length), then the five words at frame `+0x20`, `+0x28`, `+0x30`, `+0x38`, `+0x40` as unsigned varints, then the 32 hash bytes (raw). Varint (the rule of `RE-005-varint-buffer-writer-115`, re-read here as PV1..PV4): below 251 one byte; below 2^16 `0xfb` and two bytes; below 2^32 `0xfc` and four; else `0xfd` and eight, little endian. The jump tables are those `RE-005-fixed20-record-encoder-115` found, and its arm (tag byte 2) is not read here. So

```text
preimage = "Hyperliquid Consensus Payload" || 01 || signer(20) || varint(A) || varint(B) || varint(C) || varint(D) || varint(E) || hash(32)
```

with A, B the certificate pair and C, D, E = f30, f38, f40. Only variant 1 was read here; the other four arms of `0x5823db0` write the tag bytes 0, 2, 3, 4 and call other writers (the arm with tag byte 2 is `RE-005-fixed20-record-encoder-115`'s; whether the others are covered elsewhere was not searched beyond the base tree's READMEs, which name `0x5823db0` only there).

**The hasher** (KU1, KF1; DB6, RC9): state of a 200 byte buffer, position, rate, delimiter and a mode byte; both callers build it with rate `0x88` = 136, delimiter 1, position 0 and output length 32: Keccak-256 with the original padding (delimiter `0x01`, not SHA3's `0x06`), over the permutation `0x5cda380`. Absorb and finalize behave as `evm-keccak-ripemd-hash-115` found.

**The recovery wrapper `0x1536a90(out, signature, digest)`** (RC1..RC9; slot `0x64e0ad8`): reads the 65 bytes as eight words and a byte; writes `r` and `s` byte reversed (so the 32 byte halves of the signature are little endian numbers); maps the last byte to a recovery id (RC2..RC5, as in `RE-010-gov-vote-path-115`; 2..26 and 29..34 give error kind 6 without any curve call); calls the compact-signature parse (slot `0x64df9d8` = `0x632b660`), the recovery (`0x64df9e0` = `0x632b7b0`), the uncompressed serialization (`0x64df9e8` = `0x632b480`, length 0x41, flags 2); any failure of the first two is error kind 3; the address is bytes 12..32 of the Keccak-256 of the serialized key without its first byte (as in `RE-005-node115-signer-result`); the tag byte is 0.

**The boundary that remains** (SP1, SS1, SR1): the three curve entry points. `0x632b660` has the three argument checks of libsecp256k1's `secp256k1_ecdsa_recoverable_signature_parse_compact` in the same order and with the same texts (`sig != NULL`, `input64 != NULL`, `recid >= 0 && recid <= 3`, data-pins.tsv), it calls `0x6321680`, which reads 32 big endian bytes into four limbs and tests them against the group order (immediates `0xbaaedce6af48a03b`, `0xbfd25e8cd0364140`; the 32 bytes of n are at `0x458060`), and the generator point is at `0xa182e0`. The node's own dependency census (`RE-002-node115-vendor-census`) says the build carries `secp256k1-sys` 0.10.0, which is that library. These are the bytes behind the name; the bodies (336, 416, 476 and 285 bytes at the entry points and the scalar reader, and everything they call: field and group arithmetic, the multiplication tables) are not read here. Hash-pinned: `secp_parse_compact`, `secp_recover`, `secp_serialize`, `secp_scalar_set_b32` in `functions.tsv`.

### Layouts the bodies read (observations)

- Signature collection at cert `+0x00..+0x20`: tree (first word `0x8000000000000000`; root `+8`, height `+0x10`, length `+0x18`; leaf: values 72 bytes apart from `+8`, keys 20 bytes apart from `+0x320`, u16 count at `+0x3fe`, edges from `+0x400`) or ring (capacity `+0`, buffer `+8`, head `+0x10`, length `+0x18`; 0x60-byte rows, key in the first 20 bytes, signature at row `+0x18`). The signature pointer the verifier hands on is therefore row `+0x18` in a ring, but the value slot `leaf+8+72*i` in a tree, not the key address `leaf+0x320+20*i` plus `0x18` (V5r, V5t, T1). Ring iterator: front slice from the head, back slice from the buffer start; length 0 gives empty slices whatever the capacity and head.
- Stake set: stake map at `+0` (tree: root `+8`, height `+0x10`, node keys from `+0x60`, u16 count at `+0x13e`, edges from `+0x140`, stakes from `+8`; ring: 32-byte rows, stake at row `+0x18`), validator key tree at `+0x20` (null root: nothing counted), the count word at `+0x30`.
- Collector error record: tag `0x2c` and 20 bytes at +1 (the rest of the 0x48 bytes is not written).

### What the reading shows (each is an observation from the pinned instructions)

- The only tags the verifier can leave are `0x28`, `0x2c`, `0x07`, `0x02` and `0x2e`. The cleanup arm of `0x595fd20` that frees a payload for tags `0x10`, `0x13`, `0x20` (round 1) can therefore not be reached with this verifier.
- The helper is called only with the synthesized empty reference, so the empty-shape route (`f30 = f38 = f40 = B`, zero 32 bytes) gives tag `0x2e` exactly when the certificate has no signatures. The verifier, in contrast, can never accept a certificate without signatures: with no signers the stake test `3 * 0 > 2 * total` is false, so a stake set that exists gives tag `0x07`.
- The per-signature message depends on all of `cert+0x20..+0x68` and the signer address; the verifier asks the provider about the round in `cert+0x40`, the same word the ordering test constrains.

### Inference and unresolved

- Inference: names such as stake set, quorum, signer, round and QC come from callers' neighbours and the diagnostic text, not from the bytes; the first pair word may be a hard-fork counter (diagnostic text only); `0x57f54e0` being `VecDeque::binary_search_by`, `0x513b200` being a B-tree `next`, `0x53492e0` being `BTreeSet::from_iter`, `0x4e44c00`/`0x4e406f0` being the selected/total folds, rest on the prior packets and the shapes seen at the call sites, not on a re-read of those bodies here. Round 3 re-read two small parts: the entry and return blocks of `0x513b200` (what it returns) and the start and empty-set exit of `0x4e44c00`; the descent through the tree and the summation loop were not.
- Unresolved: the curve routine under the recovery wrapper, the message variants other than 1, the bodies of the history search, the log slot `0x64e0b18` (its effect is not modelled), and what the callers of `0x595fd20` do with the 0x48-byte record.

## Independent traces (rounds 3 and 4)

`independent-trace/` holds two static traces by a second model (OpenAI GPT-6.1 via Codex CLI) given only inputs and the binary, without the Rust or expectations, a third by a Claude subagent for the digest side (round 4, last bullet), and a normalizing comparison script (`independent-trace/README.md` has the details and what they do not show).

- Run 1, the decision core: for the 621 inputs of `cases.tsv` (byte-identical to the round-1 file) the second model's outputs equal the expected values in tag, call counts and helper reference record 621 of 621, and in payload words 605 of 605 compared (16 rows where the target does not return are compared on everything but the payload; the Rust model carries the two pairs in `Output::Diverges`, the target writes nothing). `compare-result.txt`; the script's own negative controls reject 7 of 7 damages.
- Run 2, the new functions: traced from the bytes first, then compared with the round-2 `relations*.tsv`: the nine function ranges and hashes matched, 47 of 50 relation rows were marked as matching, and it reported three differences (one major): the signature pointer of tree entries in V5, the missing whole-verifier result for an empty collection in V7, and "without reading any signer" in Z2. All three were confirmed in the bytes and corrected in this packet (V5 became V5/V5r/V5t with T1, V7 was reworded with F1 and V9 added, Z2 was reworded). The first changed no expected value and no Rust logic: the corpora and the crate are value-level and already handed each entry its own signature; what the packet lacked was a test that would notice otherwise, now `cases-tree.tsv` and `tests/sigslot.rs`. The model's own first text had made the same ring-only generalization and it found the tree case while comparing with the packet, so this is a second reading that caught a text error, not a blind first derivation.
- Run 3 (round 4, digest side): a Claude subagent with a fresh context read `0x57e8d40` and `0x1536a90` from the bytes, was told not to read this packet or the crate, and was given only the frame layout and the callee addresses (from my reading) and five frames (rows of `cases-digest.tsv`). Its five preimages equal the corpus rows byte for byte and its recovery-wrapper table equals RC1..RC9 (`xcheck3/`). It is the same model family as I am, it saw the same disassembly, the structure was partly supplied, and five frames are a sample: a second reading, not a native run, and weaker evidence of independence than the Codex runs.

## Results and limitations

- Closed in Rust against pinned bytes and the frozen corpora: `0x595fd20`, `0x595f880`, `0x4e08870`, `0x4e550e0`, `0x4e00160`, `0x57e8bd0`, `0x595bc40`, the strict two-thirds test of `0x4d3e1a0`, the provider `0x595e5c0`, and (round 4) the digest builder `0x57e8d40` with the variant-1 serializer, the hasher `0x5cda910` / `0x5cdad40` and the recovery wrapper `0x1536a90` around an injected curve routine. Debug and release builds: 27 tests each, see the crate README.
- Round 4 closed the digest builder `0x57e8d40` for message variant 1 (encoding and hash) and the recovery wrapper `0x1536a90` down to its three calls into the curve library, in Rust, with the digest side's oracle frozen first. What this packet still does not establish about signatures, all of it:
  - **The curve routine is not reconstructed and not run.** `0x632b660`, `0x632b7b0`, `0x632b480` and everything under them (scalar and field arithmetic, group operations, tables) are an injected trait in the crate. They are named after argument-check texts, group constants and the dependency census, not proved to be the public library's compiled code. **No real signature is verified by anything here**: the tests give the curve stand-in a key the case names. No real signature, chain data or node key is in any file. One real public key is: the standard secp256k1 generator point G (the public key of private key 1; the generator `gen_digest_corpus.py` uses it for the address check `7e5f4552091a69125d5dfcb7b8c2659029395bdf` and for the `generator-key` row of `cases-recover.tsv`). That row still goes through the injected stand-in, which returns the key the row names; it checks the address derivation (Keccak-256 of the 64 key bytes, bytes 12..32), not a signature. All other keys in the corpora are arbitrary bytes.
  - Only message variant 1 was read; `NodePrimitives::digest` panics for another variant. The size pass `0x5966cd0` and the other four arms of `0x5823db0` are unread.
  - The hasher's squeezing mode and output lengths above the rate are not modelled (neither caller uses them); the permutation is hash-pinned and its body rests on the RE-009 packet and the public algorithm.
  - The digest and recovery rows were read once by me and once, partly structure-supplied, by a Claude subagent; there is no native differential run and no expected value from outside this reading except the public hash vectors.
  - How the node obtains the signatures, keys and stake sets it passes in, and what its callers do with a tag, are outside this work.
- Provider: modelled at value level. The atomic increment is a wrapping add on a `Cell` (no concurrency), the log call at `0x64e0b18` has no modelled effect, and the history search is restated from `RE-008-proposer-selection-115` (greatest stored round `<= q`), not re-read.
- Not re-read here, modelled by value from prior packets: `0x57f54e0` (ring search), `0x513b200` (tree `next`), `0x53492e0` (set build), `0x4e44c00`/`0x4e406f0` (selected/total folds; for ring stake maps via `node115-stake-predicate`, for tree stake maps in-crate, restated from `RE-008-quorum-count-fraction-115`), the history search `0x4dce480` with `0x51f5620`, `0x57f2b50`, `0x57f35c0`, the drop loops `0x51dc470` and `memcmp`. Their native structural edge cases (unsorted rings or trees, a head in `capacity..2*capacity`, length above capacity, a tree length word that disagrees with the tree) are outside the model, which uses `BTreeMap`/rows. The three ring constructors do not check the same things: `StakeMap::ring` (through `node115_stake_predicate::predicate`) and `Rounds::ring` refuse a bad shape (`len` above capacity, `head` not below capacity) and live rows that are not in key (round) order, because the native searches over those rings (`0x57f54e0`, the history search) are binary searches that need the order; `SigMap::ring` checks only the shape, because the native consumers of the signature ring iterate it and no order requirement is read from the bytes (`tests/sigslot.rs::ring_of_64_hands_every_row_its_own_signature_in_ring_order` walks one whose logical order is not sorted and expects acceptance). All three enums are public, so a caller can build the variant directly and skip the constructor: such a value may panic (a stake ring with `head` above capacity, a signature ring with rows empty and `len` non zero) or revisit rows (`len` above capacity); that use is outside the model.
- The expected values are my reading of the same disassembly restated in Python; `relations.tsv` lists path, condition and addresses so that someone can follow each by hand. A second model has read the same bytes independently for the decision core (all 621 inputs agree) and for the new functions' relation rows (three text errors found and fixed, see above); that is a second reader, not a native differential run, and two readers can share a slip (the second model's first text shared the V5 one). Its comparison used the round-2 tables; it has not seen the corrected ones. The 621 inputs of run 1 and the cases of the new corpus were chosen by me. No native differential run exists (none is allowed here).
- The no-return diagnostic is `Output::Diverges`, not an abort; the uninitialised bytes of the tag `0x00` and `0x2c` records, the unwind landing pads (11 in the decision, others in the callees) and the native frees are not represented.
- No progress gate is requested.
