# RE-001: map node #115 chain reset and dispatch 0x5d4dc00

Bounded question: what does the 336-byte routine at 0x5d4dc00 do
with its four arguments — which chain does it tear down, how does
it reset the fourth argument's struct, and when does it dispatch
through the second argument's vtable and the 0x5eeea60 callee?

## Answer, end to end

The routine takes four arguments: a first object in rdi, a second
object in rsi, a third value in rdx, and a fourth struct in rcx.
In instruction order:

1. Lookup: the third value is passed to the lookup callee
   0x5eee790 at 0x5d4dc23. Its return value is kept in r12 and
   tested for null only after steps 2–4, so the teardown, the
   reset and the virtual call below happen even on the
   zero-return paths.
2. Chain teardown: the chain head is read from the fourth struct
   at +0x10. While the current node is non-null, in order:
   (a) the value at node +0x18 is passed to the 0x5d4cfd0
   callee at 0x5d4dc38; (b) the string at node +0x40 is disposed
   by the SSO rule — its pointer field is compared against the
   address of the node's own +0x50 field, so an inline string
   frees nothing, while a heap string is deleted with
   (pointer, capacity + 1), capacity read from +0x50, at
   0x5d4dc56; (c) the same rule disposes the string at node
   +0x20 (capacity at +0x30) at 0x5d4dc70; (d) the node itself
   is deleted with size 0x60 (96) at 0x5d4dc7d. The next pointer
   (node +0x10) is read before any of the node's fields are
   deleted, so the walk survives each deletion. Neither string's
   size field (+0x48, +0x28) is ever read.
3. Struct reset: the fourth struct is reset with four writes —
   +0x10 = 0, +0x18 = the address of the struct's own +0x08
   field, +0x20 = that same address, +0x28 = 0. The struct's
   +0x08 field itself and its +0x00 field are never written.
4. Virtual produce: the second object's vtable slot 0x30 is
   called at 0x5d4dcb3 with the second object as argument. Its
   return value is kept in rbx; its +0x8d8 field supplies the
   first dispatch argument.
5. Gates: the routine returns 0 (at 0x5d4dd40) when the lookup
   result is null, or when the lookup result's +0x28 qword is
   zero. The first byte of the lookup result is then tested.
6. Dispatch: the dispatch callee 0x5eeea60 is always called
   with (produce result +0x8d8, lookup result, third value,
   fourth struct). When the lookup result's first byte is zero,
   the path is acquire → dispatch → release: the acquire callee
   0x606ca40 is called at 0x5d4dce0 with (saved first object
   + 0x700), then the dispatch at 0x5d4dcf5, then the release
   callee 0x60d52f0 at 0x5d4dcff with the same +0x700
   argument, and the dispatch return value is returned. When
   the first byte is nonzero, the routine tail-jumps to the
   dispatch callee at 0x5d4dd36 with the same arguments and
   no acquire or release call, so the dispatch return value is
   the routine's return value on both paths.

The routine's own transfers are exactly 8 direct calls (lookup,
dispose, three operator deletes, acquire, dispatch, release),
1 indirect call (vtable slot 0x30), 1 direct tail jump (the
flag-nonzero dispatch), and 1 landing-pad-stub tail jump: the
stub at 0x5d4dd44..0x5d4dd4f moves the incoming value to rbx
and jumps to the shared cleanup block at 0x5d4dbee, which calls
0x60d52f0 and then _Unwind_Resume. The cleanup block's semantics
are not claimed here; it is not a normal-flow exit.

## References

The routine is reached only through pointers: the executable
segment contains no direct call and no tail jump to 0x5d4dc00
(exhaustive E8/E9 scan, reproduced by census.py). Four
R_X86_64_RELATIVE slots in .data.rel.ro hold the address —
0x64c9538, 0x64cb2b0, 0x64cb790, 0x64cbd90 — all four at the
same position in four parallel pointer tables, with identical
neighbour addends (0x5d63c00, 0x5d2fb80 before; 0x5d2ed80,
0x5d63e20 after), read from the .rela.dyn entries. The raw
qword scan finds only the four addend fields in .rela.dyn
(file offsets 0x104308, 0x108910, 0x109780, 0x10a8f0), because
in this RELA binary the addend lives in the relocation entry,
not in the file bytes at the slot.

## Not claimed

What the callees 0x5eee790, 0x5d4cfd0, 0x606ca40, 0x5eeea60
and 0x60d52f0 compute — only their argument lists and call
order are pinned. What the second object's vtable slot 0x30
callee computes — only its argument list is pinned. What the
four arguments, the chain nodes, or the fourth struct denote
beyond the field offsets above. Behaviour on dangling or null
pointers other than the two pinned gates (the model raises on
null inputs, stated openly). Caller semantics beyond the
pointer-table census: no direct call site exists to describe.
