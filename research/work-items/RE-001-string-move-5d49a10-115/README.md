# RE-001: node #115 string move helper 0x5d49a10

Task ID: RE-001. Bounded question: what does the 216-byte helper at
0x5d49a10 do when it is given a destination string object and a
source string object?

## Layout

A string object is three fields: a pointer at +0x00, a size at
+0x08, and a capacity-or-inline slot at +0x10. The object is
inline (short-string optimization) exactly when its pointer
equals its own +0x10 address; otherwise the pointer names a
heap buffer whose usable length is capacity + 1 (the extra
byte holds the NUL). The helper takes the destination in rdi
and the source in rsi and returns nothing meaningful.

## Semantics (traced branch by branch from main.txt)

* Heap source (source pointer != source +0x10 address): the
  destination takes over the source's heap buffer, size, and
  capacity. The source is left empty, and how it is left
  empty depends on the destination it displaced:
  * destination was heap-allocated: the source takes the
    destination's old heap buffer and its capacity; that
    buffer keeps its bytes except byte 0, which is set to
    NUL; the source size becomes 0.
  * destination was inline, or its pointer was null: the
    source becomes an empty inline string -- its pointer
    becomes its own +0x10 address, its size becomes 0, and
    byte 0 of its inline buffer is set to NUL. The
    destination's old inline bytes are simply abandoned;
    nothing is freed for them, because inline storage needs
    no free.
* Inline source (source pointer == source +0x10 address):
  the destination keeps its own buffer and capacity, and
  the source's bytes are copied into it. An empty source
  writes only the NUL; a one-byte source takes the
  single-byte fast path (one load, one store) with the
  same effect; longer sources go through memcpy. The
  destination size becomes the source size, a NUL is
  written just past the copied bytes, and the source is
  left empty: size 0, byte 0 of its inline buffer NUL,
  pointer and capacity unchanged. The copy always fits a
  live destination: an inline source holds at most 15
  bytes, and every live destination buffer holds at
  least 16.
* Self move (destination is the source object): the
  string is emptied -- size 0 and byte 0 NUL, pointer and
  capacity unchanged -- except that a null pointer
  becomes the inline buffer address first. This is what
  the code does on every self path (heap and inline
  alike); it is recorded, not smoothed over.

The only library call in the routine is memcpy on the
inline-source copy path (plus the stack-canary failure
path, which never returns). Nothing is allocated or
freed by this routine itself: heap buffers only change
owners.

## Not claimed

What the strings denote, the semantics of the eleven
caller functions beyond their addresses and FDE
ranges, behavior on cyclic or dangling buffers, and
anything about the neighbouring routines (0x5d49a10's
callers include the large map routines at 0x5d4ed40
and 0x5d4f400, whose wider behavior is not mapped
here). The model raises on a null destination
pointer on the copy path and on a destination buffer
too small for the copy; the binary dereferences
unchecked there, but no live string hits either path.
