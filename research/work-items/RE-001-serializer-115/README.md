# RE-001: pin node #115 value serializer 0x60ba600: the 25 per-kind rules

## Bounded question

What are the serializer `0x60ba600`'s 25 per-kind rules -- the single
documented boundary of #3485 -- and how does each rule turn a
Find-pipeline value into its text form, end to end including the
decimal, escape, hex, double and enum-name helpers?

## Target

Node #115 binary `work/hl-node-115.bin`, SHA-256
`a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`
(`provenance/artifacts.json`, `artifacts/node/115/hl-node`).

## Evidence

  objdump emitted them. Generated by `export_excerpts.py` with:
  `objdump -d --start-address=<start> --stop-address=<stop> work/hl-node-115.bin`
  (run from the repository root). The mnemonics in the excerpts --
  `endbr64` included -- are genuine instructions present in the

- `frames.txt` -- the 10 FDE ranges for the excerpted routines.

- `relocations.txt` -- the one GOT record the packet touches:

- `verify.py` -- the independent checker (see Verification below).

  census and the excerpt regeneration.

## The serializer

`serialize(value_ptr, kind, out_string*) -> int`, FDE
`0x60ba600..0x60bb855` (0x1255 bytes). It dispatches on `kind`
(`esi`, 0..0x18) through the jump table at `0x978650` (25 int32
relative entries, 19 distinct targets); a kind above 0x18 falls
through to the return-0 path. On success it fills the out string
(`rdx`, saved in `rbx`) and returns 1; on an unhandled kind it
returns 0 with out untouched. A stack canary is checked on every
return (`__stack_chk_fail` at `0x60bb83c`).

The sole direct caller in the whole binary is the matcher
`0x60bb9a0` (site `0x60bbb97`, pinned by #3485): the Find pipeline
renders a matched value through this serializer. That closes the
#3485 boundary -- the serializer is the matcher's rendering step,
not a standalone utility.

## The 25 kind rules

| kind | value read | rule |
| ---- | ---------- | ---- |
| 0 | u8 | bool: nonzero -> `"true"` (`0x43f883`), zero -> `"false"` (`0x430e89`), via `_M_replace` into out |
| 1 | i32 | signed decimal via `int_to_string` `0x5f06bb0`, then `move_assign` |
| 2 | i32 | same helper, same value; behaviorally identical to kind 1 |
| 3 | i64 | signed decimal: absolute value, `'-'` fill, two-digit table loop |
| 4 | u32 | unsigned decimal, 32-bit divide-by-100 loop |
| 5 | u8 | signed decimal via `int_to_string` (zero-extended byte) |
| 6 | u32 | unsigned decimal, second copy of the kind-4 loop |
| 7 | u64 | unsigned decimal, 64-bit divide-by-100 loop |
| 8 | u64 | unsigned decimal, second copy of the kind-7 loop |
| 9 | (ptr, len) | backslash-escaped copy via `escape_copy` `0x61d0f30` |
| 10 | f64 | `"%f"` via `snprintf_string` `0x60ba450` (vsnprintf, 328-byte buffer) |
| 11 | u8 | enum name, map `0x65070a0` |
| 12 | u8 | enum name, map `0x6507060` |
| 13 | u8 | enum name, map `0x6507120` |
| 14 | u32 | enum name, map `0x6507020` (the one u32 key) |
| 15 | u8 | enum name, map `0x6507160` |
| 16 | u8 | enum name, map `0x65070e0` |
| 17-22 | -- | unhandled: return 0, out untouched |
| 23 | (ptr, len) | UPPERCASE hex via `hex_encode` `0x61c7e30` with flag 1 |
| 24 | u8 | enum name, map `0x6506fe0` |

## The decimal paths

The decimal kinds are the libstdc++ `__to_chars` shape: the digit
count is computed from magnitude thresholds (9, 0x63, 0x3e7, 0x270f,
0xf423f, 0x98967f, 0x5f5e0ff, 0x1869f, and 0x3b9ac9ff for the 32-bit
paths), the string is built filled with `'-'` (signed) or NUL
(unsigned), and the digits are written from the end two at a time
from a 200-byte two-digit table (`"00".."99"`). The table is
reloaded from the same 13 `.rodata` chunks at all 10 instantiation
sites in this packet (12 `movaps` at `rsp+0x30+16*i`, one `movups`
at `rsp+0xe9`); SHA-256 of the rebuilt 200 bytes is
`bedfbc17dfedc3a783c817da8b2eec13baff8e36c4e6a61c346332973895315a`
(verify.py rebuilds it from the binary). The model implements the
table loop literally instead of calling `str()` on the whole value.

Signed edge cases: the absolute value is taken in fixed-width
arithmetic, so `INT64_MIN` formats as `"-9223372036854775808"`
(magnitude 2^63) and `INT32_MIN` as `"-2147483648"` (magnitude
2^31). The unsigned paths compare with unsigned `jbe` and use
logical shifts, so they never take a sign branch.

## The escape helpers

`escape_copy` `0x61d0f30` walks the (ptr, len) value byte by byte.
`escape_predicate` `0x61d0e90` returns true only for `0x0a`, `0x0d`,
`'#'` (`0x23`), `':'` (`0x3a`) and `'\\'` (`0x5c`): the bit-test arm
uses mask `0x0200000000800001` (bits {0, 23, 57} over byte - 0x23),
and the `jg` after `cmp $0x5c` jumps to the plain `ret` (returning
0), so bytes above `0x5c` -- `0x5d..0x7f`, `0x80..0xff` -- and NUL
are copied raw. `escape_letter` `0x61d0f00` maps `0x0a -> 'n'`,
`0x0d -> 'r'`, anything else to the byte itself, so the escape is
`'\\' + letter`. This is the inverse of the escape decoder
`0x61d0ee0` pinned by #3560 (`'r' -> 13, 'n' -> 10`, else identity).

## The hex helpers

`hex_encode` `0x61c7e30` with the flag the serializer passes (1)
reserves `2*len` and writes two hex chars per byte via `hexchar`
`0x61c7da0`. `hexchar` adds `0x37` past 9, so 10..15 become
`'A'..'F'`: the encoding is UPPERCASE. With flag 0 the helper
replaces out with the raw input bytes instead -- modelled and
tested, never taken by the serializer.

## The double kind

`snprintf_string` `0x60ba450` calls the function pointer in GOT
`0x64ed730` -- `vsnprintf@GLIBC_2.2.5` -- with a 328-byte stack
buffer and the format `"%f"` (literal `0x432165`), then installs the
result in the out string (SSO or `_M_create` + `memcpy`). Every
finite double fits the buffer, so no truncation is modelled; the
model uses Python `"%f"`, the same C `%f` (six decimals, correctly
rounded).

## The enum kinds

The seven enum kinds inline the map walk: head list at map `+0x10`,
node `next +0x00`, name string `+0x08`, key `+0x28`; on a match the
name is `_M_assign`ed into out and the kind returns 1, on a miss it
returns 0 with out untouched. This is a plain linear head-list
walk -- it does NOT use the hash-bucket walk the #3560 parsers use
in the other direction (name -> value). The maps are the same seven
`.bss` globals #3560 binds (`0x6506fe0`, `0x6507020`, `0x6507060`,
`0x65070a0`, `0x65070e0`, `0x6507120`, `0x6507160`), runtime-built,
so the model takes them as harness-injected `EnumMap` objects.

## Helpers pinned by this item

`int_to_string` `0x5f06bb0` (signed i32 decimal, 13 callers),
`snprintf_string` `0x60ba450` (2 callers: the serializer's kind-10
arm and `0x610d430..0x610e33f`), `escape_copy` `0x61d0f30`
(3 callers), `escape_predicate` `0x61d0e90` (1 caller),
`escape_letter` `0x61d0f00` (1 caller), `hex_encode` `0x61c7e30`
(120 callers -- the most widely reused helper in this packet),
`hexchar` `0x61c7da0` (2 callers), `move_assign` `0x60b79e0`
(12 callers, re-shipped from #3488).

## Duplicated kinds

Kinds 1/2, 4/6 and 7/8 are separate code copies with identical
observable behaviour -- almost certainly distinct C++ types that
lower to the same decimal instantiation. The binary gives no gloss
for which types, so the model records the duplication faithfully
and does not name them.

## Verification

`python3 research/work-items/RE-001-serializer-115/verify.py`
prints ALL CHECKS PASSED: binary digest, manifest, excerpts
regenerated byte-for-byte from fresh objdump, every excerpt line's
raw bytes matched against the binary, 3 seeded random gate spots
verified against fresh objdump, all 10 FDE ranges in `frames.txt`,
the vsnprintf relocation, the three literals read back
(`"false"`, `"true"`, `"%f"`), the census reproduced byte-identical
(156 rows, per-target counts match), the jump table at `0x978650`
re-decoded to all 25 model targets, the 200-byte two-digit table
rebuilt from the 13 chunks with the recorded SHA-256, the escape
mask read back from the `movabs` immediate, and the model tests
(`tests/test_serializer_115.py`, 168 checks) passing.

VERIFY FIXES DURING THIS CYCLE (both caught before submitting):
(1) the first draft of the model said kind 23 was lowercase hex;
the tests failed 6 checks and re-reading `hexchar` showed the
`0x37` addend -- 10..15 map to `'A'..'F'`, so the encoding is
UPPERCASE; corrected the model, tests and records. (2) the first
draft of the digits-table check concatenated the 13 chunks
naively, which misplaces the last chunk -- it lands at `rsp+0xe9`,
not `rsp+0xf0`, so the table's last 8 bytes come from chunk 12
offsets 7..14; fixed the reconstruction to the true stack layout
and the overlap with chunk 11 now checks out.
