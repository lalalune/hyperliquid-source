## Bounded question

When the node serializes the `Ip` variant, exactly which bytes does
its dedicated writer add around the payload, when does it grow the
output buffer, and what happens when the payload write fails? The
routine 0x5a2ff40 answers all three: it frames the payload as
`{"Ip":<payload>}`, grows the buffer at five pinned points, and
propagates the payload writer's status. The framing, the growth
gates, the failure path, and all six call sites are pinned; the
payload writer's own body is not.

## Object layout (pinned by the disassembly)

- Output buffer: +0x00 capacity in bytes, +0x08 data pointer,
  +0x10 length in bytes. The routine reads all three fields and
  stores the length back after every append it performs itself.
- Context: rsi points at a context whose +0x00 word is the output
  buffer pointer. The same context pointer is forwarded to the
  payload writer; this routine reads no other context field.
- rdi is an opaque payload source: forwarded untouched to the
  payload writer and never dereferenced by this routine.

## Algorithm (verified against the excerpt)

Let B be the buffer at [rsi], with length L and capacity C:

1. Append `{`, then `"`, each inline: when L == C, first call the
   grow helper 0x5963a10 with (rdi = B, edx = 1, ecx = 1, r8d = 1),
   reload L, and write at B.data[L] without re-testing capacity.
2. Append the key through the append-bytes helper
   0x50a3510(B, 0x93a200, 2) — the two bytes `Ip` — and reload L.
3. Append `"` and `:` inline, under the same growth gate.
4. Call the payload writer 0x50a2ad0(rdi, rsi). It appends the
   payload into the same buffer; reload L.
5. If the payload status is nonzero, return it verbatim at once:
   no closing brace is appended, and the buffer keeps `{"Ip":`
   plus whatever partial payload the writer appended.
6. Otherwise append `}` inline under the same growth gate and
   return 0. The zero is saved in r14 (0x5a30099) and restored
   (0x5a300a1) across the closing-brace grow call, so the grow
   cannot clobber the success status.

The success byte sequence is exactly `{"Ip":<payload>}`.

## Consumers (the six transfer sites)

- 5 direct calls + 1 tail jump, in 5 caller FDEs: 0x50457f0
  (twice), 0x5072e50, 0x50df590, 0x50e9340, 0x5080db0 (tail jump;
  that caller's return value is this routine's).
- At 3 of the 6 sites the caller appends JSON punctuation to the
  same buffer immediately before the transfer (`[` written inline
  at 0x5045987 and 0x5045aa1, `:` at 0x5072eeb): the routine writes
  one member/element inside larger serializers, not a standalone
  document.
- At 0x5072f04 the payload pointer rdi is the caller's rbx
  advanced by one when the byte at [rbx] is nonzero — a leading
  tag byte is skipped before the payload source is handed over.

No open PR and no merged work-item names this routine's address;

## Unknowns

- The payload bytes and whether they are quoted: the payload
  writer's body is not pinned. Its head reads four bytes from rdi
  and formats decimal digits around `.` separators on its stack,
  consistent with a dotted-decimal IPv4 rendering, but this packet
  claims only the forwarding and status contract.
- The grow helper's capacity policy: only the call contract
  (invoked on length == capacity with arguments 1, 1, 1; the
  append then proceeds without a re-check) is pinned.
- The append-bytes helper's internal growth and failure behavior;
  the routine relies on it for the key and reloads the length
  afterwards.
- Whether the buffer length can ever exceed its capacity: the
  routine tests equality only, so the length <= capacity
  invariant is assumed, not enforced, in the observed code.
- The caller bodies beyond the three inspected argument setups,
  and the meaning of the tag byte skipped at the 0x5072f04 site.
- What the payload writer reads from the context beyond the
  buffer word at +0x00.

## Environment limits
