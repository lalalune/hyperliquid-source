## Bounded question

What does the routine at 0x606ca40 do when it acquires a lock: when is
the acquisition plain, when is it instrumented, and what observable
effects (timer reads, counter add, observe call) follow in each case?

## Semantics, in order

The routine takes one object pointer (rdi) and returns void. It
acquires the object's lock through the stub at 0x606ca00, which
tail-jumps to the pthread lock wrapper 0x60d5230 (mapped end to end
in PR #2588; the stub is referenced here, not re-claimed).

1. Opaque prologue: callee 0x606dd10 is called on every path. No new
   argument registers are set up before the call and its return value
   is never read.
2. Global gate: the qword at 0x64ed2b0 is tested on both paths; only
   when nonzero is the TLS perf-level accessor (PLT symbol
   `_ZTHN7rocksdb10perf_levelE`) called, and its return value is
   unused.
3. Gates. Let `gate = (object+0x30 != 0) AND (object+0x28 != null)`,
   `ctx_byte = byte at (object+0x28)+0x20`,
   `tls_flag = (byte at thread-pointer - 0x10b0 > 4, unsigned)`.
   The fast path runs when `gate AND ctx_byte > 4`. On the fallback
   path the context pointer and the gate flag are zeroed, so the
   observe step below can never run there.
4. Begin call: callee 0x5fe2680 is called with the stack record at
   rsp+0x10 (flag byte = tls_flag, one zero byte, type code =
   object+0x38 as an int) exactly when the fast path runs OR tls_flag
   is set. Otherwise the routine goes straight to the lock.
5. Timer path (only when the begin call ran AND the type code is
   0x34): the virtual slot 0xa0 of the TLS first-qword object is
   called, the lock is taken, and only when the first timer result is
   nonzero is slot 0xa0 called a second time. Elapsed = second -
   first. A zero first result skips the second call, the counter add
   and the observe call.
6. Counter add: when tls_flag is set and the first timer result is
   nonzero, the elapsed value is added to the qword at
   thread-pointer - 0x350 + 0x1b8.
7. Observe call: only on the fast path with a nonzero first timer
   result, the virtual slot 0xb0 of the context object is called
   with (context, type code, elapsed).
8. Plain lock: when the type code is not 0x34, or when no begin call
   ran, the routine locks through the stub and returns after the
   stack-canary check.
9. Cleanup: the landing pad at 0x606cc5e jumps to 0x606ca0a, which
   disposes the stack record through 0x606c94c only when the
   record+0x10 slot (the first timer result) is nonzero, then checks
   the canary and resumes unwinding. This is never a normal-flow exit.

The stack record's later fields (filled after the begin call) are:
+0x08 the TLS first qword, +0x10 zeroed then overwritten with the
first timer result in the timer path, +0x18 the counter address,
+0x20 the context pointer (zero on the fallback path).

## Results and limitations

The behavior above is pinned end to end: gates, call order, argument
lists, the timer pair, the counter add and the observe call, with
boundary cases at both `> 4` comparisons (4 falls back / does not
record, 5 does) and at the zero first-timer result. The model tests
cover the fast path, the fallback timer path, the direct-lock paths,
both boundaries, the global gate, and null-object / null-context
guards.

Unknowns (not claimed): what callees 0x606dd10 and 0x5fe2680 compute
internally; what the TLS structure and the counter denote beyond
their offsets; what the virtual slot 0xa0 timer and slot 0xb0 observe
callees compute; behaviour on dangling (non-null but invalid)
pointers. The model raises on a null object, stated openly.
