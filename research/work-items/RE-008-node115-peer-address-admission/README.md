# Node115 peer address lookup to listener admission

Scoped partial progress on issue #3926 and backlog HL115-010. This contribution joins the listener's existing address gate (#2628) through the wrapper's direct and lock-tracked paths (#3276) to the concrete owner-map lookup producing the packed result. It does not establish the producer or freshness of that map, the decoded identity's authentication, stale-update policy, or complete listener acceptance.

Target: Linux x86-64 node115 SHA-256 `a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`. Static Capstone 5.0.7 decoding retains five full FDEs (8,969 bytes, 1,769 instructions), 1,774 instruction/edge facts and 12 corruption controls. No captured code is executed or emulated. Original target and FDE/window checks are performed before controls; controls bypass global/window guards so the recorded obligations must reject them.

## Selected normal-return path

* Listener `0x2af8be0`: the exact four bytes `127.0.0.1` at continuation `+0xd0` take the bypass at `0x2af8e11..0x2af8e18`. For other IPv4 addresses, `0x2af8e39..0x2af8eab` packages owner pointer `+0x10`, a 20-byte key at stack `+0x5c8`, and the `server_listen_get_node_ip` label, then calls `0x29b4360`.
* Wrapper `0x29b4360`: when its control byte `+0x20` is zero it tail-calls `0x2a59160` at `0x29b43e9`. Its nonzero thread-local lock-tracking route calls the same producer at `0x29b4b5a` on the selected normal path. The 56-byte thread-local comparisons in #3276 concern that tracking route; a matching entry is not established to be an IP-result cache.
* Producer `0x2a59160`: dereferences the supplied owner and 20-byte key, acquires the lock at owner `+0x6a8`, and searches the owner map at `+0x6b0`. The ordinary ring route calls `0x57f8e00` for exact key lookup and checks its returned index against length; the tree route calls `0x4d38140`. Ring records have 20-byte key plus a four-byte value; the selected tree hit yields the corresponding four-byte value. The search helpers compare all 20 key bytes. Missing returns a low presence byte of zero; on a hit the value is shifted left eight and ORed with one before unlock/return. Inactive payload bits for missing results are not modeled.
* At `0x2af8eb3..0x2af8ebf`, the listener shifts the packed result right eight and requires both equality of the observed four-byte value and bit zero of the low byte. An absent key or mismatching IP reaches its rejection branch. This is a local admission observation, not proof of cryptographic authentication.

The loopback exception is exact, not the entire `127/8` range. For the selected call the key is carried within the decoded result: successful decode at `0x2af8d06` writes stack `+0x2c0`; the copy at `0x2af8dd7..0x2af8dec` transfers 0x140 bytes from stack `+0x310` to `+0x4a0`, making key stack `+0x5c8` correspond to decoded-result `+0x178`. The deeper decode and its source identity are explicitly not closed here. The map is supplied as already-populated logical state, rather than a supplied boolean or fabricated network lookup.

The Rust crate performs actual 20-byte keyed map lookup and the listener gate, preserving the native little-endian pack/shift relationship. Its four hand-derived test groups cover exact loopback versus other `127` addresses, absence, stale/mismatching values, all 20 key bytes and all four address bytes, and packed-byte boundaries. A match of a supplied map entry is not evidence that the map is current or authenticated. Valid ordered containers, standard memcmp/copy semantics, normal lock and helper returns, and no alias mutation are premises; physical representation, allocation, synchronization schedules, failure diagnostics, TLS initialization, and target runtime behavior remain outside scope.
