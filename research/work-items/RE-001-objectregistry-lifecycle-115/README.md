# RE-001: pin node #115 ObjectRegistry lifecycle end-to-end

Task ID: RE-001. Bounded question: how does the node #115
ObjectRegistry live and die — its control block, its 0xc0-byte
layout, construction from the default library plus the global
registrar map, AddLibrary registration, the singleton getter,
the clone that links its parent to the singleton, the TTL
registration, and the teardown order?

Target: `work/hl-node-115.bin`, node #115, SHA-256
`a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`
(the provenance entry in `provenance/artifacts.json`).

## What is pinned

- The ObjectRegistry control block (vtable `0x64d8f00`, typeinfo
  `St23_Sp_counted_ptr_inplaceIN7rocksdb14ObjectRegistryESaIvE...`,
  0xd0-byte make-shared block, fresh packed counts
  `0x100000001` from the global at `0x459b20`): D1 is a bare
  `ret` (the object lives inside the block), D0 and _M_destroy
  delete the 0xd0 block, _M_dispose destroys the registry in the
  order parent shared_ptr, map tree, names vector, libraries
  vector, and _M_get_deleter returns `this+0x10` for the
  `_Sp_make_shared_tag` typeinfo.
- The 0xc0-byte registry layout: libraries vector (+0x00),
  names vector (+0x18), `std::map<string, weak_ptr>` (+0x30,
  0x50-byte nodes), parent shared_ptr (+0x60), the mutex
  (+0x98). The 40 bytes at +0x70..0x98 are an open unknown:
  zeroed by the ctor and the clone, never read or written by any
  pinned routine, trivially destructible.
- The recursive map-node destroy (right child, weak_ptr release,
  string-key destroy, `operator delete(node, 0x50)`, left
  sibling), the lock_guard destructor (unlock + clear owns),
  the vector<shared_ptr> destroy, and
  `vector<shared_ptr>::_M_realloc_insert` (16-byte elements,
  doubling growth, copied control-block use-count bump via
  `lock addl $0x1,0x8(%rax)`).
- AddLibrary: -1 on an empty name or a null creator manager;
  otherwise append the name, build a 0x90-byte ObjectLibrary
  make-shared block, lock +0x98, append the library, unlock,
  invoke the creator with (new library, name), release the temp.
- The ctor: seed libraries[0] with the default library, then
  replay the global registrar map at `0x6509540` (0x48-byte
  nodes: next, name string, creator std::function) calling
  AddLibrary per node.
- The singleton getter: function-local static, guard byte
  `0x65090f8`, holder at `0x6509100`, returns the shared_ptr BY
  VALUE through a hidden out-pointer.
- The clone: a new registry whose +0x60 parent is the singleton.
- The TTL registration: a hardcoded "TTL" library appended ONLY
  to the libraries vector (not names), creator invoked with
  (new library, empty string).
- The static initializer that builds the registrar map (empty)
  and the three build-info globals (git SHA, git tag v8.1.1,
  build date 2023-04-06).

## Evidence

- `records.json` — semantic records only (layout, vtable map,
  caller lists, relocations, literals, open unknowns). No
  per-instruction mnemonic list: instruction-level detail lives
  only in the raw excerpts.
- `*.objdump.txt` — whole-function verbatim objdump excerpts,
  one per window (19 windows, including the four landing-pad
  FDEs: add-library, ctor, getter, clone). Regenerated by
  `export_excerpts.py` with the relative binary path
  `work/hl-node-115.bin`; the header line of each excerpt
  records that path.
- `frames.txt` — the FDE header lines for the 19 windows.
- `callers.tsv` — every direct call, tail jump and lea reference
  to the 15 pinned routines, with the smallest enclosing FDE.
- `relocations.txt` — the 20 RELATIVE records for the
  PatternEntry + ObjectRegistry control-block vtable region and
  the `_Sp_make_shared_tag` GOT slot.
- `census.py` — the census generator (one objdump pass over
  every executable LOAD, raw-binary qword scan, `readelf -r`).
- `export_excerpts.py`, `gen_records.py`, `verify.py` — the
  packet's own generators and checker.

The `.data.rel.ro` file bytes are all zero at the vtable
addresses: the authoritative vtable contents are the
`readelf -r` R_X86_64_RELATIVE addends, not the file bytes.
Mnemonics such as `endbr64` are genuine instructions present
in the target binary, not placeholders.

## Model and tests

`tools/objectregistry_lifecycle_115.py` models the lifecycle
(getter -> ctor seeding -> AddLibrary -> clone parent link ->
dispose order, map-node destroy, weak_ptr release, lock-guard
unlock). `tests/test_objectregistry_lifecycle_115.py` has 27
checks against target-grounded expectations. The map insert in
the model is a plain binary-tree insert: the binary uses
std::_Rb_tree with balancing, but the destroy order the model
exercises depends only on the node links. The TTL creator at
0x6208290 is a large unpinned function; the model takes it as
an opaque callable, exactly as the binary invokes it through
the std::function invoker.

## Environment limits

This VM has no cargo/rustc, no git-lfs, no Ghidra/Java, so the
repo's `make verify` / `make test` / `make catalogue-check`
gates (which need the Rust toolchain) were not run here; the

check that ran. The packet is evidence + a Python model, not a
Rust reconstruction, so it does not touch those gates.

## Open unknowns

- Registry +0x70..0x98 (40 bytes): zeroed, never touched by
  any pinned routine.
- The big registry method 0x5ff88c0..0x5ff9c50 (calls the
  getter and vec-insert, locks +0x98, builds PatternEntry
  objects): not fully read.
- The TTL creator 0x6208290..0x6208afa: cited by contract only.
- The clone's caller at 0x60bb8f0 (function 0x60bb890..0x60bb932)
  and the TTL lea site at 0x6202df2 (function
  0x6202da0..0x6202e78): identities not pinned.
- Which (name, creator) pairs populate the global registrar map
  at 0x6509540 before the first getter call: the map is empty
  after static init, and the populating static initializers are
  not pinned.
