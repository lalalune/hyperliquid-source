# risk: reconstruct the node #115 clearinghouse position ratio (0x446b840) with its two container searches

This packet makes it possible to re-implement, as a plain executable rule list, the whole clearinghouse routine at `0x446b840`: the position
lookup in a ring buffer or a B-tree, the side test, the margin-table row selected by `key % 10000`, the signed notional, the saturating
arithmetic, the two floored f64 ratios and the exact order of the opaque helper requests and panics. The rule list agrees with the real bytes of
the body and of both searches on 16,024 byte-built cases, and 147 negative controls (24 wrong readings of the rule list, 114 edited bytes, 9
structural controls) are all detected.

- Component ID: `risk` (Clearinghouses and risk). Task area RE-007 (reference `l1/clearinghouse/position.rs`), filed under the component ID.
- Target release and full SHA-256: Linux x86-64 node #115, `artifacts/node/115/hl-node`, `a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`.
- Source commit / reference commit: `0781ce04826eeefd89fe336cb8ea073be0c1de30` (repository head the packet was built on). No reference source was copied.
- Claim status: observation (bytes run in an evaluator, compared with an independently written rule list); inferences are marked as such.
- Scope included: the body `[0x446b840,0x446bc48)` (1,008 bytes, 243 instructions), the ring search `[0x455cb20,0x455cc3c)` (284 bytes, 90 instructions) and
  the B-tree search `[0x35be560,0x35be5f2)` (146 bytes, 39 instructions), each a whole FDE. Scope excluded: the five opaque helper slots
  (`0x64e6dc0`, `0x64e8ba8`, `0x64e6d20`, `0x64e4ea8` and the panic slots) which are recorded stubs, the callers of the body, and every
  other copy of the routine at `0x447e810`, `0x3bebd70` and `0x469b990` (different code, not claimed here).

## Reproduce

```
python3 tools/artifacts.py verify
python3 tools/risk_position_ratio115.py --out research/work-items/risk-position-ratio-115
python3 -m unittest tests.test_risk_position_ratio115
```

The tool reads only the ELF bytes through the repository parsers (`tools/elf_index.py`, `tools/fde_extents.py`), checks the binary SHA-256 first
and never executes the binary. It calls no external program. Two runs into different folders were compared with `diff -r` and are byte identical.
A full run takes about 55 s and a peak resident size of about 385 MB on one core. Every number in this folder is produced by the tool.

What the bytes do, in order (all of it observed by running the bytes and matched by the rule list):

1. The last stack argument points at a container header whose first word is a capacity. The value `0x8000000000000000` selects a B-tree
   (`root` at `+8`, `height` at `+0x10`) searched by `0x35be560`; any other value selects a ring buffer (`buf` `+8`, `head` `+0x10`, `len` `+0x18`) of
   72-byte entries (key, then a 64-byte record) searched by `0x455cb20`. The record is found by key; a miss, or an index at or past `len`,
   returns tag 0 and leaves every other output word untouched.
2. The record word at `+0x10` (the position size `v`) must be nonzero and `(v <= 0) xor (flag & 1)` must hold, else tag 0.
3. `key % 10000` (multiply by `0x346dc5d63886594b`, shift 75) indexes a table of 96-byte rows by the field at `+0x20`; an index at or past the row count
   calls the index panic with `oracle.rs:433:18`.
4. The row field must be non-negative as a signed word and its product with `v` must not overflow, else the `position.rs:204:57` panic. The
   magnitude of the product (the bit pattern `2^63` for the most negative product) goes to two opaque calls: the constructor (opaque argument and
   record word `+0x38`) and the step call.
5. If bit 0 of the record's first word is set, the margin figure is the product plus the record word `+8`, saturating, and the saturation callback is
   called twice when it saturates. Otherwise the figure is requested from slot `0x64e6d20` with the container header, `0`, `1`, the table and the
   opaque argument.
6. First ratio: `max(float(|product|) / float(figure), 1e-8)` if the figure is positive, else `1e-8`. The record word `+0x30` (`b`) must be non-negative
   (formatted panic otherwise). The second ratio takes `b` on the long side (`flag` byte nonzero) or `-b`, subtracts it from the product
   with a saturating subtraction (callback once; only the low end can saturate because the side test fixes the signs), and gives
   `max(float(max(difference, 0)) / float(b), 1e-8)`, or `1e-8` when `b == 0`. The output is tag 1, the product of both ratios, and the
   20 bytes of the caller block copied to `+0x10..+0x24`.

Analysis was complete for the three whole functions. Rows of the body not reached by any case: `0x446ba97..0x446baa0`, the branch taken only when the
second lookup of the same key fails after the first succeeded; the containers are not changed in between, so it cannot differ (inference).

## Implementation and comparison

`tools/risk_position_ratio115.py` holds (a) a small x86-64 evaluator over the ELF bytes (its instruction decoder, register and flag model are the ones of
the earlier byte-run tools; this packet adds the two-/three-operand `IMUL` overflow flags, which the earlier version did not model and which the
product overflow test of this body depends on), (b) the rule list `spec_run`, an independent pure function from a case (container, key, flag, table,
opaque words, helper answer) to the expected output bytes, helper request log or panic, and (c) the case generators, controls and renderers.
No Rust is claimed: the comparison is between the bytes and the Python rule list. The container searches run as real bytes; only the helper slots are stubs,
and each stub records its register arguments, which are compared with the rule list.

Cases (all built from the bytes' own field offsets, none copied from a trace): 52 named edge cases, 3,456 grid cases (container x tag bit x size sign
x flag x helper figure x `b` x stored sum x row field), 2,016 edge-grid cases around the saturating sum and difference, and 10,500 pseudo-random
vectors from a fixed generator. The generated files keep sampled digests only (data share is kept low on purpose).

Negative controls (147, all detected):

- 24 plausible wrong readings of the rule list (side test dropped or inverted, zero size allowed, modulus 9999, negative row treated as zero,
  no product overflow check, tag bit 1 instead of bit 0, no add or subtract saturation, figure always requested, inverted ratio, missing floors,
  non-strict positive test, swapped long/short sign, wrong constructor argument order, missing table argument, clamped index, ignored row count, `|difference|`, clamped high end);
- 114 single-byte edits (flipped condition, immediate or displacement) of every executed row of the three bodies, each run against a fixed mixed sample of several hundred cases;
- 9 structural controls (flipped file byte changes the SHA-256, four addresses refused as function starts, doubled floor, swapped `Location` records,
  an altered opaque argument).

Ten edited-byte survivors are listed in `mutations.tsv` with the reason each is equivalent (a guard whose flipped constant leaves the halving loop
unchanged, the unused insertion point of a missed ring search, the unused height word of the tree search, saturated figures that round to the same double,
the unreachable second-lookup test and a zero test reachable only with a nonzero word). Survivors are not counted as controls.

## Results and limitations

- 16,024 cases, 0 disagreements (outcome mix: 10,660 normal returns, 4,323 row-index panics, 940 size panics, 101 formatted panics).
- 147 negative controls, 147 detected. 30 unit tests, no skip.
- Limits: the five helper slots are not reconstructed (their answers are inputs); the units and names of the fields (`v`, `b`, row field) are not
  recovered, only their roles in this body; the three sibling bodies at `0x447e810`, `0x3bebd70`, `0x469b990` use the same record layout but different code
  and are not covered; the callers of `0x446b840` are not covered. No component gate is requested.
- Next question: slot `0x64e6d20` (the figure request, 36 call sites) with its constructor `0x64e6dc0`, which decides the `figure` input used here.
