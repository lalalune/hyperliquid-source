# RE-001: pin node #115 the named-enum registries

Task RE-001. Node #115 (`work/hl-node-115.bin`, SHA-256
`a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`).
This work item resolves #4237's first open unknown: the seven `.bss`
enum registries' name lists, which #4237 said were "not recoverable
from the static file". They are recoverable -- the string literals are
passed to string constructors inside the static initializer, and the
builder functions read the values back from the stack-built records.

## What is pinned

The static initializer `__static_initialization_and_destruction_0v`
(`0x60c78a0..0x60c870d`) builds twelve registries in `.bss`
(`0x6506fa0..0x6507260`, stride `0x40`) from stack-built record arrays
(49 string-ctor calls), invoked at load time through
`.init_array[96]` -> thunk `0x60c8710..0x60c8719` (`jmp 0x60c78a0`).

- Eight `std::unordered_map<std::string, unsigned char>` (name ->
  value): PrepopulateBlobCache, Temperature, CompactionStopStyle,
  CompactionPri, CompactionStyle, EncodingType, CompressionType,
  ChecksumType. Record = {std::string @ +0, u8 value @ +0x20}.
- Four `std::map<unsigned char, std::string>` (value -> name), each
  duplicating one unordered enum: Temperature, CompactionStopStyle,
  CompactionPri, CompactionStyle. Record = {u8 key @ +0, std::string
  @ +8}.
- All twelve destructors are registered with `__cxa_atexit` (dso
  `0x64efa20`); the twelfth is a tail jump, not a call.
- Parse: seven helpers (`0x60be160..0x60bea8b`) reached from the
  `fn-60bedc0` dispatch (jump table `0x9786b4`). Element count > 20
  takes the hash path (`_ZSt11_Hash_bytes`, seed `0xc70f6907`);
  otherwise a linear scan comparing size then `memcmp`. Every
  registry has at most 10 entries, so the linear path is live.
- Serialize: seven cases inside `fn-60ba600` (jump table `0x978650`),
  each a linear reverse scan of the element list with a shared
  `_M_assign` block at `0x60bab28`.
- Consumers shipped whole: the three-map serializer `0x60b50c0`,
  the CompressionType filter `0x5d85480`, and the ChecksumType
  serializer `0x60d8b10`.

## The CompressionType anomaly (recorded, not smoothed over)

As built, the registry maps `kZSTDNotFinalCompression` -> 64 (0x40)
and `kDisableCompressionOption` -> 255 (0xff). The upstream RocksDB
header says 8 and 64. The as-built reading is what the binary's own
code expects: the initializer writes `[0,1,2,3,4,5,6,7,0x40,0xff]`
into the records (0x08 is never written anywhere in `0x60c78a0`),
and the `0x5d85480` consumer keeps only values 1..254 -- a filter
that only makes sense if the disable sentinel is 0xff.

## Type 14 is a 4-byte field

The CompactionStopStyle parse helper (`0x60be7f0`) stores the hit
with a 32-bit `mov`, and its serialize case (`0x60bb180`) loads and
compares 4 bytes. The other six named-enum types store one byte.

## Not a consumer

`0x609fd10` (the dtor for the section-name strings) references
`0x6506fa0` only as a loop bound; it never reads the
PrepopulateBlobCache registry.

## Evidence

- `records.json`: semantic records only (registry tables, builder
  contracts, parse/serialize behaviour, consumers, atexit table,
  open unknowns). No per-instruction mnemonic list.
- `registries.tsv`: the census output (12 registries, 49 pairs).
- `*.objdump.txt`: verbatim whole-function excerpts, regenerated by
  `export_excerpts.py` with
  `objdump -d --start-address=<start> --stop-address=<stop>
  work/hl-node-115.bin` from the repo root. The initializer
  (`static-initializer-60c78a0`), `fn-60bedc0` and `fn-60ba600` are
  re-shipped byte-identical from #4237.
- `census.py`: layout-aware two-pass census of the initializer
  (tags resolved at block close; map tags at dest-8, unordered tags
  at dest+0x20). `gen_records.py` builds `records.json` from the
  census. `verify.py` re-runs everything and must print
  ALL CHECKS PASSED.
- `tools/enum_registries_115.py` + `tests/test_enum_registries_115.py`:
  the model and its tests (parse every name, reject unknowns,
  serialize every value, round-trip, the as-built CompressionType
  values).

Mnemonics such as `endbr64` in the excerpts are genuine instructions
present in the target binary, not placeholders.

## Environment limits

This VM has no cargo/rustc, no git-lfs and no Ghidra/Java, so
`make verify`, `make test` and `make catalogue-check` (which need the
Rust toolchain) cannot be run here. The packet's own `verify.py`
reproduces every claim it makes from the real binary instead.

## Verification portability

GNU objdump versions differ in whether they print the implicit DS and ES
segments for the observed `rep movsb` and `rep stos %eax` instructions. The
verifier accepts those two textual spellings while comparing every instruction
byte, address and other operand exactly. The retained raw exports preserve
the original spellings.
