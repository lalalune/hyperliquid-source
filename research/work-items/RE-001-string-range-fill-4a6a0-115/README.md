## Bounded question

What does the routine at 0x5d4a6a0 do to a libstdc++-layout string
object when given a byte range, and where is it used? It is the
range-fill step the census callers use to fill the string fields of
fresh objects: each caller sets the destination's data pointer to
the object's own inline buffer, then calls this routine once per
string field.

## Semantics

Object layout: +0x00 data pointer, +0x08 size, +0x10 capacity.
Arguments: rdi = destination object, rsi = range begin, rdx = range
end (exclusive); the length is end - begin, computed at 0x5d4a6a2.

### Short path (length at most 15)

The range is copied into the buffer the +0x00 pointer already names.
A one-byte range takes a single-byte copy at 0x5d4a6d7; any other
length takes memcpy at 0x5d4a729; the empty range copies nothing.
The +0x10 capacity field is not touched, and no allocation or free
runs. The observed callers satisfy the path's precondition: they set
+0x00 to the object's own inline buffer (destination + 0x10) before
calling, so a fresh object always has room for 15 bytes plus the
terminator.

### Long path (length at least 16)

The string _M_create PLT stub is called at 0x5d4a715 with the length
as the capacity variable and old capacity 0; the returned pointer is
stored to +0x00 and the updated capacity to +0x10, then memcpy at
0x5d4a729 copies the range into the new buffer. The previous +0x00
pointer is replaced with no free call in this routine, so a previous
heap buffer would be abandoned, not disposed; for the observed fresh
callers the replaced pointer is the inline buffer, which is the
normal SSO-to-heap transition. The exact capacity _M_create chooses
is not pinned by this excerpt, only that it is at least the length.

### Common tail

The length is stored to +0x08, a NUL byte is stored at
buffer + length (0x5d4a6e8), the stack canary is checked, and the
destination pointer is returned. The copy is by length throughout:
embedded NUL bytes in the range are copied, and the terminator is
always written one past the copied length.

## Consumers

79 direct call sites in 20 distinct caller functions (callers.tsv),
including the fresh-object constructors at 0x5d4aca0 (two string
fields of a 0x50-byte object) and 0x5d77260 (many string fields of a
large object). No tail jumps, no stored qwords, no RELATIVE
relocations: the routine is a plain direct-call helper.

## Unknowns

- The exact capacity _M_create chooses on the long path is not pinned
  by this routine's excerpt; only that it is at least the length.
- The libstdc++ name of this routine (a string range-fill step) is
  inference from its shape and its callers, not a pinned symbol; the
  pinned facts are the disassembly behavior and the call sites.
- Whether any caller reuses a non-fresh destination on the short
  path is not established by the census; the short path assumes a
  buffer of at least length + 1 bytes at +0x00, as the observed
  fresh-object callers provide.
