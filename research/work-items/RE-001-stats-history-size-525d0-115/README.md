## Bounded question

How many bytes does the node's in-memory stats history occupy? The
routine 0x5d525d0 answers that question for the database object's
stats history, and its single caller logs the answer before and
after trimming the oldest slices. Together the routine and its
consumer are one complete behavior — an estimate plus the trim
loop it drives — not a lone-window fragment: the routine's walk,
its arithmetic, both call sites, both log formats, and the erase
sequence are all pinned.

## Object layout (pinned by the disassembly)

- Database object: the history map header is embedded at +0xca8
  (color +0xca8, parent +0xcb0, leftmost +0xcb8, rightmost +0xcc0)
  with the slice count at +0xcc8. The routine reads only +0xcb8
  (the oldest slice node, i.e. the header's leftmost) and +0xcc8.
  The caller confirms the layout: it erases the node from
  [object + 0xcb8] with the header at object + 0xca8, increments
  +0xcc8 on insert, decrements it on erase, and tests
  [object + 0xcb8] against object + 0xca8 for emptiness.
- Outer node (0x58 bytes, the size the caller deletes with):
  RB node base +0x00..+0x1f, ordered key at +0x20 (compared
  unsigned by the caller's insert path, consistent with a
  timestamp key), an unpinned 8-byte field at +0x28, and an
  embedded RB-tree header at +0x30 (color +0x30, parent +0x38,
  leftmost +0x40, rightmost +0x48) with its entry count at +0x50.
  The caller's insert path initializes a fresh node exactly this
  way: +0x30 zero, +0x38 zero, +0x40 and +0x48 set to the node +
  0x30 address (empty-tree left/right point at the header),
  +0x50 zero.
- Inner entry: RB node base +0x00..+0x1f, key string at +0x20
  (data pointer +0x20, size +0x28, inline buffer / capacity
  +0x30). The routine reads only the data pointer and the +0x30
  slot.

## Algorithm (verified against the excerpt)

With C = slice count at +0xcc8 and H = oldest outer node at
+0xcb8:

1. C == 0 returns 48 (0x30), not zero.
2. Otherwise walk the embedded tree inside H only: first entry =
   [H + 0x40], stepping with the Rb_tree_increment PLT stub,
   stopping at the embedded header address H + 0x30. The walk
   never visits any other slice's entries.
3. Accumulator starts at 56 (0x38). Each visited entry adds 55
   (0x37) when its key string is SSO ([entry + 0x20] equals
   entry + 0x30), or its +0x30 capacity plus 40 (0x28) when it
   is heap-allocated.
4. Return C * accumulator.

The constants decompose as 55 = 40 + 15 (the SSO buffer holds at
most 15 bytes); that decomposition is inference, and the model
implements the constants. The multiply itself is pinned: the
estimate is the slice count times the oldest slice's walked
sum. The natural reading is a representative-slice estimate —
periodic snapshots are roughly equal in size, so one slice's
sum times the slice count approximates the total at the cost of
one walk instead of all — but the binary shows only the
arithmetic, so that reading is recorded under Unknowns, not
claimed.

## Consumer (the single calling function 0x5d88840..0x5d89173)

- First call at 0x5d88e74: the result is logged with the Pre-GC
  format (level 1, file `db/db_impl/db_impl.cc`) together with
  the slice count.
- Trim loop: while the estimate exceeds the caller's limit and
  slices remain, the caller erases the oldest outer node
  (Rb_tree_rebalance_for_erase with the node from [object +
  0xcb8] and the header at object + 0xca8, dispose of the
  node's +0x38 member through 0x5d4cba0, operator delete of
  the 0x58-byte node, decrement of the +0xcc8 count), then
  recomputes the estimate. It stops when the estimate falls to
  or under the limit or the count reaches zero.
- Second call at 0x5d88ef3: the recomputed estimate is logged
  with the Post-GC format. When the first estimate is already
  at or under the limit, the caller logs Post-GC without
  trimming.

## Unknowns

- Why the estimate multiplies the oldest slice's walked sum by
  the slice count instead of summing every slice's embedded
  tree; see the representative-slice reading above.
- The outer node's 8-byte field at +0x28; the routine never
  reads it.
- The inner entries' payload beyond the +0x20 key string; the
  routine reads only the key string's data pointer and +0x30
  slot.
- The caller's limit field and the calling function's identity
  beyond its two call sites, its log formats, and its erase
  sequence; its body is not pinned here.
- Whether 55 decomposes as 40 + 15; the binary shows only the
  constants 55 and 40.
