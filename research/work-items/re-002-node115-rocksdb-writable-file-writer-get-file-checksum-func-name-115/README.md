## Answer (pinned)

**Signature.** `const char* GetFileChecksumFuncName() const`; `this` in `rdi`, the result
pointer in `rax`. Unlike its sibling `GetFileChecksum` (which returns `std::string` by value
through a hidden sret out), this function returns a pointer: no sret out, no stack frame,
no canary. No LSDA, no `.cold` FDE. The `.eh_frame` record at section offset `0x367154`
has length `0x10`, range `0x28`, `aug_len` 0: no LSDA pointer, no landing pad.

**Dispatch.** Load `this+0xc8` (`checksum_generator_`, a `std::unique_ptr<FileChecksumGenerator>`
per `file/writable_file_writer.h:163`); if null, load the address of the `"Unknown"` literal
(`0x974e00` in `.rodata`, `kUnknownFileChecksumFuncName`, `include/rocksdb/file_checksum.h:25`)
into `rax` and return; else tail-jump to vtable slot 5 of the generator (`*0x28(%rax)`) with
(`generator`). Slot 5 is `Name`: `FileChecksumGenerator`'s virtuals occupy six vtable entries
in declaration order -- the two Itanium ABI destructor slots (complete-object dtor, deleting
dtor), then `Update`, `Finalize`, `GetChecksum`, `Name` (`include/rocksdb/file_checksum.h:52-67`)
-- so the sixth entry (`0x28` past the vptr) is `Name() const`, returning `const char*` (`:67`).
The 9 instructions (verified verbatim by `--live`):

```
endbr64
mov    rdi, [rdi+0xc8]           # checksum_generator_
test   rdi, rdi
je     0x604c7a0                 # null: return "Unknown"
mov    rax, [rdi]                # vptr
jmp    [rax+0x28]                # Name (vtable slot 5), tail jump
nop                              # 10-byte alignment padding inside the FDE
lea    rax, [rip-0x56d79a7]      # "Unknown" at 0x974e00
ret
```

The tail jump leaves no frame of this function on the stack, so `Name()` returns directly to
this function's caller, and a throw from `Name()` propagates with no cleanup of ours. The
concrete name string is the generator's own behavior (the CRC32C generator's `Name` is
reconstructed in the merged `RE-002-node115-file-checksum-name-115` packet), not this
function's; this model pins the dispatch, the null branch and the returned pointer only.

**Callers.** Exactly 3 direct calls and 3 tail jumps, 0 LEA refs (whole-`.text` E8/E9/LEA scan,
Capstone-validated). The three direct callers each `strlen()` the returned pointer and assign
it into a `std::string` -- `rocksdb::BuildTable` (site 0x5e1f508, stores it in
`meta->file_checksum_func_name`), `CompactionOutputs::WriterSyncClose` (site 0x5e189be),
`BlobLogWriter::AppendFooter` (site 0x5e27213). The three tail jumps are the table builders'
own `GetFileChecksumFuncName` wrappers, which load their writer, null-check it, and either
tail-jump here or return their own TU-local copy of the `"Unknown"` literal --
`BlockBasedTableBuilder` (site 0x60e2194, literal at `0x97a0b0`), `CuckooTableBuilder`
(site 0x615cb1d, literal at `0x97ba18`), `PlainTableBuilder` (site 0x618b340, literal at
`0x97be00`). The literal is `constexpr char[]` in a header, so each translation unit has its
own copy rather than sharing this function's `0x974e00`.

**Upstream cross-check.** RocksDB v8.1.1 (`meta/rocksdb`, read live this cycle) defines this helper
exactly as the binary behaves -- `file/writable_file_writer.cc:424-430` (`if (checksum_generator_
!= nullptr) return checksum_generator_->Name(); else return kUnknownFileChecksumFuncName`) --
`file/writable_file_writer.h:284` declares it as `const char* GetFileChecksumFuncName() const`, and
`db/builder.cc:335-336` stores the checksum in `meta->file_checksum` (via `GetFileChecksum`) and the
name in `meta->file_checksum_func_name` (via this function): the same `BuildTable` call sites the
census finds in the binary. `include/rocksdb/file_checksum.h:25` defines
`kUnknownFileChecksumFuncName` as `"Unknown"` and `:67` declares `Name()` as
`virtual const char* Name() const = 0`.

## Cases

## Environment limits

No cargo/rustc/git-lfs/Ghidra on this VM. The target binary is never executed. The tool models
the helper in Python from its whole-FDE disassembly; name strings are deterministic values,
not real generator names. `make verify/test/catalogue-check` in a tooled environment
is still owed upstream.
