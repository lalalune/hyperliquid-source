# RE-001: node #115 indexed call loop 0x5f6b520 with its sole caller site

## Task and bounded question

RE-001 (#115 function map, docs/TASKS.md: "Decode FDE ranges, account for
duplicates/missing functions, validate #115 entrypoints and xrefs with
digest-bound records"). Bounded question: what is the exact call
sequence of the small loop driver at 0x5f6b520 — how many times it
calls its callee, with what arguments, in what order, and when it
stops — given that its callee 0x5f6b000 is a large tangled function
that this item does not model.

This is a whole function, end to end — a complete behavior, not a
lone-window fragment: the driver plus its sole caller site (the one
place that invokes it) plus the exact call contract of its callee,
which is the driver's only observable effect.

## Windows

* Driver 0x5f6b520..0x5f6b581 (97 bytes, FDE range as shown in
  frames.txt). The whole window is the item. It contains no landing
  pads: the two `ret` instructions are the loop-exit epilogue
  (0x5f6b57d, reached after the loop) and the empty-count early
  return (0x5f6b580, reached before any register is pushed).
* Callee 0x5f6b000..0x5f6b516 (1302 bytes, FDE range as shown in
  frames.txt). Referenced window only: its semantics are NOT
  claimed. Its sole direct call site in the whole binary is the
  driver's loop site 0x5f6b565, so every invocation of the callee
  from this driver is accounted for by this item.
* Caller function 0x5d60580..0x5d60837 (FDE range as shown in
  frames.txt). Site only: its semantics are NOT claimed. Its call
  site 0x5d607a9 is the driver's sole direct call site in the whole
  binary. caller-site.txt is the verbatim site excerpt
  0x5d60780..0x5d607ae (argument setup plus the call itself), not
  the whole caller function.

## Semantics, stated literally

The driver takes (obj, a, b, c, flag) in (rdi, rsi, rdx, rcx, r8b)
and returns nothing.

* Count: signed 32-bit value at obj + 0x54, read at entry
  (0x5f6b524) and re-read after every callee call (0x5f6b56a).
* Empty arm: count <= 0 at entry returns at once (0x5f6b529 jumps
  to the early `ret` at 0x5f6b580). No callee call, no other field
  read, no register pushed.
* Otherwise the driver saves obj, a, b, c and the flag byte in
  callee-saved registers (rbp, r15, r14, r13, r12d — the flag is
  zero-extended from its low byte only, 0x5f6b53c, so upper bits
  of r8 are ignored) and loops with index ebx starting at 0:
  * Each iteration calls callee 0x5f6b000 at site 0x5f6b565 with
    (rdi = obj, rsi = a, rdx = b, rcx = c, r9d = flag,
    r8d = index). The same a, b, c and flag go to every call;
    only the index changes, in order 0, 1, 2, ....
  * After the call the index is already incremented (the add at
    0x5f6b562 runs before the call, after the index was copied
    to r8d), and the loop continues exactly while the re-read
    count is strictly greater than the incremented index, signed
    comparison (0x5f6b56a, 0x5f6b56d).
* Consequence, stated exactly: with a stable count N > 0 the
  driver makes exactly N calls, indices 0..N-1. Because the count
  is re-read after every call, a callee that raises the count
  extends the run (further indices are called) and a callee that
  lowers it to at most the next index ends the run early; the
  model reproduces this because the callee receives the mutable
  object.

## Caller site (site only, caller semantics NOT claimed)

* Sole direct call site of the driver: 0x5d607a9, inside function
  0x5d60580..0x5d60837. At the site the arguments are
  (rdi = qword at [r12 + 0x18], rsi = rbx, rdx = rbp + 0x838,
  rcx = r14, r8b = stack byte at rsp + 0x24).
* Site conditions visible in the excerpt: the call is reached
  only when the stack byte at rsp + 0x40 is zero (0x5d60780,
  jne skips the region) and the dword at [rbx + 0x28] is not 3
  (0x5d6078b, je skips the call). Nothing else about the caller
  function is claimed.

## What is NOT claimed

* The callee 0x5f6b000's semantics: what it does with its
  arguments, what it writes to obj, or why it might change the
  count. The model takes it as an oracle callable.
* The caller function's semantics beyond the site conditions
  above, and the meaning of its registers (r12, rbx, rbp, r14)
  beyond the argument values they supply at the site.
* Any meaning for the arguments a, b, c, the flag byte, or the
  count field beyond the loop bound they implement here.
* Any effect of the callee on obj fields other than the count at
  +0x54, which is the only field the driver re-reads.
