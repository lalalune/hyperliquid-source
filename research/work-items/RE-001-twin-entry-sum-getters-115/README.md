# RE-001: map node #115 twin entry-sum getters 0x5eec290 / 0x5eec300 with leaf 0x5dd3570

Bounded question: what do the two adjacent getters at 0x5eec290 and 0x5eec300
compute over the same entry range, and how do they differ?

Target: node #115 work binary `work/hl-node-115.bin`,
SHA-256 `a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`
(bound to provenance/artifacts.json for node #115).

## What is pinned

Both getters walk the same 16-byte entry range of the sub-object at
`[outer + 0x788] + 0x30`: begin `[sub + 0xb18]`, end `[sub + 0xb20]`.
For each entry, `E = [entry]` and `F = [E]`. The leaf at 0x5dd3570 returns
`[F + 0x10] + 62` (64-bit wrapping; `endbr64`, `mov 0x10(%rdi),%rax`,
`add $0x3e,%rax`, `ret` — genuine instructions in the target binary, not
placeholders; see the verbatim excerpts).

- Getter A (0x5eec290, 99 bytes): total = sum over entries of the leaf
  result; `*out = total`; return 1.
- Getter B (0x5eec300, 104 bytes): per entry it calls the same leaf, then
  DISCARDS the return — the very next instruction overwrites `%rax` with
  the entry pointer (`mov -0x10(%rbx),%rax` at 0x5eec347) — and adds
  `[E + 0x50]` instead; `*out = total`; return 1.

Both return 1 unconditionally, check nothing for null, and sum to 0 over an
empty range. The entry's second qword is never read. All arithmetic wraps
modulo 2**64.
