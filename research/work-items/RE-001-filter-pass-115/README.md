# RE-001: filter pass 0x5f6d700 (node #115)

Bounded question: for every element of every group, which elements
does the pass append to the scan list, and how does the scan list
grow when it outgrows its inline slots?

## What is pinned

The whole 839-byte pass 0x5f6d700..0x5f6da47, end to end — a complete
behavior, not a lone-window fragment: the group loop, the per-element
predicate consultation, and the scan-list append with its inline and
heap-growth arms. The predicate it consults is referenced, not
re-claimed (its own semantics are pinned by the RE-001 later-group
predicate item).

- Group loop: the iteration total is the cursor at obj+0x30 plus the
  heap group-slot count (obj+0xc8 minus obj+0xc0, shifted right by 4),
  recomputed from the object at every outer advance; a total of 0
  returns at once with no predicate call. Group i uses inline slot i
  in the array pointed to by the qword at obj+0xb8, at that base +
  i*16, when i <= 7 (unsigned), else heap slot i - 8 at the heap
  begin pointer (qword at obj+0xc0) + (i-8)*16. Each slot is 16 bytes:
  (limit, element base). The native code loads the qwords at obj+0xb8
  and obj+0xdb8 as base pointers (add 0xb8(%rbp),%rax at 0x5f6d7fd
  and add 0xdb8(%rbp),%rax at 0x5f6d835); those fields are pointers
  to the arrays, not inline storage at those offsets.
- Inner loop: inside group i the counter r12 starts at 0 and the
  element offset starts at 0; each consultation advances both
  (r12 += 1, offset += 0x50) whether the predicate returns true or
  false, and the loop continues while r12 < limit (unsigned), where
  limit is the group slot's first qword.
- Predicate arguments: the predicate is called with (obj, rsi, rdx,
  rcx = group index i, r8d = r12 when i == 0 else -1). The rsi record
  is (element+0x30, element+0x38 - 8 wrapping) and the rdx record is
  (element+0x40, element+0x48 - 8 wrapping), built on the stack from
  the 0x50-stride element at element base + r12*0x50. A
  predicate-true element is skipped with no record; a predicate-false
  element appends.
- Append: the record is (group index i as a 32-bit value,
  element+0x28), 16 bytes. While the scan count at obj+0xd30 is <= 7
  it goes to the first scan array, at the base pointer (qword at
  obj+0xdb8) + count*16; otherwise it goes to the
  heap vector (obj+0xdc0 begin / +0xdc8 end / +0xdd0 capacity end),
  growing it when end == capacity end: capacity 1 when empty, else
  twice the size, capped at 0x7ffffffffffffff records; growing at the
  maximum throws the native length error (rodata string at 0x43d55a);
  the old buffer is freed when non-null and the new begin, end and
  capacity end are stored.

Out of contract, stated honestly: the malformed-vector arm (heap
vector with 0 < end - begin < 16, i.e. size 0 but begin != end) cannot
occur for a well-formed 16-byte-record vector and does not follow the
grow path in the native code; the model raises ValueError for it
instead of reproducing it. Whether the predicate mutates the object
(the pass re-reads the heap vector and the cursor at every outer
advance) is not pinned; the model treats the group array as stable
across one call.

The model in tools/filter_pass_115.py takes predicate results as an
oracle callable, exactly the input the native loop consults, and tests
in tests/test_filter_pass_115.py cover the empty total, zero limits,
group-0 r8 sequencing, the always--1 r8 on later groups, the cursor
bound, the heap group slot, the -8 struct fields with wrapping, the
inline-to-heap scan transition with capacity evolution 1 then 2, a
20-record growth run to capacity 16, per-group r12 resets, the missing
element guard, the maximum-capacity length error, and packet checks.

## Evidence

All claims bind to one artifact: artifacts/node/115/hl-node, SHA-256
a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301
(the materialized work/hl-node-115.bin hashes exactly to this digest;
see provenance/artifacts.json). The packet holds semantic records only
(records.json); instruction-level detail lives only in the verbatim
whole-function disassembly excerpt in excerpts/, generated by
export_excerpts.py with this command:

    objdump -d --start-address=0x5f6d700 --stop-address=0x5f6da47 \
      work/hl-node-115.bin

Run verify.py from the clone root to re-check the digest, the manifest,
excerpt regeneration, gate instructions against the raw binary, FDE
ranges, the census, and the model tests. Instruction mnemonics in the
excerpt, such as `endbr64`, are genuine instructions present in the
target binary, not placeholders; verify.py checks the excerpt
byte-for-byte against a fresh objdump run and the gate instructions
byte-for-byte against the raw binary.
