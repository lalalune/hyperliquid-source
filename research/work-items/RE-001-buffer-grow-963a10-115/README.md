# RE-001: node #115 buffer growth routine 0x5963a10

- Component ID: RE-001 (node #115 function map)
- Target release and full SHA-256: node #115,
  `a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`
  (provenance/artifacts.json, `artifacts/node/115/hl-node`; local copy
  `work/hl-node-115.bin` hashes exactly)
- Source commit / reference commit: upstream main `05bc2de3`
- Claim status: observation for everything below except the items listed
  under Unknowns, which are inference boundaries, not claims.

## Bounded question

When a full buffer in the node has to grow, exactly what new
capacity does the shared growth routine 0x5963a10 choose, what
does it hand to its allocator callee, and what happens on each
failure path? The routine answers all three in 142 bytes: the new
capacity is `max(2 * capacity, length + additional, minimum)`
with a minimum set by the element size alone, the allocator
result decides between two stores and an error transfer, and both
failure paths leave through one shared entry. Callers across the
binary rely on the computed capacity without re-checking it —
the Ip variant JSON writer appends immediately after the call —
so this policy is the guarantee behind every such append.

## Object layout (pinned by the disassembly)

- Buffer descriptor (rdi): +0x00 capacity in elements, +0x08 data
  pointer. The routine reads both and, on success only, stores
  the new data pointer at +0x08 and the new capacity at +0x00.
- The descriptor's +0x10 length field is neither read nor written
  here: the current length arrives as the rsi argument. Callers
  keep their own length bookkeeping.
- rdx = additional elements requested. rcx is forwarded unchanged
  as the allocator callee's last argument. r8 = the element size
  in bytes: it drives the zero test and the minimum-capacity
  table below.

## Algorithm (verified against the excerpt)

Let C be the stored capacity, L the length argument, A the
additional count and S the element size:

1. If S == 0, transfer to the failure entry (step 5) with
   edi = 0. This test runs before any arithmetic.
2. needed = L + A; if the sum carries out of 64 bits, take the
   same failure transfer with edi = 0.
3. new = max(2 * C, needed, minimum(S)), all comparisons
   unsigned. The doubling is a bare `lea`: it wraps modulo 2^64
   with no check (C = 2^63 doubles to 0 and loses the max to the
   other terms; C = 2^64 - 1 doubles to 2^64 - 2 and wins it).
   minimum(S) is 8 for S == 1, 4 for 2 <= S <= 0x400,
   and 1 for S >= 0x401.
4. Call the allocator callee 0x5963650 with (&out, C, data
   pointer, new, forwarded rcx). It writes a 24-byte result on
   this routine's stack: tag dword at +0x00, a word at +0x08,
   a word at +0x10.
   - Tag == 1 (error): transfer to the failure entry with
     (rdi, rsi) = (result word +0x08, result word +0x10). The
     descriptor is not stored to: it keeps its old capacity and
     data pointer.
   - Any other tag (success): store the result word +0x08 as
     the descriptor's data pointer and new as its capacity,
     and return. The routine returns no value.
5. The failure entry is 0x141e264, reached through GOT slot
   0x64df498 on both failure paths. It does not return.

Unwind: the routine's FDE references CIE 0 (augmentation `zR`,
no personality) and its own augmentation length is 0, so the
routine has no LSDA and no landing pads: a raise out of the
allocator callee runs no cleanup in this frame, and the frame
holds nothing to clean. verify.py checks the augmentation bytes
directly in .eh_frame.

## Consumers (the 15,566 transfer sites)

- 15,566 direct calls in 3,647 caller FDEs spread across the
  binary (callers.tsv) — this is the node's shared buffer-growth
  step, reached from thousands of serializer and container
  bodies. No tail jumps, no stored pointers, no relocations:
  direct code transfer only.
- The inspected setup is the Ip variant JSON writer 0x5a2ff40
  (the RE-001 packet for 0x5a2ff40): five call sites pass
  (rdi = buffer, rsi = current length, edx = 1, ecx = 1,
  r8d = 1), each gated on length == capacity, and the writer
  appends at the reloaded length immediately afterwards without
  re-testing capacity. For a byte buffer at capacity 0 the
  formula gives max(0, 1, 8) = 8, so the first append lands in
  an 8-element allocation.

## Relations to other work

The Ip variant JSON writer packet (open PR #3326) cites this
routine by address and FDE at its five growth gates and pins
only the call contract there; its README lists the grow helper's
capacity policy as an explicit unknown. This packet answers
exactly that question — the policy, the allocator call and both
failure paths — and pins no byte of the writer itself. No merged
work-item and no other open PR names this routine's address as a
subject; the gossip variant writer packet (open PR #3308) and
the remaining sibling packets neither call it as a pinned subject
nor enter its body. The allocator callee and the failure entry
are cited by address and FDE only; their bodies are separate
questions.

## Unknowns

- The allocator callee 0x5963650's body: how it chooses between
  reallocating in place and moving, and what its result words
  mean on the error path beyond being handed verbatim to the
  failure entry.
- The shared failure entry 0x141e264's onward behavior: it is a
  21-byte dispatcher that selects one of two indirect calls by
  whether rdi is zero; neither onward target is followed here,
  and no panic message is claimed for either failure path.
- The meaning of the forwarded rcx argument beyond this routine:
  element size and alignment cannot be told apart from this
  body; at the byte-wise sites both candidate meanings are 1.
- The caller bodies beyond the Ip writer's five inspected sites:
  the census pins all 15,566 sites and their FDEs, but each caller's
  argument setup is that caller's own question.
- Whether any caller can pass a length above the descriptor's
  capacity: this routine trusts the rsi length argument; nothing
  here compares it with the stored capacity except through the
  max formula.

## Environment limits

This VM has no cargo/rustc and no Ghidra/Java, so no Rust
reconstruction is attempted; the work is the Python model and
tests plus the evidence packet, all verified against the
digest-matched node #115 binary. The allocator callee and the
failure entry are reached directly from this routine; their
bodies are not pinned, only the call sites and the contracts
this routine relies on.
