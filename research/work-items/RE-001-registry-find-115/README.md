# RE-001: pin node #115 registry Find: name normalization, the '=' options parser, the options-map merge and the delegate table search

## Bounded question

How does node #115 Find a component by name: the Find entry point
`0x609e510`, the normalizer `0x609a410`, the `=` options parser
`0x60c1190`, the options-map merge, and the delegate table search
(worker `0x6097630`, matcher `0x60bb9a0`, resolver `0x60971c0`) — and
what does each step pin down about that path?

## Answer in one paragraph

The host (`0x6077820`, see #3386) calls Find `0x609e510` as its first
step for non-default names, and this item pins the whole Find
pipeline. `find_entry` first handles the empty/default name (clear
the out-string, clear the map) and the null-delegate case (straight
to `find_norm`); otherwise it asks the delegate's slot-0x78 name and
runs `find_norm`, then — when Find normal succeeded — checks the
delegate name: a non-canonical slot-0x80 target is called as a
predicate, a canonical one (GOT `0x64eceb8` → `0x5d2e770`) is matched
against the slot-0x70/0x90 names, and on a match the register path
runs the delegate table search and merges its `name=value` pairs
into the real map insert-if-absent, swallowing worker and parser
errors. `find_norm` `0x609a410` normalizes the name: empty/default →
the fallback, no `=` → the name itself, `a=1;id=foo` → `"foo"` with
the `id` entry erased (and cleared again when it equals the default
name), a parser error → the name with the map cleared and the status
reset to success. The parser `0x60c1190` strips outer braces, then
loops over `key=value` pairs separated by `;` (delimiter set
`"={};"`, errors for an unexpected char, an empty key, or a missing
`=`, brace-group values via `0x60b97f0`, duplicate keys overwritten
through `operator[]` + `_M_assign`). The options map is a
libstdc++ `unordered_map<std::string, std::string>` with
before-begin bucket pointers, a linear walk at most 20 elements, a
hash-bucket walk above (`_Hash_bytes(key, len, 0xc70f6907)`), and a
prime-list rehash. The delegate table search walks the delegate's
0x30-byte elements and their node lists: the worker `0x6097630`
skips states 4/5 and `+0xd8 & 0x2000` nodes, runs a copy path when
the value is set and `0x100` is set, and a `0x6097ef8` path for kinds
0x15/0x16 (skipped unless the value's `+0x28` field is 2 or `0x8000`
is clear); the matcher `0x60bb9a0` dispatches on kind — 0x15 takes
the resolver path unconditionally, 0x16 takes the delegate-name
path (slot 0x78) when `0x8000` is set, `+0x28` is not 2, and `+0x04`
is clear or `0x100` is set (otherwise no match), and the resolver
path otherwise; both kinds follow a `0x800/0x400/0x200` flag chain
through one name-object link. The resolver `0x60971c0` returns the
name object's slot-0x60 string as-is, or `"{" + key + "}"` when it
contains `=`. The serializer `0x60ba600` is the single documented
boundary: its 25 per-kind rules are not modeled here. The fallback
variant `0x609e2d0` delegates through `0x6097150`/`0x6097110` or
reports code 4 `"Cannot configure null object "`. This closes the
open unknown #3386/#3440 left behind — the registry lookup
`0x609e510`/`0x609a410` bodies and the `=` parser — except for the
sibling entry point `0x609a740`, which stays open.

## Model and tests

`tools/registry_find_115.py` models the whole behaviour end to
end: `Status`, `_Hash_bytes` (MurmurHash64A, verified against the
system libstdc++ on the vectors in `records.json`), the options map
with faithful before-begin bucket semantics (insert after the
before-begin node, list head for an empty bucket, erase fixing
before-begin pointers, prime-list rehash regrouping same-bucket
nodes), the 0x50-byte value struct with its shared control, `trim`,
`value_extract` (brace groups, unbalanced braces, unexpected chars
after a nested group), `parse_options` (brace stripping, duplicate
keys overwritten), `find_norm` (including the swallowed parser
error and the `id` lookup/erase), the resolver, the matcher with
both kind paths (0x15 resolver, 0x16 delegate-name vs resolver with
the `0xb1`-flag gate and the `=` requirement, the one-link flag
chains, the chain-exhausted default-name outcome), the worker (copy
path, the `0x6097ef8` skip gate, first-match-wins, the `name=value`
accumulator with no `;` separator), the thunk, `find_entry`
(including the swallowed worker/parser errors and the
insert-if-absent merge), and the fallback variant.
`tests/test_registry_find_115.py` exercises all of it (576 checks,
run directly with `python3`).

Corrected semantics worth noting, each re-verified against the raw
excerpts this cycle: the worker's accumulator holds
`name=value` pairs with NO `;` separator (no `0x43d5c7` reference
exists in the worker); the register path parses the worker's
accumulated string, not the empty string, and both a worker error
and a parser failure on that path are swallowed; on the 0x16
resolver path the `0xb1` flag being SET disables the `=`
requirement (by zeroing the copy's `+0x04` byte), it does not
enable it — and because the resolver's result never contains `=`,
that path with `+0x04` set and the flag clear always clears the
value-out; the 0x16 delegate-name path runs when `+0x28` is NOT 2
(not when it is 2), and the worker's `0x6097ef8` path skips when
`+0x28` is not 2 AND `0x8000` is set.

## Open unknowns

- The sibling entry point `0x609a740..0x609b6f3` (4019 B; the third
  `find_norm` caller at `0x609b190`; takes 9+ args, copies the
  0x50-byte value struct, uses magic `0x692e` and a `"."` char,
  calls `0x61d1390`) — a separate entry point with different
  behavior, a future candidate.
- The global default name at `0x6508980` (a `std::string`; compared
  by length then memcmp in `find_entry` and `find_norm`): its
  runtime value is set by static init, and the initializer was not
  located. 11 lea reference sites, all readers. A `"default"`
  literal sits at `0x44371c` in `.rodata`, but no lea referencing
  it as this global's initializer was established. The model
  parameterizes `DEFAULT_NAME`, defaulting to `"default"` as the
  documented assumption.
- The delegate vtable base address: the delegate's vtable slots
  0x70/0x78/0x80/0x90 and the node+0x28 vtable slots 0x40/0x78 need
  a base, which was not pinned from locally retained evidence.
  Only the GOT/canonical entries are pinned (see `vtables.tsv`).
- The serializer `0x60ba600`'s per-kind serialization rules (25
  jump-table cases, 0..0x18): a documented boundary of this item,
  not modeled internally.
- The value struct's `+0x48` shared_ptr control vtable base for
  this item's value objects (the Statistics control vptr
  `0x64d2f00` was pinned in #3440 for Statistics objects only).
- Which construction paths install a non-null `+0x28` delegate
  (the value struct's delegate slot).
