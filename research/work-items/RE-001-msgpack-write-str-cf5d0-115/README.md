- Claim status: observation for everything below except the items listed

## Bounded question

When the node appends a string to its MessagePack output buffer,
exactly which header bytes does it emit for each string length,
in what order does it interleave those stores with buffer
growth, and how does the payload follow? The routine at
0x57cf5d0 answers all three in 650 bytes: the header form is
chosen from the length's low 32 bits (fixstr / str 8 / str 16 /
str 32), every store is preceded by its own capacity decision
that asks the shared growth routine for exactly the store's
size, and the payload lands as one memcpy. 903 call sites in
440 caller bodies rely on those bytes being exactly the
MessagePack str family encoding.

- Caller census: exactly 903 direct calls in 440 caller FDEs;

- Callee FDE range: frames.txt (routine FDE plus the growth
  routine it calls). The payload copy has no FDE here: it is the

  the relocation table (relocations.txt). verify.py checks the
  resolution.

## Object layout (pinned by the disassembly)

- Buffer descriptor (rdi): +0x00 capacity in bytes, +0x08 data
  pointer, +0x10 current length — the same triple the buffer
  growth routine 0x5963a10 serves. This routine reads all three
  fields and stores the running length at +0x10 after every
  step; it never stores the capacity or the data pointer (only
  the growth routine does that, on its success path).
- rsi = the payload bytes pointer. rdx = the payload length in
  bytes: the header decision reads only its low 32 bits (the
  compares are on %ebx/%ebp), while the payload capacity check
  and the memcpy count use the full 64-bit value in %rbx.

## Algorithm (verified against the excerpt)

Let L be the low 32 bits of the length argument and N the full
length:

1. Header form, decided on L alone:
   - L < 0x20: one byte, `0xa0 | L` (fixstr).
   - L < 0x100: byte `0xd9` (str 8), then L as one byte.
   - L < 0x10000: byte `0xda` (str 16), then L as a two-byte
     big-endian store (a `rol $8` on the low word).
   - otherwise: byte `0xdb` (str 32), then L as a four-byte
     big-endian store (a `bswap`).
2. Append protocol, applied to every store below: before a
   store of n bytes the routine computes the remaining
   capacity (capacity - length); when it is below n it calls
   the growth routine 0x5963a10 with (descriptor, current
   length, additional = n, rcx = 1, r8 = 1), reloads the data
   pointer and the length, and stores without re-checking —
   the growth policy is trusted to leave at least length + n
   (the buffer growth packet pins that it does).
3. Header stores: the marker byte is a 1-byte store (for
   fixstr it is the whole header). The length bytes follow as
   one store of 1, 2 or 4 bytes, so a buffer that is full at
   the marker grows by 1, and can grow again by 2 or 4 in
   front of the length store when the first growth left less
   than the length store needs.
4. Payload: one capacity decision for the whole string — when
   N exceeds the remaining capacity, one growth call with
   additional = N (the full length, not the shortfall). Then a
   single memcpy of N bytes through slot 0x64df508 to
   data + length, and length += N. A zero-length payload takes
   neither the growth call nor the memcpy.
5. The single exit stores the constant pair rax = 2, rdx = 0
   and returns. There is no other exit and no error path in
   the body.

Unwind: the routine's FDE references CIE 0 (augmentation `zR`,
no personality) and its own augmentation length is 0, so the
routine has no LSDA and no landing pads; a raise out of the
growth routine or out of memcpy runs no cleanup in this frame.
verify.py checks the augmentation bytes directly in .eh_frame.

## Consumers (the 903 transfer sites)

- 903 direct calls in 440 caller FDEs across the binary
  (callers.tsv) — the serializer bodies that write strings
  into MessagePack output. No tail jumps, no stored pointers,
  no relocations: direct code transfer only.
- The inspected setup is the wrapper at FDE
  0x57c1130..0x57c1196, whose call site 0x57c1179 passes
  (rdi = the caller-supplied buffer, rsi = a bytes pointer its
  own callee just produced, rdx = the wrapper's length
  argument) and overwrites rax immediately afterwards: at
  least this consumer ignores the return pair entirely and
  treats the write as infallible, consistent with the absence
  of any error path in the body.

## Relations to other work

The buffer growth packet (RE-001, routine 0x5963a10) pins the
growth routine this writer calls at eight sites; it names its
callers only as a census and does not enter this body. The Ip
variant JSON writer packet (open PR #3326) and the gossip
variant writer packet (open PR #3308) pin the JSON counterparts
that share the same buffer descriptor and growth routine; this
packet is the MessagePack counterpart and pins no byte of
either. No merged work-item and no other open PR names this
routine's address as a subject: it appears in the merged tree
only as a raw call target inside RE-002 consumer dumps
(RE-002-node115-bit9-arms, RE-002-node115-cache-readback),
which record the call sites without naming or pinning the
body. The binary carries two further FDEs whose instruction
streams are identical to this one after normalizing embedded
addresses (0x159f9c0 and 0x25e8bf0, each 650 bytes, each
calling its own neighbourhood's growth routine); they are
separate copies of the same source routine in other parts of
the binary and are recorded here, not pinned — this packet's
claims cover the 0x57cf5d0 copy and its 903 sites.

## Unknowns

- The type-level meaning of the constant return pair (2, 0):
  the body stores it on its only exit and the one inspected
  consumer ignores it, but which enum or result type it
  encodes is the callers' ABI question, not determinable from
  this body.
- Whether any caller can pass a length whose low 32 bits
  misstate the payload: the header decision trusts the low
  word while the copy uses the full length; real string
  lengths come from the callers' own buffers, and auditing
  all 440 caller bodies is out of scope here.
- The caller bodies beyond the one inspected wrapper: the
  census pins all 903 sites and their FDEs, but each caller's
  argument setup (which string, which length) is that
  caller's own question.
- The two instruction-identical copies at 0x159f9c0 and
  0x25e8bf0: their caller sets and any divergence in their
  growth routines are separate questions.
