# RE-001-node115-shortstring-intern-cid-key: what does 0x1546aa0 return for a name longer than 16 bytes, and how does the CID row builder use it?

- Component ID: foundation utilities (`base/src/short_string.rs`) and the CID rows built in `base/src/cid.rs`; bounded static work under RE-001 FDE records. No reconstruction gate is requested and none is claimed.
- Target release and full SHA-256: node #115, `artifacts/node/115/hl-node`, `a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`.
- Source commit / reference commit: repository `a8616af9432b8d8517b2af677880e117b7c28ef3`. No public source copied; the SipHash-1-3 in the generator and in the crate is written from the published algorithm.
- Claim status: observation (bytes, windows below) and inference (named as such). Static reconstruction only; the target was never executed or emulated.
- Scope included: the entry `0x1546aa0` (FDE `[0x1546aa0,0x15472aa)`) for names of 17 bytes or more: map lookup, the ten-letter generator `0x155ced0`, the size limit and the insert; and the consumer `0x155cd10` as far as the order of the key call and the parser call and the row layout.
- Scope excluded: the 89-byte fold `0x15472b0` (prior packet), the map's hasher and probing (`0x156b770`, `0x156b8d0`, a hashbrown-shaped table), locking and the one-time initialisation gate, allocation and unwinding, the iterator `0x153b6d0`, the 20-byte parser `0x150d640`, and the three other callers of the entry.
- Rust: [`src/node115-shortstring-intern`](../../../src/node115-shortstring-intern/README.md) (cross-reference; this packet is its evidence).

## Evidence

Coordinates are ELF virtual addresses, ends exclusive; `.text` file offset = VA − `0x1000`. Extents used: entry `[0x1546aa0,0x15472aa)`, generator `[0x155ced0,0x155d10e)`, SipHash write `[0x15709f0,0x1570bc7)`, map hashers `[0x156b770,0x156b8d0)` and `[0x156b8d0,0x156ba3b)`, consumer `[0x155cd10,0x155cec7)`, vector grow `[0x14cac50,0x14cacde)`. Analysis used GNU `objdump -d -M intel` and was complete for the entry, the generator, the consumer and `0x15709f0`; `0x156b770` was read to `0x156b867` (its SipHash setup and first rounds) and `0x156b8d0`, `0x14cac50`, `0x153b6d0` and `0x1557260` were not read. The cited bytes are held as windows in `verify_target.py` and compared with the ELF (`verification.json`). Window ids are in `code font`.

1. **Short names bypass everything.** `cmp rsi,0x10; jbe` (`entry_len_gate`), then `xor edx,edx` and a tail `jmp [0x64e0fe0]` (`entry_short_tail`); the slot is an `R_X86_64_RELATIVE` whose addend is `0x15472b0`. The length is bytes. (Prior packet's caller note; tie-checked here.)
2. **Lookup.** The map's item-count word at `0x64f00d0` is compared with 0 first (`entry_empty_map_skip`: zero skips the probe). The name is hashed by `0x156b770(&hasher, ptr, len)` (`entry_map_hash`). A probe compares the stored length (`[bucket-0x20]`) first, then the bytes through an imported compare called with the stored pointer (`[bucket-0x28]`) (`entry_probe_compare`). A hit returns the two words at `[bucket-0x10]`, `[bucket-8]` (`entry_hit_value_load`, `entry_return`). Buckets are `0x30` bytes: a 24-byte string (capacity, pointer, length), 8 bytes of padding, then the `u128` (the insert stores below write them at `-0x30`, `-0x20`, `-0x10`, `-8`).
3. **Miss: generate, then fold.** The range `0..10` is built as the 64-bit immediate `0xa00000000` (`entry_miss_range_and_call`: low dword 0, high dword 10) and `0x155ced0(&(range, &(ptr,len)), &vec)` is called. A guard `cmp rsi,0x10; ja 0x1547205` on the produced length (`entry_after_generate`) leads to the panic edge the loc-edge packet maps; ten bytes never take it. Then the same fold slot as in 1 runs on the produced bytes with `edx = 0`.
4. **The generator** (`0x155ced0`), per index `i`: set a zero-key SipHash state (`gen_sip_init`, `gen_zero_state`: four immediates stored at `rsp+0x20,0x28,0x30,0x38` in the order v0, v2, v1, v3; key and counters zero), `write(name)`, `write([0xff])`, `write(i as 4 bytes)` through three calls to `0x15709f0` (`gen_writes`: the index is stored with a 32-bit `mov [rsp+8],ebp` and the length argument is `edx = 4`). The finish is inline: `b = (length << 56) | tail` (`gen_finish_prefix`), one round, `v0 ^= b`, `v2 ^= 0xff` (`gen_v0_and_v2_xor`), three more rounds, `v0^v1^v2^v3` (`gen_final_xor`); the four `rol …,0xd` of the rounds sit at `0x155cfce`, `0x155d005`, `0x155d035`, `0x155d065` (`rol13_sites_in_generator`), one before the `xor` window and three after. That is SipHash-1-3 with an all-zero key. The letter is `'A' + hash % 26`, the remainder by the reciprocal `0x4ec4ec4ec4ec4ec5` and a shift of 3 after the high multiply (`gen_mod26`, `gen_letter`; only the low byte of the quotient is used, which is enough because the remainder is below 26). The constant is `ceil(2^67/26)` and its error is below `2^3`, so it is exact for every `u64`. The loop jumps back to the state initialisation for each index (`gen_loop_back`). **Index width differs from the scouting note**: SCOUT.md says `i.to_le_bytes()`; the bytes write 4 bytes (`i32`), and the corpus and the crate use 4.
5. **`0x15709f0` is a streaming `write`**: it adds the length to `[rdi+0x30]` (`sip_write_length_add`), runs one round per eight-byte block (`sip_write_block_loop`), and commits the tail word and its byte count to `[rdi+0x38]`, `[rdi+0x40]` (`sip_write_tail_commit`). Struct base `rsp+0x20` + `0x30` / `0x38` are the fields the inline finish reads (`rsp+0x50`, `rsp+0x58`).
6. **When a name is stored.** After the generator, the item count at `0x64f00d0` is read (`entry_items_read`) and compared: `cmp r15,0x1869f; ja` skips the store (`entry_cap_test`), so a new name is stored only while the map holds at most 99,999 entries and the map stops at 100,000. The same word is the one incremented on insert (`entry_items_increment`) and tested for zero (`entry_empty_map_skip`): `item_count_refs` shows all three operands resolve to `0x64f00d0`. The test happens before the write lock is taken, so with concurrent callers the limit is not strict (not modelled).
7. **Insert.** Under the write lock the name is copied: allocate `len` bytes and copy from the original pointer saved at `[rsp+8]` (`entry_key_copy`; the stored key is the caller's name, not the generated letters), the string `{cap = len, ptr, len}` is built (`entry_new_key_string`), hashed again by `0x156b8d0` (`entry_recheck_hash`) and probed again. If it is now present the two value words are overwritten and the copy freed (`entry_update_existing`); otherwise a bucket is written (`entry_insert_stores`), after a grow call (`0x15471cf`, slot `0x64e0ff8` → `0x1557260`, not read) when the free-slot word at `0x64f00c8` is zero. Either way the returned value is the one just computed.
8. **Consumer.** `0x155cd10` loops over an iterator (`0x153b6d0`), reads a `(ptr,len)` pair at element `+0` and another at `+0xb0`/`+0xb8` (`cons_item_fields`), calls the entry through GOT slot `0x64dff40` (relocation addend `0x1546aa0`; `cons_entry_call`), then calls slot `0x64e0b88` (addend `0x150d640`) with the second pair (`cons_after_key`). A result tag byte of 1 goes to a `Result::unwrap()` failure whose 43-byte message is at `0x46787b` (`unwrap_message_data`, `cons_unwrap_msg_lea`); otherwise the key words are stored at row `-0x10`/`-8`, the 20 parsed bytes at row `+0` (16 + 4) and the row advances by `0x30` (`cons_row_store`). So per item the key call comes first and the parser second.
9. **Other users of the entry (raw scan, upper bound).** `call [0x64dff40]` occurs at `0x14aec3f`, `0x155cdab` (the consumer), `0x15932a3`, `0x4526eb1` (`raw_call_slot_sites_of_entry`); `0x4526eb1` is already in the two bridge records named in the credit table. Each of the other three passes a `(ptr,len)` taken from a just-built value and stores the `u128`; what those strings are was not traced.
10. `verification.json`: 36 windows (867 bytes), 6 call-target decodes, 4 slot calls checked against relocations, 23 ties (13 against crate constants, 10 labelled `window_fact:` that compare windows with each other or with a literal), a raw `E8` scan of 3 targets; controls: 6,936 bit flips, 10 crate-constant perturbations, 6 call-target flips, 4 slot flips and 3 off-by-one scan targets, all detected. This checks bytes and immediates, not instruction semantics.

### Inferences (not proven by the bytes)

- The map is a hash map from the name to the `u128`, probed hashbrown-style (control bytes, 16-byte groups, 7-bit tag from the top of the hash) with a keyed hasher whose key words sit next to the lock; `0x156b770` is SipHash-1-3 keyed from the 16 bytes at its first argument (setup and first rounds read), so the placement is not reproducible across runs (the key words are filled at run time; not traced). The model uses a standard `HashMap`; only membership and size matter here.
- The lock at `0x64f00b0` is a reader/writer lock (the lock packets above cite `parking_lot.rs` for its release slow path; the reader step `0x10` and writer value `8` are my reading of the `lock cmpxchg` / `lock xadd` operands), and the dword test of `0x64f00e8` before each use looks like a one-time initialisation gate. Neither is modelled; their slow-path targets were not read.
- Because the generator is deterministic and the stored value is its result, a hit returns what a regeneration would: the map changes cost, not the key. That is an inference from the code shape; the Rust model reports `Path` only to make the branch visible.
- `0x15709f0` implements the usual concatenation-equivalent streaming write; read by eye and byte-pinned, not proven by an independent derivation. The crate tests chunked writes against the corpus as the Rust-side check.
- The generated letters have no collision handling in the code read: the scouting note's remark (no evidence of a check) holds. The key is ten capital letters, a space of 26^10 values, so keys are **not** unique in general, and the model has a concrete collision: the 17-byte name `abcdefghijklmnopq` generates `XGOKOCQCLX`, so its key equals the key of the 10-byte name `XGOKOCQCLX` (`0x584c4351434f4b4f4758`; corpus line `COLLIDE`, checked by the crate test). Two long names that share their first 16 bytes are hashed over the whole name and usually, but not necessarily, get different keys. The corpus also records that the first 20,000 fill names gave 20,000 distinct keys and that 24 one-byte edits of one name gave distinct keys; those are samples of this function, not guarantees. This is a result of the model on corpus inputs, not an observation of the node.

## Implementation and comparison

`src/node115-shortstring-intern/lib.rs` (std only, no dependencies, own `Cargo.lock`): `SipHasher13` (zero key, streaming), `generated_name`, `fold_le_u128`, `KeyCache::key_for(&str) -> Keyed { key, path }` (short / hit / miss stored / miss not stored), and `build_rows` (key first, then a caller-supplied parser, a parse error stops the build; the failing item's key call has already run, so its long name is in the cache only if that call stored it).

The oracle (`gen_oracle.py`, 337-line corpus) is a hand-coded SipHash plus a dict cache, a different representation from the crate (big-integer arithmetic, one-shot hash, dict instead of streaming and `HashMap`). It is **not** an independent reading of the bytes: the same author read the same disassembly for both. What is independent is the hash itself: the generator refuses to write a line unless its SipHash reproduces the published SipHash-2-4 vector through the same round code, the three scouting values, and CPython's C `siphash13` (`PYTHONHASHSEED=0`) on 21,957 messages (the one skipped is `hash(b"") == 0` by definition). `ORACLE_FROZEN.txt` records hashes and an author-reported UTC time and that the crate directory did not exist at the freeze. Post-freeze changes: in the first round none to `gen_oracle.py` or `corpus.txt`; the crate was written afterwards and the corpus replay passed on its first run; the only test edits before that run were corrections of two entry counts I had miscounted (262 `KEY` lines, 47 cache probes). In the second round (review of the first draft) the generator was changed after the freeze: one more `KEY` name (`XGOKOCQCLX`, now 263 lines), one `COLLIDE` line (the 17-byte `abcdefghijklmnopq` and the 10-byte `XGOKOCQCLX` share one key), a header comment, and the scenario id `cap-fail-after-insert` renamed `cap-last-slot-then-fail` (corpus 334 -> 337 lines; every other line unchanged, checked by diff against the first-round corpus). The collision pair is the one the reviewer found in the model's own scouting values; it is not fitted to a failing test. `ORACLE_FROZEN.txt` keeps the round-1 hashes and adds the round-2 ones. `verify_target.py` was extended after the freeze (SipHash `write` windows) and does not read the corpus.

Mutation (`mutate.py`): 25 single-text edits to `lib.rs`, each in its own copy, built (`--no-run`, a build failure exits 2) and run separately; the baseline must pass 9 of 9 first. Edits: short cutoff 16→`<`/17, terminator `0x00`, index as 8 bytes / big-endian / from 1, alphabet 25 / lowercase base / last letter missing, fold big-endian / overflow check dropped, SipHash rounds 2+3 and 1+4, length byte dropped, finalisation constant `0xfe`, swapped init words, big-endian tail / block, size limit one more / one fewer, short names stored, never a hit, map keyed by the letters, parser before key, error index off by one.

## Results and limitations

- 9 tests, debug and release: SipHash lines (48) through whole, byte-by-byte and nine split points each; 263 name-to-key lines and their letters, and the `COLLIDE` pair; 47 cache probes around the 99,999/100,000 limit built by real `key_for` calls (fills of 0, 1, 99,997, 99,998, 99,999, 100,000, 100,003); 10 row scenarios (key-before-parser order, parse error at first/middle item, cache at the limit); the three scouting values; and small direct tests. `ok` means the crate agrees with the oracle on these inputs; it is not a comparison with the node.
- The limit scenarios (fills of up to 100,003 distinct long names) are function-level inputs: they are built with real `key_for` calls, but nothing here shows that the CID path, or any caller, can reach 100,000 distinct names, or which name lengths the callers pass at all.
- The row scenarios use a stand-in parser (40 chars of `[0-9a-f]`), not `0x150d640`; its real grammar is unknown here. The key call happens first, so the long name's key is computed before the parser runs. Whether that name is then in the map depends on the map, not on the parser: it is stored only if the key call stored it (a miss while the map held at most 99,999 entries; a name already present is a hit). With the map full (100,000) a miss is not stored, whether or not the parse then fails. In the corpus, `cap-last-slot-then-fail` (named `cap-fail-after-insert` in the first draft) starts with 99,999 entries: item 0 (`A`, parses) takes the last free slot, then item 1 (`B`, a miss with the map now full) fails to parse; the build stops with 100,000 entries and `B` is not among them. `cap-full` (100,000 entries, items that parse) shows nothing is stored at the limit. The failing item is not the one that took the slot. The row where the failing item's own name is stored is `fail-middle` and its relatives (small maps).
- Not established: what the iterator order is, what the other three callers of the entry pass, the lock and initialisation behaviour, the map's growth and unwinding, and whether concurrent callers can exceed the 100,000 limit.
- No execution of the target, no emulation, no network. No equivalence with the node is claimed.
