# RE-001: map node #94 status formatter 0x542f8a0

Task: RE-001 (#94 function map). Bounded question: given a status record
(code byte, subcode byte, nullable message string), what exact string does
node #94's formatter produce, and which consumer uses it?

- Component: node #94 status formatter, window `0x542f8a0..0x542fe90`.
- Target release and full SHA-256: node #94, `work/hl-node-94.bin`,
  `3b7179cd967d1b13b683e05debfc685ad4c750e918226402d5d575eff1c0459f`.
- Claim status: observation for the code/subcode tables, the assembly
  order, the caller census, and the replay-loop consumer; inference for
  the "status record" naming (the struct fields are pinned, the name is
  the reading); unresolved for subcode values above 15 and for status
  bytes +2..+7.
- Scope included: the whole formatter function, its jump table, both
  string tables, and the replay-loop call site. Scope excluded: the
  behavior of the other 177 callers, the internals of `_M_append` /
  `_M_create` beyond their append contract, and the detail builder
  `0x542f040` beyond the record it fills for the replay loop.

## Answer

`format_status(out, status)` writes one string into `out` and returns `out`:

- Code 0 writes `OK` and returns. Subcode and message are never read on
  this path.
- Codes 1..15 write their fixed prefix (table below), then the suffix rule.
- Any other code byte writes `Unknown code(<code>): ` (via `__snprintf_chk`
  into a 30-byte stack buffer; the longest rendering, `Unknown code(255): `,
  is 19 characters), then the same suffix rule.
- Suffix rule: if subcode is 0, append the message directly when it is
  non-null. If subcode is nonzero, append the subcode name, then append
  `: ` and the message when the message is non-null. When the message is
  null, the result ends after the prefix (plus the subcode name when
  subcode is nonzero); no separator is appended.
- Every append checks the remaining room against `0x3fffffffffffffff` and
  throws `length_error` past it. That throw is recorded, not modeled as an
  output: no real message comes near the cap.
- The finished local string is move-assigned into `out`. Prefixes of
  length 15 or less are built in the local string's inline buffer, longer
  ones through `_M_create`; the output string is identical either way.

The status record layout, as read here: code `u8` at +0, subcode `u8` at
+1, message `*const char` (nullable) at +8. Bytes +2..+7 are never read
by this function; their roles are not claimed.

## Consumer (pinned, not census)

The WAL replay loop `0x520ad30..0x520c053` calls this formatter at
`0x520b5e2` (see `caller-replay.txt`). For a record of 11 bytes or less
it builds a status record with the detail builder `0x542f040` — code 2,
subcode 0, message `log record too small` — formats it here, and logs
`[WalManager] %s%s: dropping %d bytes; %s`. The full caller census is
178 direct call sites, 0 tail jumps, 0 qword references; the complete
site list with enclosing FDEs is in `callers.tsv`, regenerated by
`gen_callers.py`. The behavior of the other 177 callers is not claimed.

## Worked examples

- `(2, 0, "log record too small")` → `Corruption: log record too small`
- `(2, 5, "x")` → `Corruption: Deadlock: x`
- `(2, 5, None)` → `Corruption: Deadlock`
- `(0, 9, "ignored")` → `OK`
- `(16, 0, "m")` → `Unknown code(16): m`
- `(1, 0, None)` → `NotFound: `

## Environment limits

No cargo/rustc, no git-lfs, no Ghidra/Java on this VM. All claims are
static: disassembly, rodata strings, relocations, and the jump table of
the digest-verified binary. Nothing here executes target code.

Note on the excerpts: mnemonics such as `endbr64` in `window.txt` are
genuine instructions present in the target binary, emitted verbatim by
objdump — not placeholders. `verify.py` re-checks the excerpts against a
fresh objdump run and samples instructions byte-for-byte against the raw
binary.
