# RE-002 · Node #115 RocksDB ZSTD streaming destructors

Component: storage / compression. Target: Linux x86-64 node #115, SHA-256
`a6e2897cd051213d004802deca416e8eca62b7a8278fa39f249e98c3867b5301`.

## Bounded question

How does node #115 destroy a `rocksdb::ZSTDStreamingCompress` /
`rocksdb::ZSTDStreamingUncompress` holder — what does the deleting
destructor (D0) do that the complete-object destructor (D1) does not,
which engine function frees the context, and what, if anything, calls
either destructor directly? The four body hashes match the vendor
census exactly; the four source hashes are reproduced by zeroing the
census relocation fields (see `functions.tsv`). This is the follow-up
to the wrapper packet (open PR #5857: the two Create factories, the
Compress/Uncompress calls and the two Resets); the wrappers are
reconstructed there, not here. It also closes an open unknown the
merged compress-cache packet recorded: "no separate freeCCtx was found
in the census" and "the 0x70-byte holder's teardown is unpinned" — the
teardown is the D0/D1 pair below, and the free callee is 0x6219ac0.

## Answer (pinned)

**Call shape.** D1 is `~ZSTDStreamingCompress()` /
`~ZSTDStreamingUncompress()` with `rdi` = `this`; D0 is the same
signature and additionally tail-jumps to sized operator delete
(`_ZdlPvm`) with `(this, size)`. Both destructors are 36–45 bytes;
the whole function is the answer — there are no branches except the
null guard inside the engine free (see below).

**1. Vptr store first.** Each destructor starts by restoring the
most-derived vtable address point into `[this+0x00]` — compress
`lea 0x64d7408; add 0x10` → `0x64d7418`, uncompress `lea 0x64d7438;
add 0x10` → `0x64d7448` (the lea is the single kind-42 relocation in
each body, restored from `mov` to `lea` for the source hash). The
store precedes the engine free in all four bodies, so a
partially-destroyed holder still dispatches virtually to its own
class while its context is freed.

**2. Engine free.** Compress loads `[this+0x50]` (the CCtx the ctor
created) and calls `ZSTD_freeCCtx` at 0x6219ac0 (FDE
0x6219ac0..0x6219c13); uncompress loads `[this+0x18]` (the DCtx) and
calls `ZSTD_freeDCtx` at 0x628c1e0 (FDE 0x628c1e0..0x628c3cb,
census symbol confirmed). Both frees are null-tolerant — `test
rdi,rdi; je` to `xor eax,eax; ret` — so `free(NULL)` returns 0 and
frees nothing; the destructors ignore the return value either way.
The freeCCtx identification is by shape + role + twin (it is called
with the CCtx created at 0x6218920, it has the same null-guard
prologue and free-the-workspace body shape as the census-confirmed
freeDCtx, and it is the only zstd free that takes a CCtx); it has no
census symbol, so that label is honestly marked by-shape in
`records.json`. Nothing else is freed: the inBuffer is a plain
`{src, size, pos}` struct with no destructor, and neither body
touches `+0x58..+0x70` / `+0x20..+0x38`.

**3. The ctx slot is never nulled.** After the free, neither D1 nor
D0 writes the ctx slot again. A second D1 on the same holder would
therefore double-free the engine context. The model detects this via
its handle registry and records it as an outcome instead of executing
the second real free (which would be UB in the test process).

**4. D0 inlines D1, then deletes.** D0 does NOT call D1: the 45-byte
D0 bodies duplicate the D1 steps (vptr store + engine free) and then
tail-jump to `_ZdlPvm` with the holder size as the second argument —
`0x70` for compress, `0x38` for uncompress. Those sizes independently
confirm the holder sizes the factory packet established. D1 (36 B)
just returns after the free; the holder memory stays allocated.

**5. Nobody calls them directly.** The caller census
(`census.py`, whole-`.text` E8/E9/LEA scan, Capstone-validated from
enclosing FDE starts) finds ZERO direct calls, tail jumps or LEA refs
to any of the four destructors — a second raw scan without FDE
validation agrees. All destruction goes through vtable slots 0 (D1)
and 1 (D0): a base-pointer delete dispatches through the D0 slot.
That is also why D1 has no caller at all — not even D0.

## Cases

2,400 deterministic cases (`cases.tsv`, generated by
`tools/zstd_stream_destructors115.py gen-cases`; `tests/test_zstd_stream_destructors115.py`,
13 tests pass): 600 compress-live + 600 uncompress-live (each 200 D1,
200 D0, 100 D1-then-D1 double-free, 100 D0-then-D1 use-after-free) +
600 null-ctx (150 per family per destructor) + 600 ordering/size (150
per family per destructor). The engine free runs on a REAL context
handle from the system libzstd.so.1 (1.5.5) via ctypes; the double-free
and use-after-free sequences are detected by the model, not executed
literally. See `records.json` for the full ledger.

## Upstream confirmation (RocksDB v8.1.1)

The destructors are inline in `util/compression.h`, not in `.cc`
(`util/compression.cc` is 122 lines and contains no destructor):
`~ZSTDStreamingCompress()` at lines 1754–1758 calls
`ZSTD_freeCCtx(cctx_)` under `#ifdef ZSTD_STREAMING` and does nothing
else; `~ZSTDStreamingUncompress()` at lines 1779–1783 calls
`ZSTD_freeDCtx(dctx_)` the same way. `ZSTD_STREAMING` is defined
(compression.h:56–58) when `ZSTD_VERSION_NUMBER >= 10400`. The member
layout derives exactly the binary holder sizes (compress 80 + 8 + 24 =
112 = 0x70; uncompress 24 + 8 + 24 = 56 = 0x38). Both derived classes
are `final`; the destructors are `override` (virtual). `ZSTD_freeCCtx(NULL)`
/ `ZSTD_freeDCtx(NULL)` return 0 (zstd v1.5.5: `if (cctx==NULL) return 0;
/* support free on NULL */`). The D0 sized delete is compiler-generated,
not source.

## Open unknowns
- `ZSTD_freeCCtx` 0x6219ac0 has no census symbol: its identification
  is by shape + role + twin (see `records.json`).
- Which owner deletes the holders (the factory callers at 0x5f0430b /
  0x5f01e9d install the product into an owner/holder): the delete site
  dispatches through the vtable, so no direct call site exists to name.
